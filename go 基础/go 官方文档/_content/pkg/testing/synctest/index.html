synctest 包为测试并发代码提供支持。

Test 函数会在一个隔离的“测试气泡”（bubble）中运行函数。在气泡内启动的所有 goroutine 也都属于该气泡。

每个测试都应完全自包含。以下准则适用于大多数测试：

  • 避免与并非由该测试启动的 goroutine 交互。
  • 避免使用网络；需要时使用模拟网络实现。
  • 避免与外部进程交互。
  • 避免后台任务造成 goroutine 泄漏。

时间

在气泡内，time 包使用虚拟时钟。每个气泡都有自己的时钟，初始时间为 UTC 2000 年 1 月 1 日零点。

只有当气泡内的所有 goroutine 都处于持久阻塞状态时，气泡内的时间才会推进。“持久阻塞”的确切定义见下文。

例如，下面的测试会立即完成，而不需要等待两秒：

func TestTime(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		start := time.Now() // 始终为 UTC 2000-01-01 零点
		go func() {
			time.Sleep(1 * time.Second)
			t.Log(time.Since(start)) // 始终记录 "1s"
		}()
		time.Sleep(2 * time.Second) // 上面的 goroutine 会在此次 Sleep 返回之前运行
		t.Log(time.Since(start))    // 始终记录 "2s"
	})
}

气泡的根 goroutine 退出后，时间便停止推进。

阻塞

如果气泡内的某个 goroutine 已阻塞，而且只有同一气泡内的其他 goroutine 才能解除它的阻塞，就称其处于“持久阻塞”（durably blocked）状态。如果气泡外部发生的事件能够解除其阻塞，则不属于持久阻塞。

Wait 函数会一直阻塞，直到气泡内的其他所有 goroutine 都处于持久阻塞状态。

例如：

func TestWait(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		done := false
		go func() {
			done = true
		}()
		// Wait 会阻塞，直到上面的 goroutine 执行完毕。
		synctest.Wait()
		t.Log(done) // 始终记录 "true"
	})
}

当气泡内的所有 goroutine 都处于持久阻塞状态时：

  • 如果调用了 Wait，则 Wait 返回。
  • 否则，如果存在能够解除至少一个 goroutine 阻塞的下一个时间点，而且气泡的根 goroutine 尚未退出，时间就会推进到该时间点。
  • 否则便发生死锁，Test 会触发 panic。

以下操作会使 goroutine 持久阻塞：

  • 在气泡内创建的通道上执行阻塞的发送或接收操作。
  • 执行阻塞的 select 语句，且其中每个 case 所用的通道都在气泡内创建。
  • sync.Cond.Wait
  • sync.WaitGroup.Wait，前提是在气泡内调用了 sync.WaitGroup.Add。
  • time.Sleep

上述列表以外的操作不会造成持久阻塞。尤其是以下操作虽然可能阻塞 goroutine，却不属于持久阻塞，因为气泡外发生的事件能够解除其阻塞：

  • 对 sync.Mutex 或 sync.RWMutex 加锁。
  • 阻塞在 I/O 操作上，例如读取网络套接字。
  • 系统调用。

隔离

在气泡内创建的通道、time.Timer 或 time.Ticker 会与该气泡关联。在气泡外操作这些与气泡关联的通道、定时器或周期定时器会触发 panic。

sync.WaitGroup 会在首次调用 Add 或 Go 时与某个气泡关联。关联后，在气泡外调用 Add 或 Go 会引发致命错误。（受技术限制，定义为包级变量的 WaitGroup，例如“var wg sync.WaitGroup”，无法与气泡关联，对其执行的操作也可能不会造成持久阻塞。对于保存在包级变量中的 *WaitGroup，例如“var wg = new(sync.WaitGroup)”，则没有此限制。）

sync.Cond.Wait 会造成持久阻塞。从气泡外唤醒气泡内阻塞在 Cond.Wait 上的 goroutine 会引发致命错误。

通过 runtime.AddCleanup 和 runtime.SetFinalizer 注册的清理函数和终结器，会在所有气泡之外运行。

示例：Context.AfterFunc

此示例演示如何测试 context.AfterFunc 函数。

AfterFunc 注册一个函数，在上下文被取消后通过新的 goroutine 执行。

该测试验证：上下文取消之前，该函数不会执行；上下文取消之后，该函数会执行。

func TestContextAfterFunc(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		// 创建一个可取消的 context.Context。
		ctx, cancel := context.WithCancel(t.Context())

		// context.AfterFunc 注册一个函数，
		// 在上下文被取消时调用。
		afterFuncCalled := false
		context.AfterFunc(ctx, func() {
			afterFuncCalled = true
		})

		// 上下文尚未取消，因此不会调用 AfterFunc。
		synctest.Wait()
		if afterFuncCalled {
			t.Fatalf("before context is canceled: AfterFunc called")
		}

		// 取消上下文，并等待 AfterFunc 执行完毕。
		// 验证 AfterFunc 已经运行。
		cancel()
		synctest.Wait()
		if !afterFuncCalled {
			t.Fatalf("after context is canceled: AfterFunc not called")
		}
	})
}

示例：Context.WithTimeout

此示例演示如何测试 context.WithTimeout 函数。

WithTimeout 创建一个在超时时被取消的上下文。

该测试验证：超时之前，上下文不会被取消；超时之后，上下文会被取消。

func TestContextWithTimeout(t *testing.T) {
	synctest.Test(t, func(t *testing.T) {
		// 创建一个超时后被取消的 context.Context。
		const timeout = 5 * time.Second
		ctx, cancel := context.WithTimeout(t.Context(), timeout)
		defer cancel()

		// 等待略短于超时时间的一段时间。
		time.Sleep(timeout - time.Nanosecond)
		synctest.Wait()
		if err := ctx.Err(); err != nil {
			t.Fatalf("before timeout: ctx.Err() = %v, want nil\n", err)
		}

		// 继续等待剩余时间，直到超时。
		time.Sleep(time.Nanosecond)
		synctest.Wait()
		if err := ctx.Err(); err != context.DeadlineExceeded {
			t.Fatalf("after timeout: ctx.Err() = %v, want DeadlineExceeded\n", err)
		}
	})
}

示例：HTTP 100 Continue

此示例演示如何测试 [http.Transport] 对 100 Continue 的处理。

HTTP 客户端发送请求时，可以添加“Expect: 100-continue”请求头，告诉服务器还有数据需要发送。服务器随后可以回复一条 100 Continue 信息响应，要求客户端发送数据；也可以返回其他状态，告诉客户端不需要这些数据。例如，上传大文件的客户端可以利用此功能，在发送文件前确认服务器愿意接收该文件。

该测试验证：发送“Expect: 100-continue”请求头时，HTTP 客户端不会在服务器要求之前发送请求内容；收到 100 Continue 响应后，才会发送请求内容。

func TestHTTPTransport100Continue(t *testing.T) {
	synctest.Test(t, func(*testing.T) {
		// 创建一个进程内的模拟网络连接。
		// 此测试不能使用回环网络连接，
		// 因为阻塞在网络 I/O 上的 goroutine 会使 synctest
		// 气泡无法进入空闲状态。
		srvConn, cliConn := net.Pipe()
		defer cliConn.Close()
		defer srvConn.Close()

		tr := &http.Transport{
			// 使用上面创建的模拟网络连接。
			DialContext: func(ctx context.Context, network, address string) (net.Conn, error) {
				return cliConn, nil
			},
			// 启用 "Expect: 100-continue" 处理。
			ExpectContinueTimeout: 5 * time.Second,
		}

		// 发送一个设置了 "Expect: 100-continue" 请求头的请求。
		// 在新的 goroutine 中发送，因为请求直到测试结束时才会完成。
		body := "request body"
		go func() {
			req, _ := http.NewRequest("PUT", "http://test.tld/", strings.NewReader(body))
			req.Header.Set("Expect", "100-continue")
			resp, err := tr.RoundTrip(req)
			if err != nil {
				t.Errorf("RoundTrip: unexpected error %v\n", err)
			} else {
				resp.Body.Close()
			}
		}()

		// 读取客户端发送的请求头。
		req, err := http.ReadRequest(bufio.NewReader(srvConn))
		if err != nil {
			t.Fatalf("ReadRequest: %v\n", err)
		}

		// 启动一个新的 goroutine，将客户端发送的请求体复制到缓冲区。
		// 等待气泡内的所有 goroutine 阻塞，并验证此时
		// 尚未从客户端读到任何内容。
		var gotBody bytes.Buffer
		go io.Copy(&gotBody, req.Body)
		synctest.Wait()
		if got, want := gotBody.String(), ""; got != want {
			t.Fatalf("before sending 100 Continue, read body: %q, want %q\n", got, want)
		}

		// 向客户端写入 "100 Continue" 响应，并验证
		// 客户端发送了请求体。
		srvConn.Write([]byte("HTTP/1.1 100 Continue\r\n\r\n"))
		synctest.Wait()
		if got, want := gotBody.String(), body; got != want {
			t.Fatalf("after sending 100 Continue, read body: %q, want %q\n", got, want)
		}

		// 最后发送 "200 OK" 响应，结束本次请求。
		srvConn.Write([]byte("HTTP/1.1 200 OK\r\n\r\n"))

		// 测试期间我们启动了多个 goroutine。
		// synctest.Test 会等待它们全部退出后再返回。
	})
}

func Sleep 1.27 

func Sleep(d time.Duration)

Sleep 会阻塞，直到当前气泡的时钟向前推进了 d 这么长的时间，而且当前气泡内除当前 goroutine 以外的所有 goroutine 都处于持久阻塞状态。

这完全等价于：

time.Sleep(d)
synctest.Wait()

在测试中，这通常比只调用 time.Sleep 更合适。如果测试自身与运行被测系统的另一个 goroutine 休眠了完全相同的时长，就无法预测两者中哪一个会先继续运行。测试自身通常希望在休眠后等待被测系统进入“稳定状态”，Sleep 正是用来实现这一点的。

func Test 1.25 

func Test(t *testing.T, f func(*testing.T))

Test 在一个新的气泡中执行 f。

Test 会等待气泡内的所有 goroutine 退出后再返回。如果气泡内的 goroutine 发生死锁，测试会失败。

不得在气泡内部调用 Test。

传递给 f 的 *testing.T 具有以下特性：

  • T.Cleanup 注册的函数在气泡内部运行，执行时机紧邻 Test 返回之前。
  • T.Context 返回一个 context.Context，其 Done 通道与该气泡关联。
  • 不得调用 T.Run、T.Parallel 和 T.Deadline。
