exec 包用于运行外部命令。它封装了 os.StartProcess，使重新映射标准输入和标准输出、通过管道连接 I/O，以及其他调整更加方便。

与 C 等语言中的“system”库调用不同，os/exec 包有意不调用系统 shell，也不会展开任何通配模式，或处理通常由 shell 完成的其他展开、管道和重定向。本包的行为更接近 C 的“exec”系列函数。要展开通配模式，可以直接调用 shell，并注意转义任何危险输入；也可以使用 path/filepath 包的 Glob 函数。要展开环境变量，请使用 os 包的 ExpandEnv。

本包的示例以 Unix 系统为前提。它们可能无法在 Windows 上运行，也无法在 go.dev 和 pkg.go.dev 使用的 Go Playground 中运行。

当前目录中的可执行文件

Command 和 LookPath 函数遵循宿主操作系统的约定，在当前搜索路径列出的目录中查找程序。几十年来，操作系统一直会将当前目录纳入搜索，有时是隐式包含，有时是通过默认的显式配置包含。按照现代实践，将当前目录纳入搜索通常出乎使用者预料，而且常常会引发安全问题。

为避免这些安全问题，从 Go 1.19 开始，本包不会通过相对于当前目录的隐式或显式路径项来解析程序。也就是说，无论搜索路径如何配置，运行 LookPath("go") 都不会成功返回 Unix 上的 ./go 或 Windows 上的 .\go.exe。如果通常的路径搜索算法会得出这样的结果，这些函数会改为返回一个满足 errors.Is(err, ErrDot) 的错误 err。

例如，考虑下面两段程序：

path, err := exec.LookPath("prog")
if err != nil {
	log.Fatal(err)
}
use(path)

以及：

cmd := exec.Command("prog")
if err := cmd.Run(); err != nil {
	log.Fatal(err)
}

无论当前搜索路径如何配置，它们都不会查找并运行 ./prog 或 .\prog.exe。

始终希望运行当前目录中程序的代码，可以将“prog”改写为“./prog”。

坚持要接受相对路径项所得到结果的代码，可以通过 errors.Is 检查来忽略该错误：

path, err := exec.LookPath("prog")
if errors.Is(err, exec.ErrDot) {
	err = nil
}
if err != nil {
	log.Fatal(err)
}
use(path)

以及：

cmd := exec.Command("prog")
if errors.Is(cmd.Err, exec.ErrDot) {
	cmd.Err = nil
}
if err := cmd.Run(); err != nil {
	log.Fatal(err)
}

设置环境变量 GODEBUG=execerrdot=0 可以完全禁用 ErrDot 的产生，让暂时无法采用更有针对性修复的程序恢复到 Go 1.19 之前的行为。未来版本的 Go 可能会移除对此变量的支持。

在添加这类覆盖逻辑之前，请确保理解其安全影响。更多信息见 https://go.dev/blog/path-security。

ErrDot 表示路径搜索因为搜索路径中隐式或显式包含“.”，而解析到了当前目录中的可执行文件。详细说明见包文档。

本包中的函数不会直接返回 ErrDot。代码应使用 errors.Is(err, ErrDot)，而非 err == ErrDot，判断返回的错误 err 是否由这种情况引起。

var ErrDot = errors.New("cannot run executable found relative to current directory")

当路径搜索未能找到可执行文件时，会返回 ErrNotFound 错误。

var ErrNotFound = errors.New("executable file not found in $PATH")

如果进程以表示成功的状态码退出，但在命令的 WaitDelay 到期之前，其输出管道仍未关闭，则 Cmd.Wait 返回 ErrWaitDelay。

var ErrWaitDelay = errors.New("exec: WaitDelay expired before I/O complete")

func LookPath 

func LookPath(file string) (string, error)

LookPath 遵循宿主操作系统的约定，在当前搜索路径中查找名为 file 的可执行文件。如果 file 包含斜杠，则直接尝试该路径，不查询默认搜索路径。否则，成功时返回的结果是绝对路径。

如果解析得到的路径相对于当前目录，LookPath 会返回满足 errors.Is(err, ErrDot) 的错误。更多细节见包文档。

除下述情况外，LookPath 在 PATH 环境变量指定的目录中查找名为 file 的可执行文件。

  • 在 Windows 上，文件扩展名必须在 PATHEXT 环境变量列出的范围内。未设置 PATHEXT 时，文件扩展名必须是“.com”、“.exe”、“.bat”或“.cmd”。
  • 在 Plan 9 上，LookPath 查询 path 环境变量。如果 file 以“/”、“#”、“./”或“../”开头，则直接尝试该路径，不查询 path。
  • 在 Wasm 上，LookPath 始终返回错误。

type Cmd
				
				
			

			
Cmd 表示一个正在准备执行或正在运行的外部命令。
调用 Cmd.Start、Cmd.Run、Cmd.Output 或 Cmd.CombinedOutput 方法后，Cmd 不能复用。
type Cmd struct {
    // Path 是要运行的命令的路径。
    //
    // 这是唯一必须设置为非零值的
    // 字段。如果 Path 是相对路径，则相对于
    // Dir 进行解析。
    Path string

    // Args 保存命令行参数，其中 Args[0] 是命令本身。
    // 如果 Args 为空或 nil，Run 使用 {Path}。
    //
    // 通常通过调用 Command 同时设置 Path 和 Args。
    Args []string

    // Env 指定进程的环境变量。
    // 每一项的形式都是 "key=value"。
    // 如果 Env 为 nil，新进程会使用当前进程的
    // 环境变量。
    // 如果 Env 包含重复的环境变量键，则每个重复键只使用
    // 切片中最后出现的值。
    // Windows 上有一个特殊情况：如果缺少 SYSTEMROOT，
    // 而且没有显式将其设为空字符串，就会自动添加。
    //
    // 另请参阅 Dir 字段；该字段可能设置环境中的 PWD。
    Env []string

    // Dir 指定命令的工作目录。
    // 如果 Dir 是空字符串，Run 会在调用进程的
    // 当前目录中运行命令。
    //
    // 在 Unix 系统上，如果未另行指定，Dir 的值也会决定
    // 子进程的 PWD 环境变量。
    // Unix 进程表示工作目录时，
    // 使用的是对文件树中某个节点的隐式引用，
    // 而不是目录名称。因此，如果子进程通过
    // 调用 C 的 getcwd 等函数获取工作目录，
    // 这些函数会沿文件树向上遍历，计算规范名称；
    // 如果 Dir 的原始值是一个包含符号链接的
    // 别名，便无法恢复该原始值。不过，如果
    // 子进程调用 Go 的 [os.Getwd] 或 GNU C 的
    // get_current_dir_name，而且 PWD 的值是
    // 当前目录的别名，则这些函数会返回
    // PWD 的值，也就是与 Dir 相同的值。
    Dir string

    // Stdin 指定进程的标准输入。
    //
    // 如果 Stdin 为 nil，进程从空设备（os.DevNull）读取。
    //
    // 如果 Stdin 是 *os.File，进程的标准输入会直接
    // 连接到该文件。
    //
    // 否则，在命令执行期间，会有一个独立的
    //  goroutine 从 Stdin 读取数据，并通过管道
    // 将数据传给命令。这种情况下，Wait 要等该 goroutine
    // 停止复制数据后才会完成：可能是因为已经读到 Stdin 末尾
    // （EOF 或读取错误），也可能是向管道写入时返回了错误，
    // 或者设置了非零 WaitDelay 且等待时间已到期。
    //
    // 无论 WaitDelay 如何设置，Wait 都可能阻塞，直到从
    // Stdin 进行的一次 Read 完成。如果需要使用会阻塞的 io.Reader，
    // 请调用 StdinPipe 获取管道，将 Reader 中的数据复制到
    // 管道，并安排在 Wait 返回后关闭 Reader。
    Stdin io.Reader

    // Stdout 和 Stderr 分别指定进程的标准输出和标准错误输出。
    //
    // 如果其中某个为 nil，Run 会将对应的文件描述符
    // 连接到空设备（os.DevNull）。
    //
    // 如果其中某个是 *os.File，进程的相应输出会
    // 直接连接到该文件。
    //
    // 否则，在命令执行期间，会有一个独立的 goroutine
    // 通过管道读取进程输出，并将数据交给
    // 对应的 Writer。这种情况下，Wait 要等该
    //  goroutine 读到 EOF、遇到错误，或非零 WaitDelay
    // 到期后才会完成。
    //
    // 无论 WaitDelay 如何设置，Wait 都可能阻塞，直到对
    // Stdout 或 Stderr 进行的一次 Write 完成。如果需要使用会阻塞的 io.Writer，
    // 请调用 StdoutPipe 或 StderrPipe 获取管道，
    // 将管道中的数据复制到 Writer，并安排在
    // Wait 返回后关闭 Writer。
    //
    // 如果 Stdout 和 Stderr 是同一个写入器，且其类型支持
    // 使用 == 比较，则同一时刻最多只有一个 goroutine 调用 Write。
    Stdout io.Writer
    Stderr io.Writer

    // ExtraFiles 指定由新进程继承的其他已打开文件。
    // 它不包括标准输入、标准输出和
    // 标准错误输出。如果不为 nil，第 i 项对应文件描述符 3+i。
    //
    // Windows 不支持 ExtraFiles。
    ExtraFiles []*os.File

    // SysProcAttr 保存可选的、特定于操作系统的属性。
    // Run 将它作为 os.ProcAttr 的 Sys 字段传给 os.StartProcess。
    SysProcAttr *syscall.SysProcAttr

    // Process 是启动后的底层进程。
    Process *os.Process

    // ProcessState 包含已退出进程的信息。
    // 如果进程成功启动，Wait 或 Run 会在
    // 命令完成时填充其 ProcessState。
    ProcessState *os.ProcessState

    Err error // LookPath 产生的错误（如有）；Go 1.19 新增

    // 如果 Cancel 非 nil，命令必须是通过
    // CommandContext 创建的；命令的 Context 结束时
    // 会调用 Cancel。默认情况下，CommandContext 将 Cancel 设置为
    // 调用命令的 Process 的 Kill 方法。
    //
    // 自定义的 Cancel 通常会向命令的 Process
    // 发送信号，也可以采取其他措施发起取消，
    // 例如关闭标准输入或标准输出管道，或者通过
    // 网络套接字发送关闭请求。
    //
    // 如果 Cancel 被调用后，命令以成功状态退出，
    // 而且 Cancel 返回的错误并不等价于
    // os.ErrProcessDone，那么 Wait 等方法会返回非 nil
    // 错误：可能是包装了 Cancel 所返回错误的错误，
    // 也可能是 Context 的错误。
    // （如果命令以非成功状态退出，或者 Cancel
    // 返回了包装 os.ErrProcessDone 的错误，Wait 等方法
    // 仍会返回命令通常的退出状态。）
    //
    // 如果将 Cancel 设置为 nil，命令的 Context 结束时
    // 不会立即发生任何操作，但非零 WaitDelay 仍会生效。
    // 例如，有些命令不支持关闭信号，但预期总能很快执行完毕，
    // 这种配置可以帮助规避这些命令中的死锁。
    //
    // 如果 Start 返回非 nil 错误，则不会调用 Cancel。
    Cancel func() error // Go 1.20

    // 如果 WaitDelay 非零，它会限制 Wait 中两类
    // 意外延迟的等待时间：关联的 Context 取消后
    // 子进程仍未退出，以及子进程已经退出
    // 但没有关闭其 I/O 管道。
    //
    // 关联的 Context 结束，或者 Wait 调用观察到
    // 子进程已经退出时，会启动 WaitDelay 计时器，
    // 以先发生者为准。等待时间到期后，命令会关闭子进程
    // 以及／或者它的 I/O 管道。
    //
    // 如果子进程尚未退出，例如因为它忽略了或没有收到
    // Cancel 函数发送的关闭信号，或者没有设置
    // Cancel 函数，则使用 os.Process.Kill 终止子进程。
    //
    // 随后，如果与子进程通信的 I/O 管道仍然打开，
    // 则关闭这些管道，解除所有正在阻塞于
    // Read 或 Write 调用的 goroutine 的阻塞。
    //
    // 如果管道因为 WaitDelay 而关闭，没有发生 Cancel 调用，
    // 且命令在其他方面已以成功状态退出，则 Wait 等
    // 方法返回 ErrWaitDelay，而不是 nil。
    //
    // 如果 WaitDelay 为零（默认值），会持续读取 I/O 管道，直到 EOF；
    // 只有当该命令遗留的孤儿子进程也都关闭了
    // 这些管道对应的描述符后，才可能读到 EOF。
    WaitDelay time.Duration // Go 1.20
    // 包含已过滤或未导出的字段
}



			

			

			

			
				
func Command
					
					
				

				
func Command(name string, arg ...string) *Cmd

				
Command 返回一个 Cmd 结构体，用于以给定参数执行指定程序。
它只设置返回结构体中的 Path 和 Args 字段。
如果 name 不包含路径分隔符，Command 会使用 LookPath，尽可能将 name 解析为完整路径。否则，直接使用 name 作为 Path。
返回的 Cmd 的 Args 字段由命令名称以及后续的 arg 元素组成，因此 arg 不应包含命令名称本身，例如 Command("echo", "hello")。Args[0] 始终为 name，而不是可能已经解析过的 Path。
在 Windows 上，进程以单个字符串的形式接收完整命令行，并自行解析。Command 使用一种兼容 CommandLineToArgvW 的算法，将 Args 合并并添加引号，生成命令行字符串；使用 CommandLineToArgvW 是最常见的解析方式。值得注意的例外是 msiexec.exe 和 cmd.exe（因此也包括所有批处理文件），它们使用不同的去引号算法。遇到这些或其他类似情况时，可以自行处理引号，在 SysProcAttr.CmdLine 中提供完整命令行，并将 Args 留空。

func CommandContext
					
					1.7
				

				
func CommandContext(ctx context.Context, name string, arg ...string) *Cmd

				
CommandContext 类似 Command，但额外接收一个上下文。
如果命令自行完成之前，所提供的上下文已结束，则使用该上下文中断进程，具体通过调用 cmd.Cancel 或 os.Process.Kill 实现。
CommandContext 将命令的 Cancel 函数设置为调用其 Process 的 Kill 方法，并保持 WaitDelay 未设置。调用方可以在启动命令之前修改这些字段，以改变取消行为。

func (*Cmd) Run
					
					
				

				
func (c *Cmd) Run() error

				
Run 启动指定命令，并等待其完成。
如果命令成功运行，复制标准输入、标准输出和标准错误输出时未发生问题，并且以零退出状态结束，则返回的错误为 nil。
如果命令已启动，但未成功完成，错误类型为 *ExitError。其他情况可能返回其他类型的错误。
如果调用方 goroutine 通过 runtime.LockOSThread 锁定了操作系统线程，并修改了任何可继承的操作系统线程状态（例如 Linux 或 Plan 9 的命名空间），新进程会继承调用方的线程状态。

func (*Cmd) StderrPipe
					
					
				

				
func (c *Cmd) StderrPipe() (io.ReadCloser, error)

				
StderrPipe 返回一个管道，命令启动时该管道会连接到命令的标准错误输出。
Cmd.Wait 在发现命令退出后会关闭该管道，因此大多数调用方无需自行关闭。在完成管道的全部读取之前调用 Wait 是错误用法。出于同样的原因，使用 StderrPipe 时使用 Cmd.Run 也是错误用法。惯用写法参见 StdoutPipe 示例。

String 返回供人阅读的 c 的描述，仅用于调试。尤其是，它不适合用作 shell 的输入。String 的输出可能随 Go 版本变化。
func (*Cmd) Wait
					
					
				

				
func (c *Cmd) Wait() error

				
Wait 等待命令退出，并等待向标准输入复制数据、从标准输出或标准错误输出复制数据的操作完成。
命令必须已经通过 Cmd.Start 启动。
如果命令成功运行，复制标准输入、标准输出和标准错误输出时未发生问题，并且以零退出状态结束，则返回的错误为 nil。
如果命令未能运行或未成功完成，错误类型为 *ExitError。I/O 问题可能返回其他类型的错误。
如果 c.Stdin、c.Stdout 或 c.Stderr 中的任意一个不是 *os.File，Wait 还会等待相应的 I/O 循环完成向进程或从进程复制数据的工作。
多个 goroutine 不得并发调用 Wait。自定义的 Cmd.Cancel 函数不应调用 Wait。
Wait 会释放与 Cmd 关联的所有资源。
type Error
				
				
			

			
当 LookPath 无法将文件判定为可执行文件时，会返回 Error。
type Error struct {
    // Name 是发生错误的文件名。
    Name string
    // Err 是底层错误。
    Err error
}

type ExitError
				
				
			

			
ExitError 表示命令未成功退出。
type ExitError struct {
    *os.ProcessState

    // 如果没有通过其他方式收集标准错误输出，
    // Stderr 会保存 Cmd.Output 方法产生的
    // 标准错误输出的一部分。
    //
    // 如果错误输出很长，Stderr 可能只包含输出的
    // 开头和结尾，中间部分替换为说明
    // 省略字节数的文本。
    //
    // Stderr 用于调试，可以将其加入错误消息。
    // 有其他需求的使用者应按需重定向 Cmd.Stderr。
    Stderr []byte // Go 1.6
}
