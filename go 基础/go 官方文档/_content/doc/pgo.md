# 概述 {#overview}

基于性能剖析的优化（PGO），也称反馈驱动优化（Feedback-Directed Optimization，FDO），是一种编译器优化技术：将应用程序在有代表性的运行过程中采集的信息（profile，性能剖析数据）反馈给编译器，用于下一次构建。编译器利用这些信息作出更有依据的优化决策。例如，对于剖析数据显示调用频繁的函数，编译器可能采用更积极的内联策略。

Go 编译器使用 pprof 格式的 CPU 剖析数据作为输入，例如通过 [runtime/pprof](https://pkg.go.dev/runtime/pprof) 或 [net/http/pprof](https://pkg.go.dev/net/http/pprof) 采集的数据。

截至 Go 1.22，对一组具有代表性的 Go 程序进行基准测试发现，使用 PGO 构建可带来约 2%～14% 的性能提升。随着未来 Go 版本中更多优化利用 PGO，预计总体收益还会增加。


# 采集性能剖析数据 {#collecting-profiles}

Go 编译器要求 PGO 输入为 pprof 格式的 CPU 剖析数据。Go 运行时生成的数据（例如通过 [runtime/pprof](https://pkg.go.dev/runtime/pprof) 和 [net/http/pprof](https://pkg.go.dev/net/http/pprof) 采集）可以直接作为编译器输入。其他性能分析系统的数据也可能直接使用或经转换后使用，详情见[附录](#alternative-sources)。

要取得最佳效果，剖析数据必须能够_代表_应用程序在生产环境中的实际行为。缺乏代表性的数据，通常只能带来很小的性能提升，甚至没有提升。因此，建议直接从生产环境采集；这也是 Go PGO 设计时主要面向的使用方式。

典型工作流程如下：

1. 构建并发布最初的二进制文件（不使用 PGO）。
2. 从生产环境采集剖析数据。
3. 发布更新版本时，使用最新源码构建，并提供生产环境采集的数据。
4. 回到第 2 步。

通常，Go PGO 能够容忍被采样的应用版本与使用该数据构建的版本之间存在差异，也能够使用从已优化程序中采集的数据继续构建。这使上述迭代流程成为可能。更多说明见 [AutoFDO](#autofdo) 一节。

如果难以或无法从生产环境采集数据（例如向最终用户分发的命令行工具），也可以从具有代表性的基准测试中采集。但构建这样的基准测试往往很难，随着应用演进持续保持代表性同样困难。尤其要注意，_微基准测试通常不适合作为 PGO 的数据来源_，因为它们只覆盖应用的一小部分，应用到整个程序时收益有限。

# 使用 PGO 构建 {#building}

标准做法是将 pprof CPU 剖析数据以 `default.pgo` 为文件名，保存到被采样程序的 main 包目录。默认情况下，`go build` 会自动检测 `default.pgo` 并启用 PGO。

建议将剖析数据直接提交到源码仓库，因为它也是构建输入，对于可复现且具有良好性能的构建很重要。与源码一起保存还可以简化构建：获取源码后，无需额外步骤获取剖析数据。

对于更复杂的情况，可以使用 `go build -pgo` 标志控制剖析数据的选择。其默认值是 `-pgo=auto`，对应上述 `default.pgo` 行为。设置为 `-pgo=off` 则完全禁用 PGO 优化。

如果无法使用 `default.pgo`（例如同一程序在不同场景中使用不同数据，或无法将数据与源码一起保存），可以直接传入数据文件路径，例如 `go build -pgo=/tmp/foo.pprof`。

_注意：传给 `-pgo` 的路径会应用于所有 main 包。例如，`go build -pgo=/tmp/foo.pprof ./cmd/foo ./cmd/bar` 会将 `foo.pprof` 同时应用于 `foo` 和 `bar`，这通常不符合预期。不同程序一般应使用各自的剖析数据，并分别调用 `go build`。_

_注意：Go 1.21 之前的默认值为 `-pgo=off`，必须显式启用 PGO。_

# 注意事项 {#notes}

## 从生产环境采集有代表性的数据 {#collecting-representative-profiles-from-production}

如[采集性能剖析数据](#collecting-profiles)所述，生产环境最能提供具有代表性的应用剖析数据。

最简单的入门方式是向应用添加 [net/http/pprof](https://pkg.go.dev/net/http/pprof)，然后从任意一个服务实例获取 `/debug/pprof/profile?seconds=30`。这是很好的起点，但采样可能因以下原因缺乏代表性：

* 该实例平时很忙，但采样时恰好处于空闲状态。

* 流量模式随一天中的时段变化，程序行为也相应变化。

* 实例执行耗时较长的操作，例如先用 5 分钟执行操作 A，再用 5 分钟执行操作 B。30 秒的采样可能只覆盖一种操作。

* 不同实例接收的请求分布不均衡，一些实例接收某类请求的比例更高。

更稳妥的策略是在不同时间从不同实例采集多份数据，以减少单个实例差异的影响。随后可将多份数据[合并](#merging-profiles)为一份，用于 PGO。

许多组织会运行“持续性能剖析”服务，自动对整个服务集群进行这类抽样采集。这些数据也可以作为 PGO 的输入。

## 合并剖析数据 {#merging-profiles}

可以用 pprof 工具按如下方式合并多份剖析数据：

```
$ go tool pprof -proto a.pprof b.pprof > merged.pprof
```

合并实质上是直接累加输入数据中的样本，不考虑每份数据的实际采样时长。因此，对应用运行过程中的一小段时间进行采样时（例如持续运行的服务器），通常应确保每份数据的实际采样时长相同，例如都采集 30 秒。否则，采集时间更长的数据会在合并结果中占据过高比重。

## AutoFDO {#autofdo}

Go PGO 的设计支持类似“[AutoFDO](https://research.google/pubs/pub45290/)”的工作流程。

下面仔细看看[采集性能剖析数据](#collecting-profiles)中介绍的流程：

1. 构建并发布最初的二进制文件（不使用 PGO）。
2. 从生产环境采集剖析数据。
3. 发布更新版本时，使用最新源码构建，并提供生产环境采集的数据。
4. 回到第 2 步。

这个流程看起来很简单，但有几个关键性质：

* 开发工作一直在进行，因此被采样程序的源码（第 2 步）与当前用于构建的最新源码（第 3 步）通常略有不同。Go PGO 能容忍这种差异，我们称之为_源码稳定性_。

* 这是一个闭环。第一次迭代之后，被采样的程序已经使用上一轮剖析数据进行过 PGO 优化。Go PGO 也能适应这种情况，我们称之为_迭代稳定性_。

_源码稳定性_通过启发式匹配实现：将剖析数据中的样本与正在编译的源码对应起来。因此，许多源码修改（例如新增函数）不会影响现有代码的匹配。如果编译器无法匹配修改后的代码，就会失去部分优化机会，但这是_平缓退化_。某个函数匹配失败可能使其无法获得优化，不过 PGO 的总体收益通常分布在许多函数中。匹配与退化的更多细节见[源码稳定性](#source-stability)。

_迭代稳定性_用于避免连续多次 PGO 构建中的性能周期性波动，例如第 1 次快、第 2 次慢、第 3 次又快。我们利用 CPU 剖析数据识别热点函数并进行优化。理论上，某个热点函数可能被 PGO 大幅加速，以至于下一轮数据中不再是热点，因而不被优化，又重新变慢。Go 编译器对 PGO 优化采用保守策略，我们认为这能避免显著波动。如果你观察到这类不稳定现象，请在 [go.dev/issue/new](/issue/new) 提交问题。

源码稳定性与迭代稳定性结合后，通常无需采用两阶段构建：先发布未优化版本作为小流量试运行版本进行采样，再用 PGO 重新构建并投产。除非必须追求绝对极致的性能，否则不必这样做。

## 源码稳定性与重构 {#source-stability}

如前所述，Go PGO 会尽可能将旧剖析数据中的样本匹配到当前源码。具体来说，Go 使用函数内部的行偏移，例如函数 foo 第 5 行上的调用。

许多常见修改不会破坏匹配，包括：

* 修改文件中热点函数之外的部分，例如在函数前后新增或修改代码。

* 将函数移到同一包的另一个文件中；编译器完全不依赖源文件名进行匹配。

以下修改可能破坏匹配：

* 修改热点函数内部的代码，可能影响行偏移。

* 重命名函数，或在方法的情况下重命名其接收者类型，这会改变符号名。

* 将函数移到另一个包，这也会改变符号名。

如果剖析数据较新，差异通常只影响少量热点函数，因此匹配失败导致的优化损失有限。不过，退化会随时间逐渐积累，因为代码很少会重构回原来的样子。因此，应定期采集新数据，以减少与生产环境源码的差异。

如果大规模重构重命名了许多函数，或将它们移动到其他包，匹配质量可能显著下降。这时，在新数据反映新结构之前，性能可能暂时降低。

对于机械性的重命名，理论上可以改写现有剖析数据，将旧符号名替换为新名称。[github.com/google/pprof/profile](https://pkg.go.dev/github.com/google/pprof/profile) 提供了所需的基础能力，但原文撰写时尚无现成工具。

## 新增代码的性能 {#performance-of-new-code}

新增代码或通过开关启用新执行路径时，首次构建使用的剖析数据中没有这些代码，所以它们暂时无法获得 PGO 优化，直到采集到包含这些新代码的数据。评估新代码的发布效果时，应注意最初版本的性能并不代表稳定运行后的性能。

# 常见问题 {#faq}

## 可以用 PGO 优化 Go 标准库包吗？ {#is-it-possible-to-optimize-go-standard-library-packages-with-pgo}

可以。Go 的 PGO 面向整个程序。所有包都会重新构建并考虑适用的 PGO 优化，包括标准库包。

## 可以用 PGO 优化依赖模块中的包吗？ {#is-it-possible-to-optimize-packages-in-dependent-modules-with-pgo}

可以。Go 的 PGO 面向整个程序。所有包都会重新构建并考虑适用的 PGO 优化，包括依赖包。这意味着，应用使用某个依赖的具体方式，会影响该依赖得到的优化。

## 使用缺乏代表性的数据，会比不使用 PGO 更慢吗？ {#will-pgo-with-an-unrepresentative-profile-make-my-program-slower-than-no-pgo}

原则上不会。虽然不代表生产环境行为的数据可能把优化机会用在冷代码上，但不应使热点代码变慢。如果遇到开启 PGO 后性能反而降低的程序，请在 [go.dev/issue/new](/issue/new) 提交问题。

## 不同 GOOS/GOARCH 的构建可以使用同一份数据吗？ {#can-i-use-the-same-profile-for-different-goosgoarch-builds}

可以。不同操作系统和架构配置下，剖析数据格式相同，因此可以跨配置使用。例如，从 linux/arm64 程序采集的数据可用于 windows/amd64 构建。

不过，[上文](#autofdo)有关源码稳定性的限制也适用。不同配置之间存在差异的源码无法匹配到相应优化。对大多数应用而言，绝大部分代码与平台无关，所以这种退化通常有限。

例如，`os` 包中的文件操作内部实现在 Linux 和 Windows 上不同。即使这些函数在 Linux 数据中是热点，Windows 对应实现也因无法匹配而不能获得这些 PGO 优化。

可以合并不同 GOOS/GOARCH 构建的剖析数据。这样做的取舍见下一问。

## 同一个程序用于不同类型的工作负载时，应该如何处理？ {#how-should-i-handle-a-single-binary-used-for-different-workload-types}

没有适用于所有情况的明确答案。同一个程序用于不同工作负载时，热点部分可能不同，也需要不同的优化。例如，同一个数据库在某个服务中以读取为主，在另一个服务中以写入为主。

有以下三种选择：

1. 为每种工作负载分别构建：使用对应负载的剖析数据，生成多个专用二进制文件。这能为每种负载提供最佳性能，但管理多个程序版本和数据来源会增加运维复杂度。

2. 只使用“最重要”负载的数据构建一个程序：选择资源占用最大或对性能最敏感的工作负载，仅使用它的数据构建。这能为选中的负载提供最佳性能；其他负载通常也能因公共代码得到优化而略有改善。

3. 合并不同负载的数据：按各负载的总体资源占用加权，将数据合并为一份代表整个集群的剖析数据，再用于构建一个通用程序。这通常能让所有负载获得适度的性能提升。

## PGO 如何影响构建时间？ {#how-does-pgo-affect-build-time}

启用 PGO 通常会使包的构建时间出现可测量的增加。主要原因是剖析数据会应用于程序中的所有包，因此首次使用某份数据时，需要重新构建依赖图中的每个包。这些构建结果和普通构建一样会被缓存，所以后续使用同一份数据进行增量构建时，无需全部重建。

如果构建时间异常增加，请在 [go.dev/issue/new](/issue/new) 提交问题。

## PGO 如何影响二进制文件大小？ {#how-does-pgo-affect-binary-size}

额外的函数内联可能使使用 PGO 构建的二进制文件稍大。

# 附录：其他剖析数据来源 {#alternative-sources}

Go 运行时生成的 CPU 剖析数据（例如通过 [runtime/pprof](https://pkg.go.dev/runtime/pprof)）已经采用正确格式，可以直接用于 PGO。不过，一些组织可能希望使用其他工具，例如 Linux perf，或已有的集群持续性能剖析系统。

只要满足以下要求，其他来源的数据转换为 [pprof 格式](https://github.com/google/pprof/tree/main/proto)后，也可以用于 Go PGO：

* 至少有一个样本值索引的类型/单位为 `"samples"`/`"count"` 或 `"cpu"`/`"nanoseconds"`。

* 样本应表示采样位置消耗的 CPU 时间。

* 数据必须经过符号解析，即设置 [Function.name](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L208)。

* 样本必须包含内联函数的栈帧。缺少这些信息，Go 就无法维持迭代稳定性。

* 必须设置 [Function.start_line](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L215)。它是函数起始行号，也就是包含 `func` 关键字的那一行。Go 编译器使用该字段计算样本在函数内的行偏移：`Location.Line.line - Function.start_line`。**许多现有 pprof 转换工具会省略这个字段，需要特别注意。**

_注意：Go 1.21 之前的 DWARF 元数据不包含函数起始行（`DW_AT_decl_line`），可能导致工具难以确定起始行。_

特定第三方工具与 PGO 的兼容性说明，请参阅 Go Wiki 的 [PGO 工具](/wiki/PGO-Tools)页面。
