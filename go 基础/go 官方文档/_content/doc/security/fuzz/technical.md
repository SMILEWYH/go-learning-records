本文概述 Go 原生模糊测试实现的技术细节，供贡献者参考。

## 总体架构 {#general-architecture}

模糊测试器使用一个协调进程管理语料集，以及多个工作进程变异输入并执行测试目标。协调进程与工作进程通过基于管道的 JSON RPC 协议以及共享虚拟内存区域通信。

对于每个工作进程，协调进程会创建一个 goroutine，由它启动工作进程并建立跨进程通信。各 goroutine 随后从共享通道读取指令，并转发给对应的工作进程。共享通道由协调进程的主循环提供数据。

协调进程的主循环从语料集中选取输入，发送到工作端共享通道。从通道取到该输入的 goroutine 会向对应工作进程发送模糊测试请求。工作进程循环变异输入并执行测试目标，直到某次执行使覆盖率计数器增加、引发 panic 或崩溃，或者超过预定截止时间。

如果变异后的输入使覆盖率计数器增加，或引发可恢复的 panic，工作进程会通知协调进程，后者据此重建该输入。协调进程会尝试[最小化输入](#input-minimization)：若输入拓展了覆盖率，就将其加入语料集用于进一步测试；若输入引发错误或 panic，就写入 testdata 目录。

如果模糊测试中发生导致工作进程停止的不可恢复错误，例如死循环、os.Exit、内存耗尽等，则不尝试最小化，而是直接将失败输入写入 testdata 目录并报告。

### 跨进程通信 {#cross-process-communication}

启动子工作进程时，协调进程建立两种通信方式：通过管道传递 JSON RPC 消息，通过共享内存区域传递输入和随机数生成器（RNG）状态。每个工作进程都有独立的管道和共享内存区域。

协调进程通过 RPC 管道发送模糊测试或最小化指令，以控制工作进程；工作进程则通过管道返回执行结果，例如输入是否拓展覆盖率、是否导致崩溃、是否成功最小化等。

共享内存区域用于与工作进程交换特定信息。协调进程通过该区域传入待测试的语料条目，工作进程则在其中保存当前 RNG 状态。工作进程完成目标执行后，协调进程利用该状态重建它对输入施加的变异。无论工作进程正常退出还是崩溃，都会进行这种重建。

## 输入选择 {#input-selection}

协调进程目前没有实现复杂的输入优先级策略，而是遍历整个语料集，遍历结束后重新开始。

同样，协调进程也没有实现语料集最小化。它与[下文介绍的输入最小化](#input-minimization)不同。

## 覆盖率引导 {#coverage-guidance}

模糊测试器使用[与 libFuzzer 兼容](https://clang.llvm.org/docs/SanitizerCoverage.html#inline-8bit-counters)的内联 8 位覆盖率计数器。编译时在每条代码控制流边上插入计数器，进入该边时递增。计数器不进行溢出保护，因此不会停留在饱和值。

与 AFL 和 libFuzzer 类似，跟踪覆盖率时会将计数值量化为最接近的 2 的幂，以区分执行流程中无关紧要和有意义的变化。为跟踪这些变化，测试器保存一个映射到各内联计数器的字节切片，其中各比特表示：语料集中是否至少存在一个输入，能使对应计数器递增至少 2^bit-position 次。如果已有输入使计数器命中过所有量化区间，相应字节就会饱和，此后该计数器不再提供新的有效覆盖信息。

由于编译时会在每条控制流边上插入计数器，并未被模糊测试直接针对的代码也会插桩。因此，工作进程可能检测到与当前测试目标无关的覆盖增长，例如某个无关 goroutine 触发了新代码路径。工作进程通过两种方式减小这种影响：一是在执行测试目标前立即重置全部计数器，并在目标返回后立即获取快照；二是显式忽略一组容易产生“噪声”的包。

以下包明确不插入计数器，因为它们容易引入与当前测试目标无关的计数器噪声：

* `context`
* `internal/fuzz`
* `reflect`
* `runtime`
* `sync`
* `sync/atomic`
* `syscall`
* `testing`
* `time`

## 变异引擎 {#mutation-engine}

工作进程收到新输入后，会先对其进行变异，再用变异后的输入执行测试目标。每次变异后都执行一次目标；如果没有拓展覆盖率，就继续变异。为避免输入与初始状态偏离过大，对同一个输入施加五次变异后，会先将它恢复到原始状态，再继续变异。例如，对于输入 `hello world`，变异策略可能如下：

```
0. hello world [initial state]
1. kello world [replace first byte]
2. world kello [swap two chunks]
3. world ke    [delete last three bytes]
4. owrld ke    [shuffle first three bytes]
5. owrldx ke   [insert random byte]
6. ello world  [reset to initial state, delete first byte]
...
```

为了防止语料集体积快速增长，变异器会倾向于生成较小的输入。

`[]byte` 和 `string` 类型有许多变异器；各类 `int`、`uint` 和 `float` 类型的变异器则相对较少。

目前尚未实现由执行反馈驱动的变异策略，例如输入与比较操作之间的关联分析，也没有基于字典的变异器。

## 输入最小化 {#input-minimization}

为防止语料集膨胀，我们会尝试最小化每个新发现、能够拓展覆盖率或引发可恢复崩溃的输入。语料集膨胀既会降低性能，也会降低一次变异实际触及有价值数据的概率。对于内存耗尽等导致的不可恢复崩溃，不进行最小化，因为过程会非常缓慢。所采用的最小化策略较简单：在保持最初发现的覆盖信息的同时，依次尝试删除输入中的字节，具体如下：

1. 尝试从输入末尾截去字节块，每次尝试的块大小按指数递减。
2. 尝试逐个删除字节。
3. 尝试删除每一种可能的字节子集。
4. 尝试将每个不便于人阅读的字节替换为可读字节，例如 ASCII 字符集中的可读字符。
