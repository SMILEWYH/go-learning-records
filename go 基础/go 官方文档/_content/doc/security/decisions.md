## 概述 {#overview}

本文记录 Go 安全团队对各类常见报告问题的判定，主要用于说明哪些问题不被视为漏洞。

本列表并非穷尽所有情况。

## 一般原则 {#principles}

并非每个缺陷都是漏洞。

对于几乎任何缺陷，都能构造出一个假想场景，使其导致安全漏洞。

例如，假设某个图像解码器会错误地解码一些输入。再设想一个系统，接收纸质支票的照片，并按支票内容执行银行转账。如果系统通过网关验证请求、由后端实际转账，而网关与后端的图像解码器存在解析差异，就可能导致网关放行恶意操作，并将其交给后端执行。

仅凭这种场景就将图像解析错误归类为漏洞，并没有实际价值。警告用户受到这类“漏洞”影响，只会增加噪声，因为实际受到影响的用户极少，甚至根本不存在。这样做反而有损安全，会让用户逐渐认为报告大多没有意义而选择忽略。

这个例子也说明了我们为什么不为安全问题分配严重程度标签：对于假想的支票处理系统，这可能是高严重程度问题；但对大多数用户而言，它完全不是问题。

一般原则是：仅仅能够构造出一个让缺陷引发安全问题的假想场景，不足以让我们将该缺陷本身按安全问题处理。

## 漏洞 {#vulns}

### 远程代码执行 {#rce}

如果攻击者能在本不应执行代码的场景中执行代码，就属于 PRIVATE 通道漏洞。这一判定优先于其他所有判定。

本条不适用于本来就应执行代码的函数。

属于范围内的情形：

- 解析函数在处理恶意输入时执行代码。
- 恶意请求导致 HTTP 服务器执行代码。

不属于范围内的情形：

- `go test` 命令会运行测试。对攻击者控制的测试执行 `go test`，不属于我们的威胁模型。

### panic {#panics}

处理攻击者控制的输入时触发 panic，可能构成漏洞。

对于预期会处理攻击者请求的服务器，例如 `net/http` 服务器，其中的 panic 通常属于 PRIVATE 通道漏洞。

客户端中的 panic，例如 `net/http` 客户端中的 panic，通常属于 PUBLIC 通道漏洞。

`archive/zip`、`image/png` 等有理由预期会处理恶意输入的包中，解析函数触发的 panic 通常属于 PUBLIC 通道漏洞。

输入由于自身正常大小而触发 panic，例如非常大的图像，通常不被归类为漏洞。

对于没有明确设计为解析潜在恶意数据的函数，传入无效输入不属于我们的威胁模型，通常也不在安全缺陷处理范围内。例如，图像*解析器*应当防御无效输入；但图像*编码器*中的 panic 虽然可能是缺陷，却不会按漏洞处理。

已弃用函数中的 panic 不属于漏洞，详见下文[已弃用 API](#deprecated)的判定。

### 过度消耗资源 {#quadratic}

我们通常将过度消耗 CPU 或内存的问题与 panic 等同处理，例如运行时间相对于输入规模达到 O(n²) 的函数。

### 构建恶意代码 {#malicious-build}

即使运行攻击者控制的程序并不安全，构建该程序也应当是安全的。例如，我们希望能够安全地构建不可信代码，再将其放入沙箱运行。强烈建议将这一保证视为纵深防御措施，构建不可信代码时仍在低权限沙箱环境中进行。

数据外泄不在我们的威胁模型内。构建攻击者控制的程序时，输出可能包含任意本地文件的内容。

*执行*恶意代码也不在我们的威胁模型内。运行恶意程序，显然就允许它实施恶意行为。

属于漏洞、通常归入 PRIVATE 通道的情形：

- 恶意模块导致“go build”执行任意代码。

不按安全问题处理的情形：

- “go build”的错误输出包含任意本地文件中的文本。
- 编译后的可执行文件包含任意本地文件的内容。
- 恶意程序破坏运行时状态并执行任意代码。
- 编译器缺陷使恶意代码得以被混淆隐藏。

## 不属于漏洞的情形 {#non-vuln}

### 攻击者控制运行环境 {#attacker-control}

如果攻击依赖于攻击者控制程序的运行环境，则不属于漏洞。

包括但不限于：攻击者能够将程序加入 `$PATH`，或设置任意环境变量。

### 已弃用 API {#deprecated}

相比仍受支持的 API，已弃用 API 中的缺陷需要达到更高门槛，才会被视为安全问题。

特别是，已弃用 API 中的 panic 或过度资源消耗，绝不会按漏洞处理。需要安全加固的用户应使用仍受支持的 API。

### image、x/image：大尺寸图像 {#large-image}

解析大尺寸图像可能分配大量内存。例如，原文称一张 65536×65536 的 32 位彩色图像在未压缩时需要 16 MiB 存储空间。**译注：此处原文单位有误，按像素数量计算应为 16 GiB。**

许多图像压缩格式可以将尺寸很大、内容简单的图像压缩成很小的文件。解码这个小文件时，仍可能分配大量内存。

解析不可信图像的用户应先使用 [image.DecodeConfig](https://pkg.go.dev/image#DecodeConfig) 等函数检查图像尺寸，再进行完整解析。

图像解析函数解码压缩率很高的大图像，并不被我们视为漏洞。

### net/http：重定向 {#http-redirect}

`net/http` 包的 HTTP 客户端会处理重定向，其中包含一些与安全相关的行为。例如，跟随重定向时，如果目标域名既不与初始请求域名完全相同，也不是其子域名，就会移除“Authorization”请求头。

移除请求头是一项纵深防御措施，用于避免配置错误或遭入侵的服务器意外将包含敏感请求头的客户端请求转发到不可信目标。仅仅未在重定向时移除请求头，本身并不能让攻击者获得请求头中的凭据；但它可能与其他漏洞结合，例如服务器的开放重定向漏洞，从而造成凭据泄露。

修改 HTTP 客户端行为，很容易破坏依赖现有行为的用户程序。例如，客户端当前的同源策略允许子域名：从 example.com 重定向到 www.example.com 时会保留请求头，但 WHATWG Fetch 标准并不允许。让客户端与标准一致可能有价值，但如果在安全版本中进行此类修改，给现有用户带来问题的可能性，比解决真实漏洞的可能性更高。

由于重定向过滤属于纵深防御措施，而修改行为又存在风险，我们将 HTTP 客户端重定向的所有方面排除在安全缺陷处理流程之外。
