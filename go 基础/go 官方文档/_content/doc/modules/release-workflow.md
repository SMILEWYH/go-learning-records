为其他开发者编写模块时，可以遵循一套工作流程，为使用者提供可靠、一致的体验。本文介绍该流程的主要步骤。

模块开发概览，参见[开发与发布模块](developing)。

**另请参阅**

* 如果只想在代码中使用外部包，请阅读[管理依赖](/doc/modules/managing-dependencies)。
* 每次发布新版本时，你都通过版本号说明模块的变更。详情参见[模块版本号](/doc/modules/version-numbers)。

## 常见流程步骤 {#common-steps}

以下以新模块为例，说明发布与版本管理的流程。各步骤的详细说明见本文后续章节。

1. **创建模块**，组织源码，使其便于其他开发者使用，也便于自己维护。

    如果你刚开始开发模块，请阅读[教程：创建 Go 模块](/doc/tutorial/create-module)。

    在 Go 的去中心化模块发布体系中，代码的组织方式很重要。详情参见[管理模块源码](/doc/modules/managing-source)。

1. 做好准备，**编写本地客户端代码**，调用尚未发布的模块中的函数。

    发布前，模块无法通过 `go get` 等常规依赖管理命令获取。此时可以将模块放在调用方代码附近的本地目录中，进行测试。

    本地开发的更多说明，参见[使用尚未发布的模块进行开发](#unpublished)。

1. 当模块代码已可以供其他开发者试用时，**开始发布 v0 预发布版本**，例如 alpha 和 beta。详情参见[发布预发布版本](#pre-release)。

1. **发布 v0 版本**：它不保证稳定性，但可供用户试用。详情参见[发布首个不稳定版本](#first-unstable)。

1. 发布 v0 版本后，可以而且应该持续**发布新版本**。

    新版本可能包含缺陷修复（补丁版本）、公共 API 扩展（次版本），甚至破坏性变更。由于 v0 不承诺稳定性和向后兼容性，因此允许在这些版本中引入破坏性变更。

    详情参见[发布缺陷修复](#bug-fixes)和[发布兼容的 API 变更](#non-breaking)。

1. 准备发布稳定版本时，先**发布 alpha 和 beta 等预发布版本**。详情参见[发布预发布版本](#pre-release)。

1. 发布 v1，作为**首个稳定版本**。

    这是第一次对模块稳定性作出承诺的版本。详情参见[发布首个稳定版本](#first-stable)。

1. 在 v1 主版本内，**持续修复缺陷**，并在需要时扩展公共 API。

    详情参见[发布缺陷修复](#bug-fixes)和[发布兼容的 API 变更](#non-breaking)。

1. 实在无法避免破坏性变更时，通过**新的主版本**发布。

    主版本更新，例如从 v1.x.x 升级到 v2.x.x，可能给模块使用者带来大量调整工作，应作为最后手段。详情参见[发布不兼容的 API 变更](#breaking)。

## 使用尚未发布的模块进行开发 {#unpublished}

开始开发模块或模块的新版本时，它还没有发布。在发布之前，无法通过常规 Go 命令将它作为已发布的依赖添加。因此，最初在另一个模块中编写调用方代码时，需要引用本地文件系统中的模块副本。

可以在调用方模块的 go.mod 文件中使用 `replace` 指令，引用本地模块。详情参见[依赖本地目录中的模块代码](managing-dependencies#local_directory)。

## 发布预发布版本 {#pre-release}

你可以发布预发布版本，供其他人试用模块并提供反馈。预发布版本不承诺稳定性。

预发布版本号末尾带有预发布标识。版本号的说明，参见[模块版本号](/doc/modules/version-numbers)。

下面是两个示例：

```
v0.2.1-beta.1
v1.2.3-alpha
```

发布预发布版本时，请记住：使用者必须在 `go get` 命令中显式指定它的版本号。因为 `go` 命令默认优先选择正式版本，而不是预发布版本。因此需要像下面这样明确指定：

```
go get example.com/theirmodule@v1.2.3-alpha
```

在仓库中为模块代码打标签，并在标签中指定预发布标识，即可发布预发布版本。详情参见[发布模块](publishing)。

## 发布首个不稳定版本 {#first-unstable}

与预发布版本类似，你也可以发布不保证稳定性或向后兼容性的正式版本，让用户试用模块并提供反馈。

不稳定版本的版本号位于 v0.x.x 范围内。v0 不承诺稳定性或向后兼容性，但让你能够在 v1 及后续版本作出稳定性承诺之前收集反馈、完善 API。详情参见[模块版本号](version-numbers)。

与其他已发布版本一样，在迈向稳定的 v1 版本时，可以随着变更递增 v0 的次版本号和补丁版本号。例如，发布 v0.0.0 之后，可以发布 v0.0.1，包含第一批缺陷修复。

版本号示例：

```
v0.1.3
```

在仓库中为模块代码打标签，并在标签中指定 v0 版本号，即可发布不稳定版本。详情参见[发布模块](publishing)。

## 发布首个稳定版本 {#first-stable}

首个稳定版本使用 v1.x.x 版本号。它通常经过预发布版本和 v0 版本阶段，在此期间收集反馈、修复缺陷，使模块趋于稳定。

发布 v1 意味着你向模块使用者作出以下承诺：

* 使用者可以升级到该主版本后续的次版本和补丁版本，而不会破坏自己的代码。
* 不会对公共 API（包括函数和方法签名）作出破坏向后兼容性的修改。
* 不会移除任何已导出的类型，因为这会破坏向后兼容性。
* 将来的 API 变更（例如为结构体增加字段）会保持向后兼容，并包含在新的次版本中。
* 缺陷修复（例如安全修复）会通过补丁版本或次版本发布。

**注意：** 虽然最初的主版本号可能是 v0，但 v0 不表示稳定性或向后兼容性保证。因此，从 v0 升级到 v1 时，无需遵守对 v0 的向后兼容承诺，因为 v0 本来就不被视为稳定版本。

版本号的更多说明，参见[模块版本号](/doc/modules/version-numbers)。

稳定版本号示例：

```
v1.0.0
```

在仓库中为模块代码打标签，并指定 v1 版本号，即可发布首个稳定版本。详情参见[发布模块](publishing)。

## 发布缺陷修复 {#bug-fixes}

你可以发布仅包含缺陷修复的版本，这称为补丁版本。

*补丁版本*只包含小范围修改，尤其不会更改模块的公共 API。调用方可以安全升级，无需修改自身代码。

**注意：** 发布补丁版本时，模块自身的传递依赖也应尽量只升级补丁版本。否则，用户升级你的模块补丁版本时，可能意外引入某个传递依赖中影响更大的变更。

补丁版本递增模块版本号中的补丁部分。详情参见[模块版本号](/doc/modules/version-numbers)。

以下示例中，v1.0.1 是补丁版本。

旧版本：`v1.0.0`

新版本：`v1.0.1`

在仓库中为模块代码打标签，并递增标签中的补丁版本号，即可发布补丁版本。详情参见[发布模块](publishing)。

## 发布兼容的 API 变更 {#non-breaking}

对模块公共 API 作出不破坏兼容性的变更时，可以通过*次版本*发布。

这种版本会改变 API，但不会破坏调用方代码。变更可能包括调整模块自身的依赖，或增加函数、方法、结构体字段、类型。即使包含这些变更，仍保证现有调用代码的向后兼容性和稳定性。

次版本递增模块版本号中的次版本部分。详情参见[模块版本号](/doc/modules/version-numbers)。

以下示例中，v1.1.0 是次版本。

旧版本：`v1.0.1`

新版本：`v1.1.0`

在仓库中为模块代码打标签，并递增标签中的次版本号，即可发布次版本。详情参见[发布模块](publishing)。

## 发布不兼容的 API 变更 {#breaking}

你可以通过发布新的*主版本*来发布破坏向后兼容性的变更。

新主版本不保证与之前的主版本向后兼容，通常是因为它修改了公共 API，会破坏使用旧版本的代码。

考虑到主版本升级给依赖方代码带来的影响，应尽可能避免。关于主版本更新，参见[开发主版本更新](/doc/modules/major-version)。避免破坏性变更的策略，参见博客文章[保持模块兼容性](/blog/module-compatibility)。

发布其他类型的版本，主要是为模块代码打上版本标签；发布主版本更新则需要更多步骤。

1. 开始开发新主版本前，在仓库中为新版本源码安排位置。

    一种方法是创建新分支，专门用于新主版本及其后续的次版本和补丁版本。详情参见[管理模块源码](/doc/modules/managing-source)。

1. 修改模块的 go.mod 文件，在模块路径后追加新的主版本号，例如：

    ```
    example.com/mymodule/v2
    ```

    模块路径是模块的标识，因此这一修改实际上创建了一个新模块，同时改变了包路径。这能防止开发者无意中导入会破坏自身代码的版本；想要升级的开发者需要显式将旧路径替换为新路径。

1. 更新代码中所有导入被升级模块内包的路径，包括该模块自身内部的导入。因为模块路径已经发生变化，这一步不可省略。

1. 与其他新版本一样，应先发布预发布版本，收集反馈和缺陷报告，再发布正式版本。

1. 在仓库中为模块代码打标签，递增标签中的主版本号，例如从 v1.5.2 升级到 v2.0.0，发布新主版本。

    详情参见[发布模块](/doc/modules/publishing)。
