## 起源 {#Origins}

### 这个项目的目标是什么？ {#What_is_the_purpose_of_the_project}

Go 在 2007 年萌芽时，编程世界与今天很不一样。生产软件通常使用 C++ 或 Java 编写，GitHub 尚未出现，大多数计算机还没有多个处理器。除了 Visual Studio 和 Eclipse，几乎没有其他 IDE 或高级工具，更不用说能在互联网上免费获取了。

与此同时，使用当时的语言及其构建系统开发大型软件项目，需要应付过多的复杂性，让我们倍感挫折。自 C、C++ 和 Java 等语言诞生以来，计算机已经快了很多，但编程本身的进步远没有那么大。此外，多处理器日益普及已是明显趋势，可是大多数语言对如何高效、安全地利用它们帮助甚少。

我们决定退后一步思考：随着技术发展，未来几年软件工程最重要的问题会是什么？一门新语言又能如何帮助解决这些问题？例如，多核 CPU 的兴起意味着语言应该将某种并发或并行机制作为一等特性支持。要让大型并发程序的资源管理变得可控，还需要垃圾回收，或者至少某种安全的自动内存管理机制。

这些思考促成了[一系列讨论](https://commandcenter.blogspot.com/2017/09/go-ten-years-and-climbing.html)，Go 由此诞生：最初是一组想法和目标，后来发展成一门语言。贯穿始终的目标是，让 Go 更好地帮助实际从事开发的程序员：支持工具建设，自动完成代码格式化等日常任务，减少维护大型代码库时遇到的障碍。

关于 Go 的目标，以及这些目标如何实现或逐步接近，更完整的说明见文章 [Go 在 Google：为软件工程服务的语言设计](/talks/2012/splash.article)。

### 项目的历史是怎样的？ {#history}

2007 年 9 月 21 日，Robert Griesemer、Rob Pike 和 Ken Thompson 开始在白板上勾勒新语言的目标。几天后，目标逐渐形成了行动计划，也对这门语言有了较清晰的构想。此后，设计工作在其他不相关的工作之外继续进行。到 2008 年 1 月，Ken 开始编写一个输出 C 代码的编译器，用于探索这些想法。到年中，这门语言成为全职项目，设计也稳定到足以尝试编写生产级编译器。2008 年 5 月，Ian Taylor 根据规范草案，独立开始开发 Go 的 GCC 前端。Russ Cox 于 2008 年底加入，帮助语言及其库从原型走向实用。

2009 年 11 月 10 日，Go 正式成为公开的开源项目。无数社区成员为它贡献了想法、讨论和代码。

如今，世界各地有数百万 Go 程序员，也就是 gopher，而且人数每天都在增长。Go 取得的成功远远超出了我们的预期。

### gopher 吉祥物从何而来？ {#gopher}

吉祥物和标志由 [Renée French](https://reneefrench.blogspot.com) 设计。她也设计了 Plan 9 的兔子吉祥物 [Glenda](https://9p.io/plan9/glenda.html)。一篇介绍 gopher 的[博客文章](/blog/gopher)说明了它如何由她多年前为 [WFMU](https://wfmu.org/) T 恤设计的形象演变而来。标志和吉祥物采用 [Creative Commons Attribution 4.0（知识共享署名 4.0）](https://creativecommons.org/licenses/by/4.0/)许可证。

gopher 有一份[角色设定图](/doc/gopher/modelsheet.jpg)，展示其特征以及正确的绘制方式。Renée 于 2016 年在 Gophercon 的一次[演讲](https://www.youtube.com/watch?v=4rw_B4yY69k)中首次展示了这份设定图。它有独特的特征，是 *Go gopher*，并不是随便一只地鼠。

### 这门语言叫 Go 还是 Golang？ {#go_or_golang}

这门语言叫 Go。“golang”这一别称源于最初的网站域名 *golang.org*（当时还没有 *.dev* 域名）。不过，很多人也使用 golang 这个名称，因为它很适合作为标签。例如，这门语言在社交媒体上的标签是“#golang”。无论如何，语言本身的名字就是 Go。

顺便说明：虽然[官方标志](/blog/go-brand)中的两个字母都是大写，但语言名称应写作 Go，而不是 GO。

### 为什么要创建一门新语言？ {#creating_a_new_language}

Go 的诞生源于我们在 Google 工作时，对现有语言和开发环境的不满。编程变得过于困难，而语言选择是部分原因。高效编译、高效执行和易于编程，这三者无法在同一门主流语言中兼得。有条件的程序员开始选择更容易编程的 Python、JavaScript 等动态类型语言，而不再使用 C++，有些也不再使用 Java，为此牺牲了部分安全性和效率。

这种担忧并非我们独有。编程语言领域沉寂多年后，Go 成为了新一批语言中的先行者之一。随后出现的 Rust、Elixir、Swift 等语言，让编程语言开发重新成为活跃、甚至接近主流的领域。

Go 尝试将解释型、动态类型语言的易用性，与静态类型、编译型语言的效率和安全性结合起来，以解决这些问题。它还希望通过支持网络与多核计算，更好地适应现代硬件。最后，使用 Go 进行开发应当足够*快*：在单台计算机上构建大型可执行文件，最多只应花费几秒。为了达到这些目标，我们重新思考了现有语言中的一些编程方式，于是采用了基于组合而非层级继承的类型系统，支持并发与垃圾回收，严格规定依赖关系，等等。这些问题仅靠库或工具无法很好地解决，因此需要一门新语言。

[Go 在 Google](/talks/2012/splash.article)一文讨论了 Go 语言设计的背景和动机，也更详细地解释了本 FAQ 中的许多问题。

### Go 受到哪些语言的影响？ {#ancestors}

Go 的基本语法主要属于 C 语言家族，同时受到 Pascal、Modula、Oberon 家族在声明和包方面的重要影响，也吸收了 Newsqueak、Limbo 等受 Tony Hoare 的 CSP 启发的语言在并发方面的一些思想。不过，从整体上看，它是一门全新的语言。设计语言的每个方面时，我们都会思考程序员实际在做什么，以及如何让编程——至少是我们所从事的那类编程——更有效率，也就更有乐趣。

### 语言设计遵循哪些原则？ {#principles}

Go 开始设计时，Java 和 C++ 是编写服务器最常用的语言，至少 Google 内部如此。我们认为，这些语言要求开发者维护太多琐碎细节，编写太多重复内容。一些程序员因此转向 Python 等更动态、流畅的语言，却付出了效率和类型安全方面的代价。我们认为，同一门语言应该能够兼顾效率、安全性和流畅的开发体验。

Go 希望同时减少“typing”的两层负担：键盘输入和类型声明。在整个设计过程中，我们始终尝试减少杂乱与复杂性。没有前向声明，也没有头文件；每个内容只声明一次。初始化表达力强、自动化程度高且易于使用。语法简洁，关键字不多。通过 `:=` 声明并初始化变量的形式，利用简单的类型推导减少 `foo.Foo* myFoo = new(foo.Foo)` 这样的重复内容。也许最根本的改变是取消类型层级：类型只需*存在*，无需显式声明彼此的关系。这些简化让 Go 在不牺牲开发效率的前提下，兼具表达力和可理解性。

另一个重要原则是保持概念正交：方法可以为不同类型定义，结构体表示数据，接口表示抽象，等等。正交性使各种概念组合时的行为更容易理解。

## 使用 {#Usage}

### Google 内部使用 Go 吗？ {#internal_usage}

是的。Go 广泛用于 Google 内部的生产环境。例如，Google 的下载服务器 `dl.google.com` 使用 Go，负责分发 Chrome 二进制文件及其他大型安装包，如 `apt-get` 软件包。

Go 远不是 Google 唯一使用的语言，但它是[站点可靠性工程（SRE）](/talks/2013/go-sreops.slide)、大规模数据处理等多个领域的重要语言，也是运行 Google Cloud 的软件的重要组成部分。

### 还有哪些公司使用 Go？ {#external_usage}

Go 的使用范围在全球不断扩大，云计算领域尤其明显，但绝不限于这一领域。Docker 和 Kubernetes 是两个使用 Go 编写的重要云基础设施项目，此外还有很多。

从 [go.dev 网站](/)上的公司列表和[成功案例](/solutions/case-studies)可以看出，Go 的应用远不止云计算。Go Wiki 还有一个定期更新的[页面](/wiki/GoUsers)，列出了众多使用 Go 的公司中的一部分。

Wiki 还提供了一个包含更多[成功案例](/wiki/SuccessStories)链接的页面，介绍使用这门语言的公司和项目。

### Go 程序可以与 C/C++ 程序链接吗？ {#Do_Go_programs_link_with_Cpp_programs}

可以在同一地址空间中同时使用 C 和 Go，但两者并非天然契合，可能需要专门的接口层。此外，将 C 代码与 Go 代码链接，会失去 Go 所提供的部分内存安全和栈管理保障。有时确实必须使用 C 库解决问题，但这样总会引入纯 Go 代码没有的风险，因此需要谨慎。

如果确实需要同时使用 C 和 Go，具体方法取决于 Go 编译器的实现。由 Google 的 Go 团队支持、属于 Go 工具链的“标准”编译器叫作 `gc`。此外，还有基于 GCC 的编译器 `gccgo`、基于 LLVM 的编译器 `gollvm`，以及不断增加的、面向特定用途的其他编译器；其中一些只实现语言的子集，例如 [TinyGo](https://tinygo.org/)。

`Gc` 的调用约定和链接器与 C 不同，因此不能直接从 C 程序调用，反过来也一样。[`cgo`](/cmd/cgo/) 程序提供“外部函数接口”机制，使 Go 代码能够安全地调用 C 库。SWIG 将这种能力扩展到了 C++ 库。

`gccgo` 和 `gollvm` 也可以使用 `cgo` 和 SWIG。由于它们采用传统 ABI，在充分谨慎的前提下，也可以将这些编译器生成的代码直接与 GCC/LLVM 编译的 C 或 C++ 程序链接。不过，要安全地这样做，必须了解所有相关语言的调用约定，并注意从 Go 调用 C 或 C++ 时的栈限制。

### Go 支持哪些 IDE？ {#ide}

Go 项目没有附带专用 IDE，但语言和库的设计让源代码分析比较容易。因此，大多数知名编辑器和 IDE 都直接支持 Go，或者可以通过插件提供良好支持。

Go 团队还维护一个支持 LSP 协议的 Go 语言服务器，名为 [`gopls`](https://pkg.go.dev/golang.org/x/tools/gopls#section-readme)。支持 LSP 的工具可以使用 `gopls` 集成 Go 语言功能。

对 Go 提供良好支持的知名 IDE 和编辑器包括 Emacs、Vim、VSCode、Atom、Eclipse、Sublime、IntelliJ 的专用产品 GoLand，以及许多其他工具。你喜欢的开发环境很可能也适合高效编写 Go 程序。

### Go 支持 Google 的 Protocol Buffers 吗？ {#protocol_buffers}

一个独立的开源项目提供了所需的编译器插件和库，地址是 [github.com/golang/protobuf/](https://github.com/golang/protobuf)。

## 设计 {#Design}

### Go 有运行时吗？ {#runtime}

Go 有一个功能丰富的运行时库，通常简称为*运行时（runtime）*，它是每个 Go 程序的一部分。这个库实现了垃圾回收、并发、栈管理，以及 Go 语言的其他关键功能。虽然 Go 的运行时与语言的联系更紧密，但它的角色可以类比 C 语言的 `libc`。

不过，Go 的运行时并不包含 Java 运行时那样的虚拟机。Go 程序会预先编译为本地机器码，某些变体实现也会生成 JavaScript 或 WebAssembly。因此，虽然“运行时”经常用来描述程序运行的虚拟环境，但在 Go 中，它只是提供关键语言服务的库的名称。

### 为什么 Unicode 标识符是现在这样设计的？ {#unicode_identifiers}

设计 Go 时，我们希望它不会过于以 ASCII 为中心，因此需要将标识符的范围扩展到 7 位 ASCII 之外。Go 的规则是：标识符中的字符必须是 Unicode 定义的字母或数字。这个规则容易理解和实现，但也有局限。例如，设计上排除了组合字符，因此无法支持天城文等某些文字。

这个规则还有一个不理想的结果：导出标识符必须以大写字母开头，因此某些文字中的字符天然无法构成导出名称。目前只能使用 `X日本語` 这样的形式，显然不够理想。

从语言最早的版本开始，我们就一直认真考虑如何更好地扩展标识符范围，方便使用其他母语的程序员。具体方案仍在积极讨论，未来版本可能对标识符给出更宽松的定义。例如，可以采纳 Unicode 组织关于标识符的[建议](http://unicode.org/reports/tr31/)中的部分想法。不论最终怎样修改，都必须保持兼容，并保留或扩展通过字母大小写决定标识符可见性的方式；这仍是我们最喜欢的 Go 特性之一。

目前采用的是一个简单、今后可以在不破坏现有程序的前提下扩展的规则，同时避免因允许有歧义的标识符而产生的缺陷。

### 为什么 Go 没有特性 X？ {#Why_doesnt_Go_have_feature_X}

每门语言都有自己的新特性，也都会缺少某些人喜欢的特性。Go 的设计考虑了编程体验、编译速度、概念正交性，以及支持并发和垃圾回收等功能的需要。某个你喜欢的特性没有被纳入，可能是因为它不适合 Go，会影响编译速度或设计的清晰性，或者会让基本系统模型过于复杂。

如果 Go 缺少特性 *X* 让你感到困扰，请多包涵，也不妨研究一下 Go 已有的特性。你可能会发现，它们以有趣的方式弥补了 *X* 的缺失。

### Go 是什么时候支持泛型类型的？ {#generics}

Go 1.18 为语言加入了类型形参，从而支持一种形式的多态编程或泛型编程。详细说明请参阅[语言规范](/ref/spec)和[提案](/design/43651-type-parameters)。

### 为什么 Go 最初发布时没有泛型类型？ {#beginning_generics}

Go 最初的目标是编写易于长期维护的服务器程序，更多背景见[这篇文章](/talks/2012/splash.article)。设计重点是可扩展性、可读性和并发等方面。当时，多态编程并不是实现这些目标的必要条件，因此为了保持简单，最初没有加入。

泛型确实方便，但也会增加类型系统和运行时的复杂性。我们花了一段时间，才形成一个我们认为收益与复杂性相称的设计。

### 为什么 Go 没有异常？ {#exceptions}

我们认为，将异常与控制结构耦合起来，例如 `try-catch-finally` 这种用法，会使代码复杂难懂，也容易让程序员把打开文件失败这样的普通错误都当成异常。

Go 采用了不同的方法。对于普通错误处理，Go 的多返回值机制能方便地报告错误，无需让一个返回值同时承担正常结果和错误的多重含义。[统一的错误类型与 Go 其他特性的结合](/doc/articles/error_handling.html)，让错误处理易于使用，但与其他语言很不一样。

Go 还提供了一对内置函数，用于报告真正的异常情况并从中恢复。恢复机制只会在出错后清理函数状态的过程中执行，这足以处理严重故障，无需额外的控制结构；使用得当时，可以得到简洁的错误处理代码。

详细说明请参阅 [Defer、Panic 和 Recover](/doc/articles/defer_panic_recover.html)一文。[错误是值](/blog/errors-are-values)这篇博客还演示了一种简洁的错误处理方式：既然错误只是普通的值，就可以充分利用 Go 的各种能力来处理它们。

### 为什么 Go 没有断言？ {#assertions}

Go 不提供一般意义上的断言语句。断言无疑很方便，但我们的经验是，程序员常常依赖它，回避对正确错误处理和报告方式的思考。正确的错误处理意味着服务器遇到非致命错误时应继续工作，而不是崩溃。正确的错误报告意味着错误信息直截了当、切中问题，让程序员不必解读冗长的崩溃堆栈。尤其当看到错误的程序员不熟悉相关代码时，准确的错误信息更为重要。

我们知道这一点存在争议。Go 语言和库中有许多与当代常见做法不同的设计，只是因为我们认为，有时值得尝试另一种方法。

### 为什么并发机制基于 CSP 思想？ {#csp}

并发和多线程编程长期以来都以困难著称。我们认为，部分原因是 [pthreads](https://en.wikipedia.org/wiki/POSIX_Threads) 等设计比较复杂，另一部分原因是过于强调互斥锁、条件变量、内存屏障等底层细节。更高层的接口能够让代码简单得多，即使其内部仍然使用互斥锁等机制。

在语言层面为并发提供高层支持的最成功模型之一，是 Hoare 提出的通信顺序进程，即 CSP（Communicating Sequential Processes）。Occam 和 Erlang 是两个源自 CSP 的著名语言。Go 的并发原语来自这一家族的另一个分支，其主要贡献是将通道作为一等对象这一强大理念。早期几门语言的实践表明，CSP 模型与过程式语言的框架能很好地结合。

### 为什么使用 goroutine，而不是线程？ {#goroutines}

goroutine（轻量级协程）是让并发易于使用的重要组成部分。它采用了一个存在已久的思想：将独立执行的函数，也就是协程，复用到一组线程上。某个协程阻塞时，例如调用了阻塞的系统调用，运行时会自动将同一个操作系统线程上的其他协程移到另一个可运行的线程上，避免它们一起阻塞。程序员无需感知这个过程，这正是设计目的。我们将这种机制称为 goroutine。它的成本可以很低：除了仅占几 KB 的栈内存，几乎没有其他开销。

为了让栈保持较小，Go 运行时使用可调整大小、具有上限的栈。新创建的 goroutine 只分配几 KB 的栈空间，通常已经够用。如果不够，运行时会自动扩展栈内存，并在适当时缩小，使得有限的内存也能容纳大量 goroutine。CPU 开销平均约为每次函数调用三条低成本指令。在同一地址空间中创建数十万个 goroutine 是可行的。如果 goroutine 就是普通线程，系统资源会在数量小得多时耗尽。

### 为什么 map 操作没有被定义为原子操作？ {#atomic_maps}

经过长时间讨论，我们认为，映射（map）的典型用法不需要多个 goroutine 安全地同时访问；确实需要时，map 往往已经是某个更大数据结构或计算过程的一部分，而这些结构或过程本身已有同步机制。因此，如果要求每次 map 操作都获取互斥锁，就会拖慢大多数程序，却只为少数程序增加安全保障。不过，这个决定并不容易，因为它意味着未经控制的 map 并发访问可能使程序崩溃。

语言并不禁止实现原子性的 map 更新。有需要时，例如托管不可信程序的环境，实现可以对 map 访问进行互锁保护。

只有发生更新时，map 的并发访问才是不安全的。只要所有 goroutine 都仅进行读取，包括查找元素和使用 `for` `range` 循环遍历，而不对元素赋值或执行删除，就可以不使用同步措施而安全地并发访问 map。

为帮助正确使用 map，某些语言实现包含专门检查，会在运行时自动报告不安全的并发修改。sync 库还提供了 [`sync.Map`](https://pkg.go.dev/sync#Map) 类型，适用于静态缓存等特定使用模式，但不适合作为内置 map 类型的通用替代品。

### 你们会接受我提出的语言修改吗？ {#language_changes}

人们经常提出语言改进建议，[邮件列表](https://groups.google.com/group/golang-nuts)中保存了大量此类讨论，不过最终被接受的修改很少。

虽然 Go 是开源项目，但语言和库受到[兼容性承诺](/doc/go1compat.html)保护，至少在源代码层面，不允许破坏现有程序的修改；程序有时可能需要重新编译，以适应更新。如果提案违反 Go 1 规范，无论它多么优秀，我们都无法考虑。未来的某个 Go 主版本可能与 Go 1 不兼容，但相关讨论才刚开始，有一点可以确定：这个过程中引入的不兼容之处会非常少。此外，兼容性承诺也促使我们在这种情况出现时，为旧程序提供自动迁移的途径。

即使提案与 Go 1 规范兼容，也可能不符合 Go 的设计目标。*[Go 在 Google：为软件工程服务的语言设计](/talks/2012/splash.article)*解释了 Go 的起源及其设计动机。

## 类型 {#types}

### Go 是面向对象语言吗？ {#Is_Go_an_object-oriented_language}

既是，也不是。Go 有类型和方法，允许采用面向对象的编程风格，但没有类型层级。Go 的“接口”概念提供了另一种方式，我们认为它易于使用，在某些方面也更通用。还可以将类型嵌入其他类型，提供类似于子类化、但并不完全相同的能力。此外，Go 的方法比 C++ 或 Java 更通用：可以为各种数据形式定义方法，甚至包括以普通、无需“装箱”的整数等内置类型为底层类型的命名类型，而不局限于结构体或类。

没有类型层级，也使 Go 中的“对象”比 C++ 或 Java 等语言中的对象显得轻量得多。

### 如何实现方法的动态分派？ {#How_do_I_get_dynamic_dispatch_of_methods}

只能通过接口实现方法的动态分派。结构体或其他具体类型上的方法调用始终是静态解析的。

### 为什么没有类型继承？ {#inheritance}

面向对象编程，至少在最知名的那些语言中，需要讨论太多类型之间的关系，而这些关系往往可以自动推导出来。Go 采用了另一种方式。

Go 不要求程序员预先声明两个类型有关联。只要一个类型的方法包含某接口要求的方法，它就自动满足这个接口。这不仅减少了需要维护的信息，还带来了实际好处：类型可以同时满足多个接口，而不会引入传统多重继承的复杂性；接口可以非常轻量，一个方法甚至零个方法的接口都能表达有用的概念；当出现新想法或测试需求时，可以事后添加接口，而无需修改原有类型。类型与接口之间没有显式声明的关系，也就没有需要管理或讨论的类型层级。

利用这些思想，可以构造类似类型安全 Unix 管道的机制。例如，`fmt.Fprintf` 可以向任意输出目标进行格式化输出，而不局限于文件；`bufio` 包可以完全独立于文件 I/O；`image` 相关包可以生成压缩图像文件。这些能力都源于一个只包含单个方法 `Write` 的接口 `io.Writer`。这还只是最表面的例子。Go 的接口对程序结构有着深远影响。

这种隐式的类型依赖方式需要一些时间适应，但它也是 Go 最能提升开发效率的设计之一。

### 为什么 `len` 是函数，而不是方法？ {#methods_on_basics}

我们讨论过这个问题，最终认为，将 `len` 及类似操作实现为函数，在实践中效果很好，也不会使基本类型的接口（这里指 Go 类型意义上的接口）问题复杂化。

### 为什么 Go 不支持方法和运算符重载？ {#overloading}

如果方法分派不需要同时进行类型匹配，就能更简单。其他语言的经验表明，名称相同而签名不同的多个方法偶尔很有用，但实际使用中也容易造成混淆，使代码脆弱。只按名称匹配，并要求类型一致，是 Go 类型系统中一个重要的简化决策。

至于运算符重载，它更像是便利功能，而非绝对必要的能力。同样，不提供它会让事情更简单。

### 为什么 Go 没有“implements”声明？ {#implements_interface}

Go 类型只需实现接口要求的方法，就实现了该接口，无需其他声明。这使得接口可以在不修改现有代码的情况下定义和使用。这是一种[结构化类型机制](https://en.wikipedia.org/wiki/Structural_type_system)，有助于分离关注点、提升代码复用，也便于利用代码演进过程中逐渐形成的模式。接口的这种语义，是 Go 显得灵活轻量的主要原因之一。

更多说明请参阅[关于类型继承的问题](#inheritance)。

### 如何确保我的类型满足某个接口？ {#guarantee_satisfies_interface}

可以根据需要，使用类型 `T` 或 `*T` 的零值进行赋值，让编译器检查它是否实现接口 `I`：

```
type T struct{}
var _ I = T{}       // Verify that T implements I.
var _ I = (*T)(nil) // Verify that *T implements I.
```

如果 `T`（或对应的 `*T`）没有实现 `I`，编译器就会发现这个错误。

如果希望接口的使用者明确声明自己实现了该接口，可以在接口的方法集中添加一个名称具有说明性的标记方法。例如：

```
type Fooer interface {
    Foo()
    ImplementsFooer()
}
```

这样，一个类型要成为 `Fooer`，就必须实现 `ImplementsFooer` 方法。这个事实既会清楚地体现在代码中，也会出现在 [go doc](/cmd/go/#hdr-Show_documentation_for_package_or_symbol) 的输出里。

```
type Bar struct{}
func (b Bar) ImplementsFooer() {}
func (b Bar) Foo() {}
```

大多数代码不使用这种约束，因为它会限制接口这一设计的灵活性。不过，有时需要借此消除相似接口之间的歧义。

### 为什么类型 T 不满足 Equal 接口？ {#t_and_equal_interface}

考虑以下简单接口，它表示一个可以将自身与另一个值进行比较的对象：

```
type Equaler interface {
    Equal(Equaler) bool
}
```

再考虑类型 `T`：

```
type T int
func (t T) Equal(u T) bool { return t == u } // does not satisfy Equaler
```

与某些多态类型系统中的类似情况不同，`T` 没有实现 `Equaler`。`T.Equal` 的参数类型是 `T`，而不是接口要求的 `Equaler`。

Go 的类型系统不会自动提升 `Equal` 的参数类型，这需要程序员处理。下面的 `T2` 就实现了 `Equaler`：

```
type T2 int
func (t T2) Equal(u Equaler) bool { return t == u.(T2) }  // satisfies Equaler
```

不过，这仍然与其他类型系统不同。在 Go 中，*任何*满足 `Equaler` 的类型都能作为实参传给 `T2.Equal`，因此必须在运行时检查实参是否为 `T2`。某些语言会在编译期保证这一点。

另一个相关的例子发生在返回值这一侧：

```
type Opener interface {
   Open() Reader
}

func (t T3) Open() *os.File
```

在 Go 中，`T3` 不满足 `Opener`，尽管在其他语言中可能满足。

Go 的类型系统在这些情况下确实为程序员做得少一些，但没有子类型关系，就能让接口实现规则非常明确：方法名称和签名是否与接口完全相同？这个规则也容易高效实现。我们认为，这些好处足以弥补缺少自动类型提升的不足。

### 可以将 []T 转换为 []interface{} 吗？ {#convert_slice_of_interface}

不能直接转换。语言规范不允许这样做，因为两种类型在内存中的表示不同。必须将元素逐个复制到目标切片中。以下示例将 `int` 切片转换为 `interface{}` 切片：

```
t := []int{1, 2, 3, 4}
s := make([]interface{}, len(t))
for i, v := range t {
    s[i] = v
}
```

### 如果 T1 和 T2 的底层类型相同，可以将 []T1 转换为 []T2 吗？ {#convert_slice_with_same_underlying_type}

下面代码的最后一行无法编译。

```
type T1 int
type T2 int
var t1 T1
var x = T2(t1) // OK
var st1 []T1
var sx = ([]T2)(st1) // NOT OK
```

在 Go 中，类型与方法密切相关：每个命名类型都有一个可能为空的方法集。一般规则是，可以改变正在转换的类型本身的名称，从而可能改变其方法集，但不能以此改变复合类型中元素的类型名称及其方法集。Go 要求显式进行类型转换。

### 为什么我的 nil 错误值不等于 nil？ {#nil_error}

从内部表示来看，接口由两部分构成：类型 `T` 和值 `V`。`V` 是一个具体值，例如 `int`、`struct` 或指针，其类型为 `T`，而不会是另一个接口本身。例如，将 `int` 值 3 存入接口后，可以把得到的接口值表示为（`T=int`、`V=3`）。`V` 也称为接口的*动态值*，因为同一个接口变量在程序执行过程中可能保存不同的 `V`，以及相应的类型 `T`。

只有 `T` 和 `V` 都未设置时，接口值才为 `nil`，即 `T=nil` 且 `V` 未设置。特别地，nil 接口的动态类型一定也是 nil。如果将一个类型为 `*int` 的 `nil` 指针存入接口，那么无论指针的值是什么，动态类型都是 `*int`，即（`T=*int`、`V=nil`）。因此，*即使内部指针值 `V` 为* `nil`，接口值本身仍然不是 `nil`。

这容易引起困惑，例如将一个 nil 值放入接口并作为 `error` 返回时：

```
func returnsError() error {
    var p *MyError = nil
    if bad() {
        p = ErrBad
    }
    return p // Will always return a non-nil error.
}
```

如果一切正常，函数返回的是值为 `nil` 的 `p`，因此返回的 `error` 接口包含（`T=*MyError`、`V=nil`）。这意味着，即使没有发生错误，调用方将返回值与 `nil` 比较时，也总会认为存在错误。要向调用方返回真正的 `nil` 错误，函数必须显式返回 `nil`：

```
func returnsError() error {
    if bad() {
        return ErrBad
    }
    return nil
}
```

返回错误的函数最好始终在签名中使用 `error` 类型，如上例所示，而不是 `*MyError` 这样的具体类型，以帮助确保错误值被正确构造。例如，[`os.Open`](/pkg/os/#Open) 返回 `error`，尽管其非 nil 错误值的具体类型始终是 [`*os.PathError`](/pkg/os/#PathError)。

任何使用接口的地方都可能出现类似情况。只需记住：接口一旦存入任何具体值，它就不再是 `nil`。更多信息请参阅[反射法则](/doc/articles/laws_of_reflection.html)。

### 为什么零大小类型的行为有些奇怪？ {#zero_size_types}

Go 支持零大小类型，例如没有字段的结构体 `struct{}`，或没有元素的数组 `[0]byte`。这些类型没有可存储的数据，但在不需要数据值时很有用，例如 `map[int]struct{}`，或者只需要方法而不需要存储数据的类型。

零大小类型的不同变量可能放在相同的内存位置。这是安全的，因为这些变量没有可存储的数据。

此外，语言不保证指向两个不同零大小变量的指针比较时是否相等。根据程序具体的编译和执行方式，这种比较甚至可能在程序中的一处返回 `true`，在另一处返回 `false`。

零大小类型还有一个独立问题：指向结构体中零大小字段的指针，不能与内存中另一个对象的指针重叠，否则可能使垃圾回收器产生混淆。因此，如果结构体最后一个字段的大小为零，实现会增加填充，避免指向该字段的指针落在紧随结构体之后的内存上。所以，以下程序：

```
func main() {
	type S struct {
		f1 byte
		f2 struct{}
	}
	fmt.Println(unsafe.Sizeof(S{}))
}
```

在大多数 Go 实现中会输出 `2`，而不是 `1`。

### 为什么没有 C 那样的无标签联合体？ {#unions}

无标签联合体会破坏 Go 的内存安全保证。

### 为什么 Go 没有变体类型？ {#variant_types}

变体类型（variant type），也常称为代数类型，允许规定一个值只能是某一组类型中的一种。系统编程中的常见例子是规定错误只能是网络错误、安全错误或应用程序错误，并允许调用方通过检查错误类型判断问题来源。另一个例子是语法树，其中每个节点可能是声明、语句、赋值等不同类型。

我们考虑过为 Go 添加变体类型，但讨论后决定不加入，因为它与接口的功能重叠可能造成混淆。例如，如果变体类型的成员本身又是接口，会发生什么？

此外，语言已有的能力能够解决变体类型处理的部分问题。错误分类的例子很容易用接口值保存错误，再通过类型选择区分各种情况。语法树的例子也能实现，只是没有那么优雅。

### 为什么 Go 不支持返回类型协变？ {#covariant_types}

如果支持返回类型协变，那么下面这样的接口：

```
type Copyable interface {
    Copy() interface{}
}
```

就可以由以下方法满足：

```
func (v Value) Copy() Value
```

因为 `Value` 实现了空接口。在 Go 中，方法类型必须完全匹配，因此 `Value` 没有实现 `Copyable`。Go 将类型的行为，也就是方法，与类型的实现区分开来。如果两个方法返回不同类型，就不算做完全相同的事。希望使用返回类型协变的程序员，往往是在尝试通过接口表达类型层级。在 Go 中，更自然的方式是清楚地分离接口与实现。

## 值 {#Values}

### 为什么 Go 不提供隐式数值类型转换？ {#conversions}

C 中数值类型之间的自动转换带来的困惑，超过了它的便利：表达式什么时候是无符号的？值能有多大？会不会溢出？结果是否可移植，是否与运行它的机器无关？这也让编译器更加复杂；C 的“通常算术转换”既不容易实现，在不同架构上也不一致。出于可移植性的考虑，我们决定让规则清楚直接，代价是在代码中多写一些显式转换。不过，Go 将常量定义为无需标注符号和位宽的任意精度值，已经大大缓解了这个问题。

还有一个相关细节：与 C 不同，即使 `int` 是 64 位类型，`int` 与 `int64` 仍是不同类型。`int` 是通用整数类型；如果关心整数究竟有多少位，Go 鼓励你明确写出来。

### Go 中的常量如何工作？ {#constants}

虽然 Go 严格限制不同数值类型的变量之间的转换，但对常量灵活得多。`23`、`3.14159` 和 [`math.Pi`](/pkg/math/#pkg-constants) 等常量处于一种理想数值空间中，具有任意精度，不发生上溢或下溢。例如，源代码中的 `math.Pi` 指定了 63 位十进制数字，包含它的常量表达式能够保持超出 `float64` 容量的精度。只有当常量或常量表达式被赋给变量，也就是程序中的某个内存位置时，它才变成具有通常浮点数特性和精度的“计算机数值”。

此外，这些无类型常量只是数值，而非带有固定类型的值，因此比变量使用起来更自由，缓解了严格转换规则带来的不便。例如可以写：

```
sqrt2 := math.Sqrt(2)
```

编译器不会报错，因为理想数值 `2` 可以安全、精确地转换为调用 `math.Sqrt` 所需的 `float64`。

[常量](/blog/constants)这篇博客更详细地讨论了这个主题。

### 为什么 map 是内置类型？ {#builtin_maps}

原因与字符串相同：它是如此重要而强大的数据结构，提供一个优秀的实现并给予语法支持，会使编程更愉快。我们认为，Go 的 map 实现足以满足绝大多数场景。如果某个应用能从自定义实现中受益，也可以自行编写，只是语法上不如内置类型方便；这似乎是一个合理的取舍。

### 为什么 map 不允许切片作为键？ {#map_keys}

map 查找需要相等比较，而切片不支持这种比较。原因是这类类型的“相等”没有清楚统一的定义：需要考虑浅比较与深比较、指针比较与值比较、递归类型如何处理等多个问题。将来我们可能重新考虑这件事，而且为切片实现相等比较不会使现有程序失效。不过，在尚未明确切片相等应该意味着什么之前，暂时不提供这种操作会更简单。

结构体和数组定义了相等比较，因此在其组成部分满足可比较要求时，可以用作 map 的键。

### 为什么 map、切片和通道具有引用语义，而数组具有值语义？ {#references}

这个问题有很长的历史。早期，map 和通道在语法上都是指针，无法声明或使用非指针实例。我们也曾反复思考数组应该如何工作。最终，我们认为严格区分指针和值反而让语言难以使用。让这些类型作为对相关共享数据结构的引用，解决了这些问题。这次修改确实为语言增添了一些令人遗憾的复杂性，但显著改善了易用性：Go 因此变得更高效、更舒适。

## 编写代码 {#Writing_Code}

### 库文档是如何生成和查看的？ {#How_are_libraries_documented}

要从命令行访问文档，可以使用 [go](/pkg/cmd/go/) 工具的 [doc](/pkg/cmd/go/#hdr-Show_documentation_for_package_or_symbol) 子命令，以文本形式查看声明、文件、包等内容的文档。

全局包检索页面 [pkg.go.dev/pkg/](/pkg/) 背后的服务，会从互联网上的 Go 源代码中提取包文档，生成 HTML，并附上声明及相关元素的链接。这是了解现有 Go 库最方便的方式。

项目早期有一个类似程序 `godoc`，也可以提取本机文件中的文档；[pkg.go.dev/pkg/](/pkg/) 基本上是它的后继者。另一个后继者是 [`pkgsite`](https://pkg.go.dev/golang.org/x/pkgsite/cmd/pkgsite) 命令，它与 `godoc` 一样可以在本地运行，不过尚未与 `go` `doc` 的输出整合。

### Go 有编程风格指南吗？ {#Is_there_a_Go_programming_style_guide}

Go 没有一份明确、统一的风格指南，但确实存在一种容易辨认的“Go 风格”。

Go 已经形成了关于命名、排版和文件组织的约定。[高效 Go 编程](effective_go.html)对这些主题给出了一些建议。更直接地说，`gofmt` 程序是一个代码格式化工具，用来统一排版规则，取代通常需要人为解读的各种“应该”和“不应该”的长篇规定。仓库中的全部 Go 代码，以及开源世界中绝大多数 Go 代码，都经过了 `gofmt` 处理。

[Go 代码审查建议](/s/comments)汇集了一组短文，介绍程序员常常忽略的 Go 惯用法细节，是审查 Go 项目代码时很方便的参考资料。

### 如何向 Go 库提交补丁？ {#How_do_I_submit_patches_to_the_Go_libraries}

库的源代码位于仓库的 `src` 目录中。如果计划进行较大修改，请先在邮件列表中讨论，再开始实施。

具体流程请参阅[为 Go 项目贡献代码](contribute.html)。

### 为什么“go get”克隆仓库时使用 HTTPS？ {#git_https}

公司网络通常只允许通过标准 TCP 端口 80（HTTP）和 443（HTTPS）访问外部，阻止其他端口的出站流量，包括 TCP 端口 9418（git）和 22（SSH）。使用 HTTPS 而非 HTTP 时，`git` 默认会验证证书，防范中间人攻击、窃听和篡改。因此，`go get` 出于安全考虑使用 HTTPS。

可以配置 `Git` 通过 HTTPS 进行身份验证，也可以用 SSH 替代 HTTPS。要通过 HTTPS 验证身份，可以在 git 读取的 `$HOME/.netrc` 文件中添加一行：

```
machine github.com login *USERNAME* password *APIKEY*
```

对于 GitHub 账号，密码位置可以使用[个人访问令牌](https://help.github.com/articles/creating-a-personal-access-token-for-the-command-line/)。

也可以配置 `Git`，对匹配指定前缀的 URL 使用 SSH 替代 HTTPS。例如，要让所有 GitHub 访问都使用 SSH，可以在 `~/.gitconfig` 中添加：

```
[url "ssh://git@github.com/"]
	insteadOf = https://github.com/
```

如果项目包含私有模块，同时又通过公共模块代理获取其他依赖，可能需要设置 `GOPRIVATE`。具体说明和其他相关设置请参阅[私有模块](/ref/mod#private-modules)。

### 如何使用“go get”管理包版本？ {#get_version}

Go 工具链内置了一套系统，用于管理带版本的一组相关包，称为*模块（module）*。模块在 [Go 1.11](/doc/go1.11#modules) 中引入，从 [1.14](/doc/go1.14#introduction) 开始已适合生产使用。

要创建使用模块的项目，请运行 [`go mod init`](/ref/mod#go-mod-init)。该命令会创建用于记录依赖版本的 `go.mod` 文件。

```
go mod init example/project
```

要添加、升级或降级依赖，请运行 [`go get`](/ref/mod#go-get)：

```
go get golang.org/x/text@v0.3.5
```

入门说明请参阅[教程：创建模块](/doc/tutorial/create-module.html)。

使用模块管理依赖的相关指南，请参阅[开发模块](/doc/#developing-modules)。

模块中的包应在演进过程中保持向后兼容，遵循[导入兼容性规则](https://research.swtch.com/vgo-import)：

> 如果旧包和新包具有相同的导入路径，\
> 那么新包必须向后兼容旧包。

[Go 1 兼容性准则](/doc/go1compat.html)是很好的参考：不要删除导出名称，鼓励使用带字段名的复合字面量，等等。如果需要不同的功能，应添加新名称，而不是改变旧名称的含义。

模块通过[语义化版本](https://semver.org/)和语义导入版本机制落实这一规则。如果必须破坏兼容性，就应发布模块的新主版本。主版本为 2 及以上的模块，其路径中必须包含[主版本后缀](/ref/mod#major-version-suffixes)，例如 `/v2`。这样可以维持导入兼容性规则：同一模块不同主版本中的包具有不同路径。

## 指针与内存分配 {#Pointers}

### 函数参数在什么情况下按值传递？ {#pass_by_value}

与 C 语言家族的其他语言一样，Go 中所有参数都是按值传递的。也就是说，函数总会获得传入内容的一份副本，就像通过赋值语句将值赋给形参一样。例如，传入 `int` 值会复制这个整数，传入指针值会复制这个指针，但不会复制指针所指向的数据。关于这如何影响方法接收者，请参阅[后面的章节](/doc/faq#methods_on_values_or_pointers)。

map 和切片值的行为类似指针：它们是包含指向底层 map 或切片数据的指针的描述信息。复制 map 或切片值不会复制底层数据。复制接口值，则会复制接口中保存的具体值。如果接口保存的是结构体，就会复制结构体；如果保存的是指针，就会复制指针，同样不会复制它所指向的数据。

注意，这里讨论的是操作的语义。实际实现可以通过优化避免复制，只要不改变程序语义即可。

### 什么时候应该使用指向接口的指针？ {#pointer_to_interface}

几乎从来不需要。只有一些罕见而复杂的场景，例如为了延迟求值而隐藏接口值的类型，才可能需要接口指针。

一个常见错误是，向期望接收接口值的函数传入接口值的指针。编译器会报告错误，但这仍然容易令人困惑，因为有时确实[必须使用指针才能满足接口](#different_method_sets)。关键在于：具体类型的指针可以满足接口，但除一个例外之外，*接口的指针无法满足接口*。

考虑以下变量声明：

```
var w io.Writer
```

格式化输出函数 `fmt.Fprintf` 的第一个实参需要满足 `io.Writer`，即实现约定的 `Write` 方法。因此可以写：

```
fmt.Fprintf(w, "hello, world\n")
```

但如果传入 `w` 的地址，程序就无法编译。

```
fmt.Fprintf(&w, "hello, world\n") // Compile-time error.
```

唯一的例外是，任意值，包括指向接口的指针，都可以赋给空接口类型 `interface{}` 的变量。即便如此，如果这个值是接口指针，几乎可以确定这不是你真正想要的做法，结果也可能令人困惑。

### 方法应该使用值接收者还是指针接收者？ {#methods_on_values_or_pointers}

```
func (s *MyStruct) pointerMethod() { } // method on pointer
func (s MyStruct)  valueMethod()   { } // method on value
```

对于不熟悉指针的程序员，这两个例子的区别可能令人困惑，但实际情况很简单。为类型定义方法时，接收者（上例中的 `s`）的行为与方法的普通参数完全相同。因此，选择值接收者还是指针接收者，与选择函数参数按值还是按指针传入，是同一个问题。需要考虑以下几点。

首先，也是最重要的一点：方法是否需要修改接收者？如果需要，接收者*必须*是指针。（切片和 map 具有引用语义，情况略有不同，但如果方法要修改切片的长度，接收者仍必须是指针。）在上例中，如果 `pointerMethod` 修改 `s` 的字段，调用方能够看到这些修改；而 `valueMethod` 接收到的是调用方实参的副本，这正是按值传递的含义，因此对副本的修改不会反映到调用方。

顺便说，Java 的方法接收者一直具有指针性质，只是这种性质在语法上有所隐藏；而近期的发展也在为 Java 引入值接收者。Go 的值接收者才是相对不常见的做法。

其次是效率。如果接收者很大，例如一个较大的 `struct`，使用指针接收者可能成本更低。

然后是一致性。如果某个类型的部分方法必须使用指针接收者，其他方法也应如此，这样无论如何使用该类型，方法集都能保持一致。详细说明见[方法集](#different_method_sets)一节。

对于基本类型、切片和较小的 `struct`，值接收者的复制成本很低。因此，除非方法语义要求使用指针，值接收者通常既高效又清晰。

### new 和 make 有什么区别？ {#new_and_make}

`new` 分配内存，而 `make` 初始化切片、map 和通道类型。

详细说明请参阅[《高效 Go 编程》的相关章节](/doc/effective_go.html#allocation_new)。

### 在 64 位机器上，`int` 有多大？ {#q_int_sizes}

`int` 和 `uint` 的大小由实现决定，但在同一平台上二者大小相同。为了可移植性，依赖特定位宽的代码应使用 `int64` 这样显式指定位宽的类型。在 32 位机器上，编译器默认使用 32 位整数；在 64 位机器上，整数为 64 位。历史上并非一直如此。

另一方面，浮点数和复数类型始终明确指定位宽，没有 `float` 或 `complex` 这样的基本类型，因为程序员使用浮点数时应明确了解其精度。无类型浮点常量的默认类型是 `float64`，因此 `foo` `:=` `3.0` 会声明一个 `float64` 类型的 `foo` 变量。要用无类型常量初始化 `float32` 变量，必须在声明中明确写出类型：

```
var foo float32 = 3.0
```

也可以通过转换为常量指定类型，例如 `foo := float32(3.0)`。

### 如何判断变量分配在堆上还是栈上？ {#stack_or_heap}

从程序正确性的角度看，不需要知道。Go 中的变量只要仍被引用，就会继续存在。实现选择的存储位置与语言语义无关。

但存储位置会影响程序效率。条件允许时，Go 编译器会将函数局部变量分配在该函数的栈帧中。不过，如果无法证明函数返回后该变量不再被引用，编译器就必须将它分配到由垃圾回收器管理的堆上，避免悬空指针。此外，如果局部变量很大，放在堆上而不是栈上也可能更合理。

在当前编译器中，如果对一个变量取地址，它就可能被分配到堆上。不过，基本的*逃逸分析*能够识别某些变量不会活过函数返回的情况，让它们仍然留在栈上。

### 为什么我的 Go 进程使用这么多虚拟内存？ {#Why_does_my_Go_process_use_so_much_virtual_memory}

Go 内存分配器会预留一大片虚拟地址空间作为内存分配区域。这部分虚拟内存只属于相应的 Go 进程，预留它不会占用其他进程可用的物理内存。

要查看 Go 进程实际分配的内存，可以使用 Unix 的 `top` 命令，观察 Linux 上的 `RES` 列或 macOS 上的 `RSIZE` 列。

## 并发 {#Concurrency}

### 哪些操作是原子的？互斥锁呢？ {#What_operations_are_atomic_What_about_mutexes}

Go 操作的原子性说明见 [Go 内存模型](/ref/mem)。

[sync](/pkg/sync) 和 [sync/atomic](/pkg/sync/atomic) 包提供底层同步与原子操作原语，适合增加引用计数、保证小范围互斥等简单任务。

对于并发服务器之间协调这样的高层操作，采用更高层的技术能得到更好的程序。Go 通过 goroutine 和通道支持这种方式。例如，可以组织程序，让某份数据在任一时刻都只由一个 goroutine 负责。最初的这句 [Go 箴言](https://www.youtube.com/watch?v=PAAkCSZUG1c)概括了这种方法：

不要通过共享内存来通信，而应通过通信来共享内存。

关于这个理念的详细讨论，请参阅[通过通信共享内存](/doc/codewalk/sharemem/)代码导读及其[配套文章](/blog/share-memory-by-communicating)。

大型并发程序很可能会同时使用这两类工具。

### 为什么增加 CPU 后，程序没有变快？ {#parallel_slow}

更多 CPU 能否让程序变快，取决于程序解决的问题。Go 提供 goroutine、通道等并发原语，但只有问题本身能够并行处理时，并发才有可能转化为并行。本质上必须按顺序处理的问题，无法靠增加 CPU 加速；可以拆分为多个独立并行部分的问题，则能够加速，有时提升非常明显。

有时，增加 CPU 反而会使程序变慢。实际中，如果程序花在同步或通信上的时间多于有效计算，那么使用多个操作系统线程可能降低性能。这是因为在线程之间传递数据涉及上下文切换，其成本不低，而且可能随 CPU 数量增加而上升。例如，Go 规范中的[素数筛示例](/ref/spec#An_example_package)虽然启动了许多 goroutine，却没有明显的并行性；增加线程或 CPU 数量，更可能使它变慢而不是变快。

更多说明请参阅演讲[并发不等于并行](/blog/concurrency-is-not-parallelism)。

### 如何控制使用的 CPU 数量？ {#number_cpus}

可以同时执行 goroutine 的 CPU 数量由 shell 环境变量 `GOMAXPROCS` 控制，默认值为可用的 CPU 核心数量。因此，具备并行执行条件的程序在多 CPU 机器上默认就应该能够并行执行。要调整使用的并行 CPU 数量，可以设置这个环境变量，或调用 runtime 包中的同名[函数](/pkg/runtime/#GOMAXPROCS)，配置运行时使用不同数量的线程。将其设为 1 会排除真正并行执行 Go 代码的可能，让独立的 goroutine 轮流执行。

为了处理多个尚未完成的 I/O 请求，运行时可以创建超过 `GOMAXPROCS` 数量的线程。`GOMAXPROCS` 只影响实际能够同时执行的 goroutine 数量；还可以有更多 goroutine 阻塞在系统调用中。

Go 的 goroutine 调度器能够较好地平衡 goroutine 与线程，甚至可以抢占某个 goroutine，防止同一线程上的其他 goroutine 得不到执行。不过，它并非完美无缺。如果遇到性能问题，针对具体应用调整 `GOMAXPROCS` 可能有所帮助。

### 为什么没有 goroutine ID？ {#no_goroutine_id}

goroutine 没有名称，只是匿名的执行单元。它不向程序员暴露唯一标识符、名称或数据结构。有些人对此感到意外，认为 `go` 语句应该返回某种对象，以便之后访问和控制该 goroutine。

保持 goroutine 匿名的根本原因，是让编写并发代码时仍然能充分使用 Go 的全部能力。相比之下，为线程或 goroutine 命名所形成的使用模式，可能限制库的实现方式。

下面的例子可以说明问题。一旦为 goroutine 命名并围绕它建立模型，它就变得特殊，开发者容易将全部计算都与它绑定，忽略使用多个、甚至共享的 goroutine 处理任务的可能。如果 `net/http` 包将每个请求的状态绑定到某个 goroutine，使用者就无法在处理请求时继续使用更多 goroutine。

此外，图形系统等要求所有操作都在“主线程”执行的库，已经表明这种方式在并发语言中有多么别扭和受限。特殊线程或 goroutine 的存在，会迫使程序员扭曲程序结构，以避免不小心在错误线程上操作造成崩溃等问题。

对于某个 goroutine 确实需要特殊对待的情况，语言已经提供通道等特性，可以灵活地与它交互。

## 函数与方法 {#Functions_methods}

### 为什么 T 和 *T 的方法集不同？ {#different_method_sets}

正如 [Go 语言规范](/ref/spec#Types)所述，类型 `T` 的方法集包含所有接收者为 `T` 的方法，而对应指针类型 `*T` 的方法集包含所有接收者为 `*T` 或 `T` 的方法。也就是说，`*T` 的方法集包含 `T` 的方法集，反过来则不成立。

之所以这样区分，是因为如果接口值保存了指针 `*T`，调用方法时可以通过解引用取得 `T` 值；但如果接口保存的是值 `T`，就没有安全的方式让方法调用取得指向它的指针。那样做会允许方法修改接口内部的值，而语言规范不允许这种行为。

即使编译器能够对某个值取地址并传给方法，如果方法修改这个值，调用方也不会得到这些修改。

例如，假设下面的代码合法：

```
var buf bytes.Buffer
io.Copy(buf, os.Stdin)
```

它会把标准输入复制到 `buf` 的*副本*中，而不是 `buf` 本身。这几乎从来不是期望的行为，因此语言不允许这样做。

### 将闭包作为 goroutine 运行时会发生什么？ {#closures_and_goroutines}

在 Go 1.22 之前，由于循环变量的工作方式，将闭包与并发结合时可能产生困惑。本节末尾说明了后续的变化。考虑下面的程序：

{{raw `
<pre>
func main() {
    done := make(chan bool)

    values := []string{"a", "b", "c"}
    for _, v := range values {
        go func() {
            fmt.Println(v)
            done &lt;- true
        }()
    }

    // wait for all goroutines to complete before exiting
    for _ = range values {
        &lt;-done
    }
}
</pre>
`}}

有人可能误以为输出会是 `a, b, c`，但更可能看到 `c, c, c`。这是因为循环的每次迭代都使用同一个变量 `v`，各个闭包共享它。闭包执行时，输出的是 `fmt.Println` 实际执行那一刻的 `v`，而在 goroutine 启动之后，`v` 可能已经发生变化。运行 [`go vet`](/cmd/go/#hdr-Run_go_tool_vet_on_packages) 可以提前帮助发现这类及其他问题。

要在启动闭包时将当前的 `v` 值与它绑定，需要修改循环，让每次迭代都创建一个新变量。一种方式是将变量作为参数传入闭包：

{{raw `
<pre>
    for _, v := range values {
        go func(<b>u</b> string) {
            fmt.Println(<b>u</b>)
            done &lt;- true
        }(<b>v</b>)
    }
</pre>
`}}

这里将 `v` 的值作为实参传给匿名函数，函数内通过变量 `u` 访问这个值。

更简单的方式是直接创建一个新变量。下面这种声明看起来可能有些奇怪，但在 Go 中完全合法：

{{raw `
<pre>
    for _, v := range values {
        <b>v := v</b> // create a new 'v'.
        go func() {
            fmt.Println(<b>v</b>)
            done &lt;- true
        }()
    }
</pre>
`}}

回过头看，没有为每次迭代定义新变量的设计被认为是一个错误。[Go 1.22](/wiki/LoopvarExperiment) 已经修正了这一点：现在每次迭代确实会创建新变量，从而消除这个问题。

## 控制流 {#Control_flow}

### 为什么 Go 没有 `?:` 运算符？ {#Does_Go_have_a_ternary_form}

Go 没有三元条件运算符。可以使用以下代码达到同样的效果：

```
if expr {
    n = trueVal
} else {
    n = falseVal
}
```

Go 没有 `?:`，是因为语言设计者见过太多人用它构造极其复杂、难以理解的表达式。`if-else` 虽然更长，但无疑更清楚。一门语言只需要一种条件控制流结构。

## 类型形参 {#Type_Parameters}

### 为什么 Go 要支持类型形参？ {#why_generics}

类型形参支持泛型编程：定义函数和数据结构时，先用尚未确定的类型描述它们，再在使用时指定具体类型。例如，可以编写一个函数，返回任意有序类型的两个值中的较小值，而不必为每种可能的类型分别编写版本。更深入的说明及示例请参阅博客文章[为什么需要泛型？](/blog/why-generics)。

### Go 如何实现泛型？ {#generics_implementation}

编译器可以选择为每次实例化分别编译，也可以让相似的实例化共享一份实现。共享实现的方式类似于使用接口参数的函数。不同编译器会针对不同情况作出不同选择。标准 Go 编译器通常会让具有相同“形状”的类型实参共享一个实例化版本；形状由类型大小、所含指针的位置等属性决定。未来的版本可能继续探索编译时间、运行效率和代码体积之间的取舍。

### Go 的泛型与其他语言相比有什么不同？ {#generics_comparison}

各门语言提供的基本功能类似：都允许使用稍后才指定的类型来编写类型和函数。不过，具体机制存在一些区别。

* Java

	在 Java 中，编译器会在编译期检查泛型类型，但运行时会移除泛型类型信息，这称为[类型擦除](https://en.wikipedia.org/wiki/Generics_in_Java#Problems_with_type_erasure)。例如，编译时的 `List<Integer>` 到运行时会成为非泛型的 `List`。因此，使用 Java 反射时，无法区分 `List<Integer>` 和 `List<Float>` 的值。Go 泛型类型的反射信息则包含完整的编译期类型信息。

	Java 使用 {{raw `<code>List&lt;? extends Number&gt;</code>`}} 或 {{raw `<code>List<? super Number></code>`}} 这样的类型通配符实现泛型的协变和逆变。Go 没有这些概念，因此泛型类型简单得多。

* C++

	传统的 C++ 模板不对类型实参强制施加约束，不过 C++20 通过 [concepts（概念）](https://en.wikipedia.org/wiki/Concepts_(C%2B%2B))支持可选约束。在 Go 中，所有类型形参都必须有约束。C++20 的 concept 用小段代码表达，要求这些代码在使用给定类型实参时能够编译。Go 的约束则是接口类型，用于定义所有允许的类型实参的集合。

	C++ 支持模板元编程，Go 不支持。实践中，C++ 编译器会在模板实例化的位置编译每个模板；如前所述，Go 可以针对不同实例化采用不同策略，实际也会如此。

* Rust

	Rust 中的约束称为 trait bound（特征约束）。在 Rust 中，类型与 trait 的实现关系必须显式定义，定义位置要么是声明该 trait 的 crate，要么是声明该类型的 crate。在 Go 中，类型实参隐式满足约束，就像 Go 类型隐式实现接口一样。Rust 标准库为比较、加法等操作定义了标准 trait；Go 标准库没有这样做，因为用户代码可以通过接口类型表达这些要求。唯一的例外是 Go 的预声明接口 `comparable`，它表达了无法用普通类型系统机制表达的可比较属性。

* Python

	Python 不是静态类型语言，因此可以合理地认为，所有 Python 函数默认都是泛型的：总是可以用任意类型的值调用它们，类型错误则在运行时发现。

### 为什么 Go 使用方括号表示类型形参列表？ {#generic_brackets}

Java 和 C++ 使用尖括号表示类型形参列表，例如 Java 的 `List<Integer>` 和 C++ 的 `std::vector<int>`。但 Go 无法采用这种方案，因为它会造成语法歧义：解析函数内部的 `v := F<T>` 之类代码时，看到 {{raw `<code>&lt;</code>`}} 的那一刻，无法判断这是泛型实例化，还是使用 {{raw `<code>&lt;</code>`}} 运算符的表达式。没有类型信息，就很难消除这种歧义。

例如，考虑下面这样的语句：

{{raw `
<pre>
    a, b = w &lt; x, y &gt; (z)
</pre>
`}}

没有类型信息，就无法判断赋值右侧是两个表达式 {{raw `<code>w &lt; x</code>`}} 和 {{raw `<code>y &gt; z</code>`}}，还是一次返回两个结果的泛型函数实例化及调用，即 {{raw `<code>(w&lt;x, y&gt;)(z)</code>`}}。

Go 的一个关键设计决策是：无需类型信息即可完成语法解析。而泛型若使用尖括号，似乎就无法保持这一点。

使用方括号并非 Go 独有或首创；Scala 等其他语言也使用方括号编写泛型代码。

### 为什么 Go 不支持带类型形参的方法？ {#generic_methods}

Go 允许泛型类型拥有方法，但方法只能使用接收者类型已有的类型形参，不能额外声明自己的类型形参。我们预计 Go 将来也不会加入这种泛型方法。

问题在于如何实现，尤其是如何检查接口中的某个值是否实现了另一个包含额外方法的接口。例如，考虑下面这个假想类型：一个空结构体，具有泛型方法 `Nop`，能够原样返回任意类型的实参。

```
type Empty struct{}

func (Empty) Nop[T any](x T) T {
	return x
}
```

假设将 `Empty` 值存入 `any`，再传给其他代码，检查它能做什么：

```
func TryNops(x any) {
	if x, ok := x.(interface{ Nop(string) string }); ok {
		fmt.Printf("string %s\n", x.Nop("hello"))
	}
	if x, ok := x.(interface{ Nop(int) int }); ok {
		fmt.Printf("int %d\n", x.Nop(42))
	}
	if x, ok := x.(interface{ Nop(io.Reader) io.Reader }); ok {
		data, err := io.ReadAll(x.Nop(strings.NewReader("hello world")))
		fmt.Printf("reader %q %v\n", data, err)
	}
}
```

如果 `x` 是 `Empty`，这段代码应该如何工作？看起来，`x` 必须满足所有三个检查，还要满足使用其他任意类型的类似检查。

调用这些方法时，又应该执行哪段代码？对于非泛型方法，编译器会为所有方法实现生成代码，并链接到最终程序中。但泛型方法可能有无限多种实例化实现，因此需要另一种策略。

有四种选择：

 1. 在链接时列出所有可能的动态接口检查，查找本应满足这些接口、却缺少已编译方法的类型，再次调用编译器补齐相关方法。

    这样需要在链接之后暂停并重复部分编译工作，会显著拖慢构建，尤其是增量构建。更糟的是，新编译的方法本身可能带来新的动态接口检查，迫使流程继续重复，甚至可以构造出永远无法结束的例子。

 2. 实现某种 JIT（即时编译），在运行时编译需要的方法代码。

    Go 从纯粹的提前编译中获得了简单性和可预测性能方面的巨大收益。我们不愿意仅为实现一个语言特性，就引入 JIT 的复杂性。

 3. 为每个泛型方法生成一个较慢的回退实现，通过函数表处理类型形参上所有可能的语言操作，并在动态检查时使用它。

    这会让使用编译期未预见类型的泛型方法，远慢于使用编译期已知类型的相同方法，使性能更加难以预测。

 4. 规定泛型方法完全不能用于满足接口。

    接口是 Go 编程的核心组成部分。从设计角度看，禁止泛型方法满足接口是不可接受的。

这些方案都不好，因此我们选择不采用其中任何一个。

需要类似能力时，可以使用带类型形参的包级函数，或者将类型形参加到接收者类型上。

更多细节和示例请参阅[提案](/design/43651-type-parameters#no-parameterized-methods)。

### 为什么不能在泛型类型的方法接收者中指定更具体的类型？ {#types_in_method_declaration}

为泛型类型声明方法时，接收者中要写出类型形参的名称。可能因为这种语法与调用时指定类型实参的形式很像，有些人以为可以在接收者中写入 `string` 这样的具体类型，从而为某些类型实参定制方法：

```
type S[T any] struct { f T }

func (s S[string]) Add(t string) string {
    return s.f + t
}
```

这段代码会失败，因为编译器把这里的 `string` 当作方法中重新声明的类型形参名称。错误信息可能类似“`operator + not defined on s.f (variable of type string)`”。这看起来很困惑，因为预声明类型 `string` 明明支持 `+`，但在这个方法内，声明的类型形参遮蔽了预声明的 `string`。这个新 `string` 与真正的字符串类型无关，其约束也不保证支持 `+`。遮蔽预声明名称在语法上合法，但很不寻常，通常是误写。

### 为什么编译器无法推断我程序中的类型实参？ {#type_inference}

许多情况下，程序员很容易看出泛型类型或函数应该使用什么类型实参，但语言并不允许编译器推断它。类型推断受到有意限制，以确保推断结果始终清楚、没有歧义。其他语言的经验表明，出乎意料的类型推断会给代码阅读和调试带来很大困惑。你始终可以在调用时显式指定类型实参。未来可能支持更多推断形式，但前提是规则依然简单明确。

## 包与测试 {#Packages_Testing}

### 如何创建包含多个文件的包？ {#How_do_I_create_a_multifile_package}

将这个包的所有源文件放在同一个独立目录中。源文件可以直接引用同包其他文件中的内容，无需前向声明或头文件。

除了分散在多个文件中，这个包的编译和测试方式与单文件包完全相同。

### 如何编写单元测试？ {#How_do_I_write_a_unit_test}

在包源文件所在目录中创建一个以 `_test.go` 结尾的新文件。在其中写入 `import "testing"`，并编写如下形式的函数：

```
func TestFoo(t *testing.T) {
    ...
}
```

在该目录中运行 `go test`。它会查找 `Test` 函数，构建测试可执行文件并运行。

更多说明请参阅[如何编写 Go 代码](/doc/code.html)、[`testing`](/pkg/testing/) 包和 [`go test`](/cmd/go/#hdr-Test_packages) 子命令的文档。

### 为什么没有我习惯使用的测试辅助函数？ {#testing_framework}

Go 标准库的 [`testing`](/pkg/testing/) 包使编写单元测试很方便，但缺少其他语言测试框架中的一些功能，例如断言函数。本文[前面的章节](#assertions)解释了 Go 为什么不提供断言，同样的理由也适用于测试中的 `assert`。妥善处理错误意味着某个测试失败后，让其他测试继续运行，以便调试者全面了解问题。测试报告 `isPrime` 对 2、3、5、7（或 2、4、8、16）都给出了错误结果，比只报告它对 2 出错、随后停止其他测试更有价值。触发测试失败的程序员可能并不熟悉出错的代码。现在花时间编写清楚的错误消息，将来测试失败时就会得到回报。

另一个相关问题是，测试框架容易发展成自己的小语言，拥有条件判断、控制结构和输出机制，但 Go 已经具备这些能力，为什么还要重新造一套？我们更愿意用 Go 本身编写测试，既少学一门语言，也让测试直观易懂。

如果为了输出清晰错误而编写的额外代码显得重复繁琐，可以考虑表驱动测试：将输入和期望输出定义在数据结构中，再循环遍历它们。Go 对数据结构字面量有很好的支持。这样，编写良好测试和错误消息的投入可以复用于多个测试用例。标准库中有很多示例，例如 [`fmt` 包的格式化测试](/src/fmt/fmt_test.go)。

### 为什么标准库中没有 *X*？ {#x_in_std}

标准库的目的是支持运行时库、连接操作系统，并提供许多 Go 程序都需要的关键功能，例如格式化 I/O 和网络功能。它也包含 Web 编程中的重要组成部分，包括密码学，以及 HTTP、JSON、XML 等标准的支持。

对于历史上哪些内容被纳入标准库，没有明确统一的标准，因为很长一段时间里，它是*唯一*的 Go 库。不过，对于如今新增的内容，已有明确的衡量标准。

标准库很少增加新内容，纳入门槛也很高。标准库中的代码会带来长期而高昂的维护成本，且通常由原作者之外的人承担；它受到 [Go 1 兼容性承诺](/doc/go1compat.html)约束，难以修正 API 中的设计缺陷；同时还要遵循 Go 的[发布计划](/s/releasesched)，使修复无法迅速交付用户。

大多数新代码应放在标准库之外，通过 [`go` 工具](/cmd/go/)的 `go get` 命令获取。这样的代码可以拥有自己的维护者、发布周期和兼容性保证。用户可以在 [pkg.go.dev](https://pkg.go.dev/) 查找包并阅读文档。

虽然标准库中有些内容并不十分适合留在其中，例如 `log/syslog`，但由于 Go 1 兼容性承诺，我们仍会维护库中的所有内容。不过，我们鼓励大多数新代码放在其他地方。

## 实现 {#Implementation}

### Go 编译器采用什么技术构建？ {#What_compiler_technology_is_used_to_build_the_compilers}

Go 有多个可用于生产环境的编译器，也有面向不同平台的其他编译器正在开发中。

默认编译器 `gc` 随 Go 发行版提供，是支持 `go` 命令的工具链的一部分。由于自举的困难，`Gc` 最初用 C 编写：要搭建 Go 环境，本来就需要先有一个 Go 编译器。不过，情况已经改变，从 Go 1.5 开始，编译器本身就是 Go 程序。它通过自动翻译工具从 C 转换为 Go，过程见这份[设计文档](/s/go13compiler)和[演讲](/talks/2015/gogo.slide#1)。因此，编译器如今是“自托管”的，也就必须面对自举问题。解决办法是预先准备一个可工作的 Go 安装，就像通常需要先有一个可工作的 C 环境一样。如何从源代码搭建新的 Go 环境，详见[自举说明](/s/go15bootstrap)和[源码安装文档](/doc/install/source)。

`Gc` 使用 Go 编写，采用递归下降语法分析器，并使用同样以 Go 编写、基于 Plan 9 实现发展而来的自定义链接器，生成 ELF、Mach-O 和 PE 二进制文件。

`Gccgo` 的前端用 C++ 编写，采用递归下降分析器，并连接到标准 GCC 后端。一个实验性的 [LLVM 后端](https://go.googlesource.com/gollvm/)也使用相同的前端。

项目刚开始时，我们考虑过让 `gc` 使用 LLVM，但认为它过于庞大且速度较慢，无法达到性能目标。回头看，更重要的是，如果一开始就采用 LLVM，就更难引入 Go 所需、却不属于标准 C 体系的 ABI 和相关变化，例如栈管理。

事实证明，Go 很适合用来实现 Go 编译器，尽管这并非最初目标。没有从一开始就要求自托管，使语言设计能够专注于最初的使用场景：网络服务器。如果早早决定 Go 必须能编译自身，最终可能会得到一门更面向编译器构建的语言；这也是有价值的目标，却不是我们当初的目标。

虽然 `gc` 有自己的实现，但 [`go/parser`](/pkg/go/parser/) 包提供了用 Go 编写的词法和语法分析器，也有用 Go 编写的[类型检查器](/pkg/go/types)。`gc` 编译器使用了这些库的变体。

### 运行时支持是如何实现的？ {#How_is_the_run_time_support_implemented}

同样由于自举问题，运行时代码最初主要使用 C 编写，只包含少量汇编；后来除部分汇编外，都已转换为 Go。`Gccgo` 的运行时支持使用 `glibc`。`gccgo` 编译器使用分段栈技术实现 goroutine，并由 gold 链接器的相关改动提供支持。`Gollvm` 则类似地构建在相应的 LLVM 基础设施之上。

### 为什么这么简单的程序也会生成很大的二进制文件？ {#Why_is_my_trivial_program_such_a_large_binary}

`gc` 工具链中的链接器默认创建静态链接的二进制文件。因此，所有 Go 二进制文件都包含 Go 运行时，以及动态类型检查、反射、panic 时的堆栈回溯所需的运行时类型信息。

在 Linux 上，用 gcc 编译并静态链接一个简单的 C “hello, world”程序，大小约为 750 kB，其中包含 `printf` 的实现。使用 `fmt.Printf` 的等价 Go 程序则有几 MB，不过也包含更强大的运行时支持，以及类型和调试信息。

使用 `gc` 编译 Go 程序时，可以在链接阶段传入 `-ldflags=-w`，禁止生成 DWARF 调试信息。这样只会移除二进制文件中的调试信息，不影响其他功能，通常能够显著减小文件体积。

### 能否关闭未使用变量或导入的报错？ {#unused_variables_and_imports}

未使用的变量可能意味着代码有缺陷，而未使用的导入会拖慢编译；随着项目代码和参与人员的积累，这种影响可能十分明显。因此，Go 拒绝编译包含未使用的局部变量或导入的程序，用短期便利换取长期的构建速度和代码清晰度。

不过，开发过程中临时出现这种情况很常见，每次都必须删除它们才能编译，确实可能让人烦恼。

有人希望增加编译器选项来关闭检查，或至少将其降为警告。但我们没有加入这种选项，因为编译器选项不应影响语言语义，而且 Go 编译器不报告警告，只报告阻止编译的错误。

不提供警告有两个原因。第一，既然值得报告，就值得修改代码修复；反之，不值得修复的问题也不值得提及。第二，让编译器发出警告，容易促使实现针对依据不够充分的情况也发出提醒，使编译输出充满噪声，掩盖真正*应该*修复的错误。

不过，应对这种情况很容易：开发时可以使用空白标识符，让暂时未使用的内容保留下来。

```
import "unused"

// This declaration marks the import as used by referencing an
// item from the package.
var _ = unused.Item  // TODO: Delete before committing!

func main() {
    debugData := debug.Profile()
    _ = debugData // Used only during debugging.
    ....
}
```

如今，大多数 Go 程序员使用 [goimports](https://godoc.org/golang.org/x/tools/cmd/goimports)，自动重写 Go 源文件中的导入，使其保持正确，实际解决了未使用导入的问题。这个程序很容易集成到大多数编辑器和 IDE 中，在保存 Go 源文件时自动运行。[前面提到的](/doc/faq#ide) `gopls` 也内置了这项功能。

### 为什么杀毒软件认为 Go 发行版或编译出的二进制文件有病毒？ {#virus}

这种情况很常见，尤其是在 Windows 上，而且几乎总是误报。商业杀毒软件可能不熟悉 Go 二进制文件的结构，因为与其他语言生成的文件相比，它们遇到 Go 文件的频率较低。

如果刚安装 Go 发行版，系统就报告它被感染，通常是误报。要进一步确认，可以将下载文件的校验和与[下载页面](/dl/)上列出的校验和进行比较。

无论如何，如果认为报告有误，请向杀毒软件供应商提交问题。随着时间推移，杀毒软件也许会更好地识别 Go 程序。

## 性能 {#Performance}

### 为什么 Go 在基准测试 X 中表现不佳？ {#Why_does_Go_perform_badly_on_benchmark_x}

Go 的设计目标之一，是让相同用途程序的性能接近 C，但它在某些基准测试中表现较差，包括 [golang.org/x/exp/shootout](https://go.googlesource.com/exp/+/master/shootout/) 中的一些测试。最慢的测试往往依赖某些库，而 Go 尚没有性能相当的对应实现。例如，[pidigits.go](https://go.googlesource.com/exp/+/master/shootout/pidigits.go) 依赖多精度数学库，而 C 版本使用了以优化汇编编写的 [GMP](https://gmplib.org/)，Go 版本则没有。依赖正则表达式的测试，例如 [regex-dna.go](https://go.googlesource.com/exp/+/master/shootout/regex-dna.go)，本质上是在比较 Go 原生的 [regexp 包](/pkg/regexp)与 PCRE 等成熟、经过高度优化的正则表达式库。

基准测试竞赛往往靠大量调优取胜，而大多数测试的 Go 版本仍需要投入优化。如果比较真正可比的 C 和 Go 程序，例如 [reverse-complement.go](https://go.googlesource.com/exp/+/master/shootout/reverse-complement.go)，就会发现两门语言的原始性能比这组测试给人的印象接近得多。

当然，仍有改进空间。编译器已经不错，但还可以更好；许多库需要大量性能优化，垃圾回收器也还不够快。即使垃圾回收足够快，注意避免生成不必要的垃圾对象仍然会有显著影响。

无论如何，Go 的性能经常很有竞争力。随着语言和工具的发展，许多程序的性能都有了明显改善。[Go 程序性能分析](/blog/profiling-go-programs)这篇博客提供了一个很有启发性的例子。文章虽然较早，仍有实用价值。

## 与 C 的差异 {#change_from_c}

### 为什么语法与 C 差别这么大？ {#different_syntax}

除了声明语法，差别其实并不大，主要来自两个目标。第一，语法应当轻巧，没有过多强制关键字、重复内容或晦涩规则。第二，语言应易于分析，无需符号表就能完成语法解析。这能大大简化调试器、依赖分析器、自动文档提取工具、IDE 插件等工具的构建，而 C 及其后继语言在这方面出了名地困难。

### 为什么声明的顺序是反过来的？ {#declarations_backwards}

只有习惯了 C 才会觉得它是反的。C 的思想是让变量声明看起来像一个能表达其类型的使用表达式，这是个不错的想法，但类型语法和表达式语法结合得并不好，结果可能令人困惑，函数指针就是一例。Go 基本上分离了表达式和类型的语法，使事情更简单；指针使用前缀 `*` 是少数例外。在 C 中，声明：

```
    int* a, b;
```

会将 `a` 声明为指针，而 `b` 不是；在 Go 中：

```
    var a, b *int
```

会将两者都声明为指针。这更清楚，也更规则。此外，既然存在 `:=` 这种简短声明形式，完整变量声明也应采用相同顺序，因此：

```
    var a uint64 = 1
```

与以下代码效果相同：

```
    a := uint64(1)
```

让类型使用独立于表达式的语法，也简化了语法解析；`func`、`chan` 等关键字使含义保持清楚。

更多说明请参阅 [Go 的声明语法](/doc/articles/gos_declaration_syntax.html)。

### 为什么没有指针算术？ {#no_pointer_arithmetic}

为了安全。没有指针算术，就能避免通过地址计算产生非法地址、却错误地访问成功的情况。编译器和硬件技术已经发展到足以让数组索引循环与指针算术循环一样高效。此外，不提供指针算术也能简化垃圾回收器的实现。

### 为什么 `++` 和 `--` 是语句而不是表达式？为什么只支持后缀，不支持前缀？ {#inc_dec}

没有指针算术后，前缀和后缀自增运算符的便利性就降低了。将它们彻底移出表达式体系，可以简化表达式语法，同时消除围绕 `++` 和 `--` 求值顺序的复杂问题，例如 `f(i++)` 和 `p[i] = q[++i]`。这种简化意义很大。至于后缀还是前缀，两者都可以，但后缀形式更传统。对前缀形式的强调兴起于 STL；有趣的是，STL 所属语言的名称 C++ 恰恰包含后缀自增。

### 为什么有大括号，却没有分号？为什么左大括号不能放在下一行？ {#semicolons}

Go 使用大括号组织语句，这种语法为 C 家族语言的程序员所熟悉。分号主要是给语法分析器看的，而不是给人看的，因此我们希望尽量消除它们。为此，Go 借用了 BCPL 的一个技巧：正式语法仍然包含分隔语句的分号，但词法分析器会在可能结束一条语句的行末自动插入分号，无需向后预读。实践中效果很好，不过也固定了大括号的排版方式。例如，函数的左大括号不能单独放在下一行。

有人主张让词法分析器向后预读，以允许左大括号放到下一行。我们并不赞同。既然 Go 代码要由 [`gofmt`](/cmd/gofmt/) 自动格式化，就必须选择*某一种*风格。这种风格也许与你在 C 或 Java 中的习惯不同，但 Go 是另一门语言，而 `gofmt` 的风格并不逊于其他风格。更重要的是，让所有 Go 程序采用一种由工具统一执行的格式，收益远远超过人们对某种具体风格的不满。此外，Go 的风格还使交互式 Go 实现能够逐行使用标准语法，而无需特殊规则。

### 为什么采用垃圾回收？开销不会太大吗？ {#garbage_collection}

在系统程序中，管理已分配对象的生命周期是最繁重的日常工作之一。C 等语言要求手动完成这项工作，会消耗程序员大量时间，也经常造成难以察觉的严重缺陷。即使 C++ 或 Rust 等语言提供了辅助机制，这些机制也可能显著影响软件设计，并带来额外的编程负担。我们认为消除这些负担非常重要，而近年来垃圾回收技术的进步，让我们相信其开销和延迟可以足够低，适合网络系统。

并发编程的许多困难都源自对象生命周期：对象在线程之间传递时，很难保证它们最终被安全释放。自动垃圾回收让并发代码容易编写得多。当然，在并发环境中实现垃圾回收本身也是挑战，但统一解决一次，而不是让每个程序都重新处理，对所有人都有益。

最后，即使不考虑并发，垃圾回收也能简化接口，因为接口无需规定跨边界的内存管理方式。

这并不意味着 Rust 等语言近年来在资源管理问题上引入新思路的工作方向错误。我们鼓励这些探索，也很期待看到它们的发展。只是 Go 采用了更传统的方式，通过垃圾回收，而且仅通过垃圾回收，管理对象生命周期。

当前实现采用标记清扫垃圾回收器。如果机器有多个处理器，回收器可以在单独的 CPU 核心上与主程序并行运行。近年来的大量优化，使得即使堆很大，暂停时间也通常能降到亚毫秒级，基本消除了网络服务器使用垃圾回收时的一项主要顾虑。我们仍在改进算法，进一步降低开销与延迟，并探索新方法。Go 团队的 Rick Hudson 在 2018 年 [ISMM 主题演讲](/blog/ismmkeynote)中介绍了当时的进展，并提出了一些未来方向。

谈到性能，还应记住，Go 让程序员对内存布局和分配拥有相当多的控制权，远多于典型的垃圾回收语言。细心的程序员可以善用语言特性，大幅降低垃圾回收开销。[Go 程序性能分析](/blog/profiling-go-programs)一文给出了完整示例，也演示了 Go 的性能分析工具。
