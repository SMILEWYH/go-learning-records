# 3. Redis 事务和 Lua 脚本

## 3.1 Redis 事务

我们知道数据库事务具有 ACID：原子性，一致性，隔离性，持久性。

但是 Redis 事务不同：

 	1. 不具备和数据库事务一样的原子性；事务开始后不保证全部成功或全部撤销（所以没有事务回滚）：执行时某条命令报错，其他命令仍会执行，已成功的操作不会回滚。
 	2. 不具备和数据库事务一样的一致性；因为 Redis 事务执行时不具备和数据库事务一样的原子性，例如转账时，扣款成功但入账失败，就无法保证双方余额总和不变。
 	3. 具备隔离性； 保证 `EXEC` 执行期间的隔离：事务中的命令连续执行，其他客户端的命令不会插入其中。
 	4. 是否具备持久性取决于持久化配置和保存策略。

所以 Redis 事务的本质：一组命令的集合！一个事务中的所有命令会被序列化，然后一次性、顺序性、排他性的执行这一组命令。

Redis 事务没有隔离级别的概念（因为 Redis 执行事务是放到主线程（单线程）串行执行的）。

所有的命令在事务中，并没有直接被执行，只有发起执行命令的时候才会执行（exec）。

Redis 单条命令是保证原子性的，但是事务不保证原子性。

Redis 事务从开始到结束的命令：

- 开启事务：multi
- 命令入队
- 执行事务：exec
- 撤销事务：discard

### 3.1.1 正常执行事务

~~~shell
127.0.0.1:6379> multi		# 开启事务
OK
127.0.0.1:6379> set k1 v1
QUEUED
127.0.0.1:6379> set k2 v2
QUEUED
127.0.0.1:6379> get k2
QUEUED
127.0.0.1:6379> set k3 v3
QUEUED
127.0.0.1:6379> exec			# 执行事务，结束后一次性返回事务内全部命令的结果
1) OK
2) OK
3) "v2"
4) OK
127.0.0.1:6379> 
~~~

### 3.1.2 放弃事务

~~~shell
127.0.0.1:6379> multi
OK
127.0.0.1:6379> set m1 n1
QUEUED
127.0.0.1:6379> set m2 n2
QUEUED
127.0.0.1:6379> DISCARD		# 放弃事务
OK
127.0.0.1:6379> get m1		# 事务队列中命令都不会被执行
(nil)
~~~

我们知道了 Redis 事务不具备和数据库事务一样的原子性，所以需要额外注意以下两种事务异常：

> 编译型异常：命令有错，事务中所有的命令都不会被执行

~~~shell
127.0.0.1:6379> multi
OK
127.0.0.1:6379> set k1 v1
QUEUED
127.0.0.1:6379> set k2 v2
QUEUED
127.0.0.1:6379> setget k3 v3		# 错误的命令
(error) ERR unknown command `setget`, with args beginning with: `k3`, `v3`, 
127.0.0.1:6379> set k4 v4
QUEUED
127.0.0.1:6379> exec		# 执行事务报错
(error) EXECABORT Transaction discarded because of previous errors.
127.0.0.1:6379> get k4		# 所有的命令都不会被执行
(nil)
127.0.0.1:6379> 
~~~

> 运行时异常：如果事务中某条命令执行结果报错，其他命令是可以正常执行的，错误命令抛出异常

~~~shell
127.0.0.1:6379> set k1 "v1"
OK
127.0.0.1:6379> multi
OK
127.0.0.1:6379> incr k1		# 会执行失败
QUEUED
127.0.0.1:6379> set k2 v2
QUEUED
127.0.0.1:6379> set k3 v3
QUEUED
127.0.0.1:6379> get k3
QUEUED
127.0.0.1:6379> exec
1) (error) ERR value is not an integer or out of range		# 第一条命令执行失败，其余的正常执行
2) OK
3) OK
4) "v3"
127.0.0.1:6379> get k2
"v2"
127.0.0.1:6379> 
~~~

### 3.1.3 监视 Watch （面试常问）

悲观锁：很悲观，认为什么时候都会出并发问题，无论什么都会加锁（共享锁、排他锁）。适合冲突较少、重做成本较低的场景。适合先读取、计算，提交时检查有没有冲突。有冲突就放弃这次更新，再根据业务决定重试，还是提示失败。

乐观锁：很乐观，认为什么时候都不会出现并发问题，所以不上锁。更新数据的时候会判断一下，在此期间是否修改过数据。适合冲突较多、希望减少重复计算的场景，但会增加等待和锁管理成本。先获取锁，再读取、修改数据。其他访问者按锁的规则等待或获取锁失败。

乐观锁的实现：Redis 中使用 watch + 事务，而数据库可以使用 version 字段。

悲观锁的实现：Redis 中使用 set nx ex 配合后端业务代码，而数据库有内置实现。

首先要了解 redis 事务中 watch 的作用：watch 命令可以监控一个或多个 key，一旦其中有一个 key 在事务 exec 执行前修改或删除（无论是其它 Redis 客户端做的、当前开启 watch 的这个 Redis 客户端在 multi 命令前做的）都会这个事务就不会执行。

所以，需要注意的是watch监控键之后，再去操作这些键，否则watch可能会起不到效果。

> Redis 监视测试

正常测试：

```bash
127.0.0.1:6379> set money 100		
OK
127.0.0.1:6379> set out 0
OK
127.0.0.1:6379> watch money		# 监视 money 对象
OK
127.0.0.1:6379> multi
OK
127.0.0.1:6379> DECRBY money 20
QUEUED
127.0.0.1:6379> INCRBY out 20
QUEUED
127.0.0.1:6379> exec 		# 事务正常结束，执行期间，money 没有变动，这个时候就能执行成功了
1) (integer) 80
2) (integer) 20
```

测试多线程修改值，使用 watch 可以当做 Redis 的乐观锁操作。

```bash
127.0.0.1:6379> set money 100
OK
127.0.0.1:6379> set out 10
OK
127.0.0.1:6379> watch money	# 监视 money
OK
127.0.0.1:6379> multi
OK
127.0.0.1:6379> DECRBY money 10
QUEUED
127.0.0.1:6379> DECRBY out 10
QUEUED
127.0.0.1:6379> exec		# 执行之前，在另外一个线程 B 中修改 money 的值，下面就是执行失败。
(nil)
127.0.0.1:6379> 
```

B 线程：

```bash
[root@coder bin]# redis-cli -p 6379
127.0.0.1:6379> set money 30
OK
```

如果修改失败，获取最新的值就好。

```bash
127.0.0.1:6379> UNWATCH		# 事务执行失败，先解锁
OK
127.0.0.1:6379> WATCH money		# 获取最新的值，再次监视。相当于 MySQL 中的 select version
OK
127.0.0.1:6379> multi
OK
127.0.0.1:6379> DECRBY money 1
QUEUED
127.0.0.1:6379> INCRBY out 1
QUEUED
127.0.0.1:6379> exec		# 执行的时候会对比监视的值，如果发生变化会执行失败。
1) (integer) 29
2) (integer) 11
127.0.0.1:6379> 
```



## 3.2 Lua 脚本

你可以明显发现 redis 事务中的命令执行结果只能在事务结束后一次性返回，无法根据前一条命令的结果，动态决定后续操作，所以需要Lua脚本来解决这个问题。
