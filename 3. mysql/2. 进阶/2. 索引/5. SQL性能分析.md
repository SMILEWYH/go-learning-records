# SQL性能分析

## SQL 执行频率

MySQL 客户端连接成功后，通过 `SHOW [SESSION | GLOBAL] STATUS` 命令可以提供服务器状态信息。

通过如下指令，可以查看整个 MySQL 实例中 INSERT、UPDATE、DELETE、SELECT 等语句的累计执行次数，而不是当前选中数据库的统计：

```sql
SHOW GLOBAL STATUS LIKE 'Com_______';
```

若要了解某段时间的执行频率，需要间隔采样，用两次累计次数的差值除以间隔时间。

如果 SELECT 执行较频繁，可以重点分析查询性能，再结合耗时、资源消耗等确定需要优化的 SQL；执行次数多并不代表执行速度慢。







现在我们确认了数据库的 SELECT 的访问频次很高，那么我们又应该具体对哪些 SELECT 语句进行优化呢？

## 慢查询日志

慢查询日志用于记录执行耗时较长的 SQL，帮助定位需要优化的语句。时间阈值由 `long_query_time` 指定，单位为秒，默认值为 10 秒。

### 1. 查看慢查询日志是否开启

```sql
SHOW VARIABLES LIKE 'slow_query_log';
```

作用：查看慢查询日志开关 `slow_query_log` 的当前值。返回 `ON` 表示已开启，`OFF` 表示未开启；这条命令只查看状态，不会开启日志。

### 2. 配置慢查询日志

MySQL 的慢查询日志默认未开启。以截图中的 Linux 环境为例，在 MySQL 配置文件 `/etc/my.cnf` 的 `[mysqld]` 部分添加或修改以下配置：

```ini
[mysqld]
# 开启 MySQL 慢查询日志
slow_query_log=1

# 设置慢查询时间阈值为 2 秒
long_query_time=2
```

执行时间超过 2 秒的 SQL，在满足其他日志记录条件时会被记录。实际是否记录还受 `min_examined_row_limit` 等配置影响，并非所有超时语句都无条件写入日志。

### 3. 重启 MySQL，使配置生效

在 Linux 终端执行（适用于使用 Linux 的 systemd 的环境）：

```bash
sudo systemctl restart 系统服务名
```

### 4. 查看慢查询日志文件

重启后重新连接 MySQL，可检查开关、时间阈值和日志文件路径：

```sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'slow_query_log_file';
```

当 `log_output` 包含 `FILE` 时，根据 `slow_query_log_file` 返回的实际路径，查看或持续跟踪日志文件内容。`slow_query_log_file` 是保存日志路径的系统变量名，不是实际文件名。



## Performance Schema：SQL 执行统计与耗时分析

### 1. 作用与统计范围

Performance Schema 是 MySQL 内置的运行时性能监控机制，可以收集 SQL 执行次数、耗时、等待事件等信息。

它可以汇总当前 MySQL 实例中各连接被采集到的 SQL，帮助发现“单次执行很快，但调用次数特别多”的语句。统计不限于当前连接，也不跨越多个 MySQL 实例。

`SHOW PROFILE` 主要分析当前会话中的语句，且已被弃用；现代 MySQL 项目优先使用 Performance Schema。这里学习 SQL 汇总统计和单次执行耗时的查看方法。

### 2. 使用前提

查看 Performance Schema 是否开启：

```sql
SHOW VARIABLES LIKE 'performance_schema';
```

返回 `ON` 表示已开启。还需要相关语句采集与计时、摘要统计已启用，并且当前账号有查询权限；不能仅凭开关为 ON 就认为所有 SQL 都已完整记录。

`sys` 库提供了便于阅读的视图，将 Performance Schema 的统计结果整理出来。下面使用 `sys.statement_analysis` 查询。

### 3. 找出累计调用最多的 SQL

```sql
SELECT
    db,             -- 执行时默认数据库
    query,          -- 归一化后的 SQL 模板
    exec_count,     -- 累计执行次数
    avg_latency,    -- 平均执行耗时
    total_latency,  -- 累计总耗时
    digest          -- SQL 摘要标识，可用于匹配两次采样
FROM sys.statement_analysis
ORDER BY exec_count DESC
LIMIT 10;
```

查询结果是当前已收集统计中，累计执行次数最多的 10 类 SQL。若需要限定某个默认数据库，可在 `ORDER BY` 前添加 `WHERE db = '实际数据库名'`。

结构相同、参数不同的 SQL 会归为同一类，例如：

```sql
SELECT * FROM tb_user WHERE id = 1;
SELECT * FROM tb_user WHERE id = 2;

-- 归一化后的模板类似如下，问号表示被归一化的参数值
SELECT * FROM tb_user WHERE id = ?;
```

同一模板在不同默认数据库下会分别统计。上面的模板用于展示统计方式，分析执行计划时需要使用实际 SQL 和有代表性的参数。

### 4. 如何判断是否值得优化

以下是示意结果，并非实际执行结果：

| SQL 类型 | 累计执行次数 | 平均耗时 | 累计总耗时 |
| --- | --- | --- | --- |
| 根据 id 查询用户 | 100,000 | 2 毫秒 | 200 秒 |

单次只需 2 毫秒，可能达不到慢查询日志的阈值，但大量重复调用仍会产生开销。这里的 200 秒是各次执行耗时相加，不代表某个请求等待了 200 秒，也不等于 CPU 使用时间。

执行次数多不一定有问题，需要结合总耗时和业务需求判断：

1. 使用 `EXPLAIN` 检查单次查询的索引与扫描方式。
2. 结合应用日志或请求追踪，定位调用这类 SQL 的业务代码。
3. 检查是否在循环中反复查询相同数据，或查出订单列表后又逐条查询用户；根据业务考虑批量查询、合适的表连接或缓存。
4. 修改后比较调用次数、耗时和返回结果，确认优化有效且结果正确。

### 5. 累计次数与最近一段时间的频率

`exec_count` 是已收集的累计次数，不是自动统计“最近一分钟”。若要分析最近一分钟的调用情况：

1. 保存一次统计快照。
2. 约 60 秒后再次采集，按 `db` 和 `digest` 匹配同一类 SQL。
3. 计算次数增量，再除以实际间隔秒数，得到该时间段的平均每秒调用次数。

例如，某类 SQL 的次数从 10,000 增加到 16,000，间隔为 60 秒，则该分钟执行了 6,000 次，平均每秒 100 次。

区间分析应采集完整的目标统计集合后再按增量排名，不能只比较两次累计排名前 10 的结果。实例重启、统计重置、采集配置和容量限制会影响结果；计数下降或条目缺失时，不能直接按普通增量计算。

### 6. 查看某条 SQL 某一次执行的实际耗时

`sys.statement_analysis` 提供一类 SQL 的汇总统计；`performance_schema.events_statements_history` 保存各线程最近完成的语句事件，可以查看某条 SQL 某一次执行的实际耗时。

在同一个数据库连接中，先执行要分析的 SQL，再立即执行以下查询：

```sql
-- 查看当前连接最近完成的 SQL 及其实际耗时
SELECT
    h.THREAD_ID,
    h.EVENT_ID,
    h.SQL_TEXT,
    ROUND(h.TIMER_WAIT / 1000000000, 3) AS duration_ms,
    h.ROWS_EXAMINED,
    h.ROWS_SENT
FROM performance_schema.events_statements_history AS h
JOIN performance_schema.threads AS t
    ON h.THREAD_ID = t.THREAD_ID
WHERE t.PROCESSLIST_ID = CONNECTION_ID()
ORDER BY h.EVENT_ID DESC
LIMIT 10;
```

| 字段 | 含义 |
| --- | --- |
| THREAD_ID、EVENT_ID | 共同标识某一次语句事件；EVENT_ID 不能单独作为整个实例中的唯一标识。 |
| SQL_TEXT | 本次执行的 SQL 文本，较长的文本可能被截断。 |
| duration_ms | 本次执行在数据库端测得的耗时，单位为毫秒，不等于应用请求的端到端耗时。 |
| ROWS_EXAMINED | 本次执行检查的行数。 |
| ROWS_SENT | 本次执行返回的行数。 |

`TIMER_WAIT` 的单位为皮秒，除以 `1,000,000,000` 转为毫秒。例如，某条记录的 `duration_ms = 2.350`，表示该次执行耗时约 2.35 毫秒，不是该类 SQL 的平均耗时。

使用时注意：

1. 必须事先开启 Performance Schema、相关语句采集与计时，以及 `events_statements_history` 等所需的消费者，并确保目标线程被采集。未采集的历史执行无法事后补录；未开启计时的记录中 `TIMER_WAIT` 可能为 `NULL`。
2. 历史表只保存每个线程有限条最近完成的记录，旧记录会被覆盖；`LIMIT 10` 只是本次查询的返回上限，不会扩大历史容量。
3. 这条查询通过 `CONNECTION_ID()` 限定当前连接。要查看应用连接中的语句，需要定位对应的线程，不能在数据库客户端执行后就认为看到的是应用连接的记录。
4. 如果要进一步查看该次 SQL 各阶段的耗时，需要另外开启阶段采集，并将阶段事件与该语句事件关联；上面的查询只展示整条语句的耗时。

参考：[语句事件字段](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-events-statements-current-table.html)、[语句历史表](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-events-statements-history-table.html)。

### 7. 与慢查询日志、EXPLAIN 配合

| 工具 | 主要用途 |
| --- | --- |
| 慢查询日志 | 找到达到记录条件的慢 SQL。 |
| Performance Schema 语句汇总 | 从执行次数、平均耗时、总耗时等角度定位需要分析的 SQL，包括高频短查询。 |
| EXPLAIN | 分析目标 SQL 的执行计划、索引选择与预计扫描行数。 |

参考：[SQL 汇总视图](https://dev.mysql.com/doc/refman/8.4/en/sys-statement-analysis.html)、[sys 使用前提](https://dev.mysql.com/doc/refman/8.4/en/sys-schema-prerequisites.html)、[Performance Schema 语句汇总表](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-statement-summary-tables.html)。



## EXPLAIN 执行计划

`EXPLAIN` 或者 `DESC` 命令可以获取 MySQL 如何执行 SELECT 语句的信息，包括表如何连接以及连接的顺序。

### 1. 语法

```sql
-- 直接在 SELECT 语句之前加上关键字 EXPLAIN / DESC
EXPLAIN SELECT 字段列表 FROM 表名 WHERE 条件;
```

### 2. 示例

```sql
EXPLAIN SELECT * FROM tb_user WHERE id = 1;
```

截图中的执行计划结果：

| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | SIMPLE | tb_user | NULL | const | PRIMARY | PRIMARY | 4 | const | 1 | 100.00 | NULL |

### 3. 执行计划各字段含义

#### id

SELECT 查询的序列号，用于标识查询中的 SELECT 查询块。

截图中的阅读口诀是：“id 相同，执行顺序从上到下；id 不同，值越大，越先执行。”这只是简化理解，不能仅凭 id 大小判断所有查询的实际执行顺序，还需结合优化器改写后的执行计划。

#### select_type

表示 SELECT 的类型，常见取值如下：

| 取值 | 含义 |
| --- | --- |
| SIMPLE | 简单查询，不包含 UNION 或子查询；可以包含表连接。 |
| PRIMARY | 最外层的 SELECT 查询。 |
| UNION | UNION 中第二个或后面的 SELECT 查询。 |
| SUBQUERY | 子查询中的第一个 SELECT；依赖外层查询时可能显示为 DEPENDENT SUBQUERY。 |

#### type

表示连接类型，也可理解为表的访问方式。截图中的常见类型可按以下顺序作粗略比较（通常从高效查找到大范围扫描）：

```text
NULL → system → const → eq_ref → ref → range → index → ALL
```

其中 `NULL` 通常表示无需访问表，`index` 表示全索引扫描，`ALL` 表示全表扫描，`const` 常见于主键／唯一索引的常量等值查找，`ref` 常见于普通索引的等值查找。



以上并非完整类型列表，也不能仅凭 type 判断实际耗时，还要结合扫描行数等信息。

#### possible_keys

显示可能用于查找该表数据的索引，可以是一个或多个。截图中的 `possible_key` 应为 `possible_keys`。

#### key

执行计划实际选择的索引；如果为 `NULL`，表示未选择索引。

#### key_len

表示执行计划使用的索引键长度，单位为字节，可用于判断联合索引使用了哪些列。它按字段定义等计算，并非某条记录中字段值的实际长度。

截图中“在不损失精确性的前提下，长度越短越好”更适合作为索引设计的考虑；分析执行计划时，不能简单认为 `key_len` 越小越好，较大的值也可能表示使用了联合索引中更多的列。

#### rows

MySQL 预计执行查询时需要检查的行数。对于 InnoDB 表，这是估计值，可能并不准确，不是查询最终返回的行数。

#### filtered

预计读取的行中，经过该表条件过滤后保留下来的行数百分比。`rows × filtered / 100` 可估算传递给后续连接的行数。

截图中“filtered 的值越大越好”不能作为通用结论：它表示过滤后的保留比例，需要结合 `rows`、索引和查询条件一起判断。





**这套方法在开发和生产环境都适用：**

**慢查询日志定位 SQL → EXPLAIN 分析执行计划 → 优化 SQL 或索引 → 实测验证效果。**

不过有三个边界：

- **开发时已知目标 SQL**，可以直接用 `EXPLAIN`，不必等待慢查询日志。
- **慢查询日志没有记录，不代表没有性能问题**。单次很快但调用过多的 SQL，或者应用等待数据库连接，都可能让接口变慢。
- **普通 `EXPLAIN` 给出的是计划和估算**。若慢在锁等待、磁盘 I/O 等方面，还需要结合运行时监控分析。

生产环境还要根据业务设置日志阈值，并管理日志大小；你笔记中的 **2 秒是示例值，不是固定标准**。

使用可以使用 **Performance Schema 的 SQL 汇总统计**，
