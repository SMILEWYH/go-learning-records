# limit优化

因为索引是**按键值组织的，不是按行号动态变化的。**主键值为 100 万的记录，不一定是扫描到的第 100 万条记录，所以 `LIMIT 1000000, 10` 不能直接定位到主键值为 100 万的位置，再取后面的 10 条；它需要扫描并跳过前 100 万条记录，然后返回接下来的 10 条。

## 大偏移量分页的问题

例如 `LIMIT 2000000, 10`，在记录足够时，需要先扫描并跳过前 200 万条记录，再返回第 2000001～2000010 条记录。虽然只返回 10 条记录，但扫描的代价很大。 

## 优化思路：覆盖索引 + 子查询

一般分页查询时，可以通过覆盖索引加子查询的形式进行优化：先在子查询中只查询当前页的 `id`，再根据这 10 个 `id` 关联原表，获取完整记录。

```sql
EXPLAIN
SELECT *
FROM tb_sku t,
     (SELECT id FROM tb_sku ORDER BY id LIMIT 2000000, 10) a
WHERE t.id = a.id;
```

这种方式仍需要扫描并跳过前 200 万条索引记录，不能直接按行号跳转；优化重点是先只取 `id`，再取当前页的完整数据。实际性能是否提升，需要结合表结构和执行计划判断。

> 子查询中的 `ORDER BY id` 用于确定当前页的 ID；如果最终结果也需要保证按 `id` 排序，应在外层查询添加 `ORDER BY t.id`。
