# 并发事务问题

以下以 InnoDB 为例，事务 A、B 分别在两个数据库连接中执行。

每个例子相互独立，步骤按先后顺序描述；是否出现问题与隔离级别、SQL 写法和加锁方式有关。

## 1. 脏读

描述：一个事务读到另外一个事务还没有提交的数据。

例子（事务 B 使用 READ UNCOMMITTED）：

- ① 账户余额原来是 1000，事务 A 将其改成 800，但尚未提交。

- ② 事务 B 查询余额，读到了 800，此时就发生了脏读。

- ③ 事务 A 回滚，余额恢复为 1000，B 刚才读到的修改最终没有生效。

注意：读取自己事务内尚未提交的修改不叫脏读；InnoDB 默认的 REPEATABLE READ 不允许脏读。

## 2. 不可重复读

描述：一个事务先后读取同一条记录，但两次读取的数据不同，称之为不可重复读。

例子（事务 A 使用 READ COMMITTED，两次均为普通 SELECT）：

- ① 事务 A 查询 id = 1 的账户，余额为 1000。

- ② 事务 B 将这个账户的余额改成 800，并提交。

- ③ 事务 A 在同一个事务内再次查询这个账户，余额变成 800。

同一条记录前后读到的值不同，就是不可重复读。

## 3. 幻读

图片描述：一个事务按照条件查询数据时，没有对应的数据行，但是在插入数据时，又发现这条数据已经存在，好像出现了“幻影”。

补充理解：通常指同一个事务按相同条件重复查询时，返回的记录集合发生变化，例如多出了符合条件的记录。

例子（事务 A 使用 READ COMMITTED，两次均为普通 SELECT）：

- ① 事务 A 查询年龄 >= 18 的用户，查到 3 条记录。

- ② 事务 B 插入一名年龄为 20 的用户，并提交。

- ③ 事务 A 在同一个事务内按相同条件再次查询，查到 4 条记录，多出了一条“幻影”记录。

注意：图片中的“查不到却插入冲突”还涉及唯一键检查，不能直接等同于普通 SELECT 两次结果不同。

InnoDB 默认的 REPEATABLE READ 下，重复的普通快照查询沿用同一快照，不会因 B 提交新增记录就看到它。

## 4. 丢失更新

描述：一个事务基于旧数据计算并写回结果，覆盖了另一个事务已经提交的修改。

例子（先普通 SELECT，再由程序计算，最后将计算结果写回）：

- ① 事务 A、B 都查询到账户余额为 1000。

- ② A 要存入 100，计算后执行 UPDATE account SET money = 1100 WHERE id = 1;，并提交。

- ③ B 要扣除 200，仍按旧余额 1000 计算，执行 UPDATE account SET money = 800 WHERE id = 1;，并提交。

正确余额应为 900，实际却为 800，A 存入的 100 被覆盖了。

注意：这与直接执行 SET money = money + 100 或 SET money = money - 200 的原子更新不同。

## 5. 写偏斜

描述：两个事务根据各自读到的数据修改不同记录，最终共同违反业务规则。

例子（使用 REPEATABLE READ 的普通快照查询，未对共同业务规则加锁保护）：

- ① 业务要求至少一名医生值班，当前张三、李四都在值班。

- ② 事务 A、B 都先查询到两人在值班，分别认为自己下班后还有另一人值班。

- ③ A 将张三设为下班，B 将李四设为下班，两个事务分别提交。

两个事务修改的是不同记录，但最终无人值班，违反了“至少一人值班”的规则。

## 6. 死锁

描述：两个或多个事务互相持有对方需要的锁，形成循环等待。

例子（更新不同主键对应的两行数据）：

- ① 事务 A 更新 id = 1 的记录，持有该行的锁，尚未提交。

- ② 事务 B 更新 id = 2 的记录，持有该行的锁，尚未提交。

- ③ A 尝试更新 id = 2，等待 B 释放锁。

- ④ B 又尝试更新 id = 1，等待 A 释放锁，形成死锁。

InnoDB 默认检测到死锁后，会选择一个事务整体回滚，让另一个事务继续执行。

## 7. 锁等待超时

描述：一个事务等待其他事务释放锁，等待时间超过设定限制后报错。

## 例子：

- ① 事务 A 更新 id = 1 的账户，但一直没有提交或回滚，持续持有该行的锁。

- ② 事务 B 也尝试更新这个账户，只能等待 A 释放锁。

- ③ 等待超过 innodb_lock_wait_timeout 后，B 收到 Lock wait timeout exceeded 错误。

注意：这里可以只有 B 等 A，不需要互相等待；默认只回滚 B 超时的那条语句，并非整个事务。
