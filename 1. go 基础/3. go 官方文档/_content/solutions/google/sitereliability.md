Google 运行着少量规模极大的服务。这些服务由全球基础设施支撑，涵盖开发者所需的一切：存储系统、负载均衡器、网络、日志、监控等等。然而，这不是一个静止的系统，也不可能是。架构不断演进，新产品和新想法不断出现，新版本需要发布，配置需要推送，数据库模式需要更新，还有更多事情要做。最终，我们每秒都要向系统部署数十次变更。

由于这种规模和对可靠性的关键需求，Google 开创了站点可靠性工程（SRE）这一角色，后来许多公司也采用了它。“将运维视为软件问题来处理，就产生了 SRE。我们的使命是保护、支撑并推进 Google 所有公共服务背后的软件和系统，并时刻关注它们的可用性、延迟、性能和容量。”——[站点可靠性工程（SRE）](https://sre.google/)。

2013 至 2014 年间，Google 的 SRE 团队意识到，我们管理生产环境的方式在许多方面已经难以满足需求。虽然我们早已超越只使用 shell 脚本的阶段，但在这样的规模下，各种动态组件和复杂性使我们必须寻找新方法。我们决定为生产环境引入一个名为“Prodspec”的声明式模型，并用它驱动一个名为“Annealing”的专用控制平面。

这些项目启动时，Go 刚开始成为 Google 关键服务的一种可行选择。大多数工程师更熟悉 Python 和 C++，而这两者本来也都是合理的选择。不过，Go 引起了我们的兴趣。新鲜感当然是因素之一，但更重要的是，Go 有望在性能和可读性之间取得另外两种语言无法提供的平衡。我们先在 Annealing 和 Prodspec 的部分初始组件中小规模试用 Go。随着项目推进，这些用 Go 编写的部分逐渐成为核心。我们对 Go 很满意：越来越喜欢它的简洁性，性能符合要求，并发原语也难以替代。

{{backgroundquote `

从来没有人强制或要求我们使用 Go，但我们也没有回到 Python 或 C++ 的愿望。Go 在 Annealing 和 Prodspec 中自然地扩展开来。它是合适的选择，因此如今也是我们的首选语言。Google 生产环境的大部分内容，都由我们用 Go 编写的系统管理和维护。

在这些项目中，一门简单语言的价值再怎么强调也不为过。确实曾有一些功能缺失，例如无法在代码中强制保证某个复杂结构不可被修改。但每遇到一次这样的情况，简洁性带来帮助的情形，毫无疑问都有数十次乃至数百次。

{{backgroundquote `
  quote: |
    Go 的简洁性让代码容易理解，无论是在代码审查中发现缺陷，还是在服务中断时查明究竟发生了什么。
`}}

例如，Annealing 影响着许多团队和服务，因此我们非常依赖整个公司的贡献。Go 的简洁性使团队以外的人也能理解某个部分为什么不符合他们的需求，并且经常能够自行提供修复或新功能。这让我们得以快速发展。

Prodspec 和 Annealing 负责一些相当关键的组件。Go 的简洁性让代码容易理解，无论是在代码审查中发现缺陷，还是在服务中断时查明究竟发生了什么。

Go 的性能和并发支持同样是我们工作中的关键。由于生产环境模型是声明式的，我们经常需要操作大量结构化数据，用来描述生产环境的现状和期望状态。服务规模很大，数据也可能变得很多，使得纯串行处理往往不够高效。

我们在许多地方、以许多方式操作这些数据。问题不在于找一个聪明人，为算法设计某个并行版本；而在于能够随手引入并行处理：找到下一个瓶颈，把那一段代码并行化。Go 恰好提供了这种能力。

由于 Go 的应用取得成功，如今我们在 Prodspec 和 Annealing 的所有新开发中都使用 Go。

除了站点可靠性工程团队，Google 的许多工程团队也已在开发过程中采用 Go。你可以继续了解 [Core Data Solutions](/solutions/google/coredata/)、[Firebase Hosting](/solutions/google/firebase/) 和 [Chrome](/solutions/google/chrome/) 团队如何使用 Go 大规模构建快速、可靠、高效的软件。
