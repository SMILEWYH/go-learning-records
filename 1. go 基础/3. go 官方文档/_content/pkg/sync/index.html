sync 包提供互斥锁等基本同步原语。除 Once 和 WaitGroup 类型外，大多数原语面向底层库代码。更高层的同步更适合通过通道和通信实现。

包含本包所定义类型的值不应被复制。

func OnceFunc 1.21 

func OnceFunc(f func()) func()

OnceFunc 返回一个函数，它只调用 f 一次。返回的函数可以并发调用。

如果 f 触发 panic，则返回的函数每次被调用时都会以同一个值触发 panic。

type Cond

Cond 实现条件变量，为等待事件发生或通知事件已发生的 goroutine（轻量级协程）提供协调点。

每个 Cond 都关联一个 Locker L（通常为 *Mutex 或 *RWMutex）。修改条件和调用 Cond.Wait 方法时，必须持有该锁。

Cond 首次使用后不得复制。

按照 Go 内存模型的术语，Cond 保证：对 Cond.Broadcast 或 Cond.Signal 的调用“同步先于”它所解除阻塞的任何 Wait 调用。

对于许多简单场景，使用通道比使用 Cond 更合适：Broadcast 对应关闭通道，Signal 对应向通道发送值。

关于 sync.Cond 的替代方案，更多内容参见 Roberto Clapis 的高级并发模式系列文章，以及 Bryan Mills 关于并发模式的演讲。 

type Cond struct {

    // 观察或更改条件时持有 L
    L Locker
    // 包含已过滤或未导出的字段
}

func NewCond 

func NewCond(l Locker) *Cond

NewCond 返回一个关联 Locker l 的新 Cond。

func (*Cond) Broadcast 

func (c *Cond) Broadcast()

Broadcast 唤醒所有正在 c 上等待的 goroutine。

调用方可以在调用时持有 c.L，但并非必须如此。Broadcast 的执行时间与等待中的 goroutine 数量成正比；请注意，调用 Broadcast 期间持有锁，会延长持锁时间。

func (*Cond) Signal 

func (c *Cond) Signal()

Signal 唤醒一个正在 c 上等待的 goroutine（如果存在）。

调用方可以在调用时持有 c.L，但并非必须如此。

Signal() 不影响 goroutine 的调度优先级；如果其他 goroutine 正尝试锁定 c.L，它们可能先于某个“等待中”的 goroutine 被唤醒。

func (*Cond) Wait 

func (c *Cond) Wait()

Wait 原子地解锁 c.L，并挂起调用它的 goroutine。之后恢复执行时，Wait 会在返回前重新锁定 c.L。与其他系统不同，Wait 只有被 Cond.Broadcast 或 Cond.Signal 唤醒后才能返回。

由于 Wait 等待期间 c.L 未锁定，调用方通常不能假定 Wait 返回时条件一定成立。因此，调用方应在循环中调用 Wait： 

c.L.Lock()
for !condition() {
    c.Wait()
}
... make use of condition ...
c.L.Unlock()

type Map 1.9

Map 类似于 Go 的 map[any]any，但无需额外加锁或协调，就能安全地供多个 goroutine 并发使用。读取、存储和删除操作的摊还时间复杂度为常数。

Map 类型针对特定场景设计。大多数代码应使用普通 Go 映射，并单独进行加锁或协调，以获得更好的类型安全性，也便于在维护映射内容的同时维护其他不变量。

Map 类型针对两种常见场景优化：（1）某个键的条目只写入一次，但读取多次，例如只增不减的缓存；（2）多个 goroutine 对互不相交的键集合中的条目进行读、写和覆盖。在这两种情况下，与普通 Go 映射配合单独的 Mutex 或 RWMutex 相比，Map 可能显著减少锁竞争。

Map 的零值为空且可直接使用。Map 首次使用后不得复制。

按照 Go 内存模型的术语，Map 保证写操作“同步先于”任何观察到该写操作效果的读操作。这里的读写操作定义如下：Map.Load、Map.LoadAndDelete、Map.LoadOrStore、Map.Swap、Map.CompareAndSwap 和 Map.CompareAndDelete 是读操作；Map.Delete、Map.LoadAndDelete、Map.Store 和 Map.Swap 是写操作；Map.LoadOrStore 在返回的 loaded 为 false 时是写操作；Map.CompareAndSwap 在返回的 swapped 为 true 时是写操作；Map.CompareAndDelete 在返回的 deleted 为 true 时是写操作。

func (*Map) Range 1.9 

func (m *Map) Range(f func(key, value any) bool)

Range 针对映射中的每个键和值依次调用 f。如果 f 返回 false，则停止迭代。

Range 不一定对应 Map 内容的某个一致快照：每个键最多访问一次，但如果某个键的值被并发存储或删除（包括由 f 执行），Range 可能反映该键在 Range 调用期间任意时刻的映射关系。Range 不会阻塞对接收者其他方法的调用；即使 f 本身也可以调用 m 的任意方法。

即使 f 在调用常数次后就返回 false，Range 的复杂度仍可能为 O(N)，其中 N 为映射中的元素数量。

type Mutex

Mutex 是互斥锁。Mutex 的零值是一把未锁定的互斥锁。

Mutex 首次使用后不得复制。

按照 Go 内存模型的术语，对于任意 n < m，第 n 次 Mutex.Unlock 调用“同步先于”第 m 次 Mutex.Lock 调用。成功的 Mutex.TryLock 调用等价于一次 Lock 调用。失败的 TryLock 调用不会建立任何“同步先于”关系。

    // 包含已过滤或未导出的字段
}

func (*Mutex) Lock 

func (m *Mutex) Lock()

Lock 锁定 m。如果锁已被占用，调用方 goroutine 会阻塞，直到互斥锁可用。

func (*Mutex) TryLock 1.18 

func (m *Mutex) TryLock() bool

TryLock 尝试锁定 m，并报告是否成功。

注意，虽然确实存在适合使用 TryLock 的场景，但这类场景很少；使用 TryLock 往往表明互斥锁的使用方式存在更深层的问题。

func (*Mutex) Unlock 

func (m *Mutex) Unlock()

Unlock 解锁 m。如果进入 Unlock 时 m 未锁定，会发生运行时错误。

已锁定的 Mutex 不与特定 goroutine 绑定。允许一个 goroutine 锁定 Mutex，再安排另一个 goroutine 将其解锁。

func (*Once) Do 

func (o *Once) Do(f func())

当且仅当针对这个 Once 实例首次调用 Do 时，Do 才会调用函数 f。换言之，给定 

var once Once

如果多次调用 once.Do(f)，只有第一次调用会执行 f，即使每次调用时 f 的值不同也是如此。每个需要执行的函数都需要单独的 Once 实例。

Do 用于必须且只能执行一次的初始化。由于 f 不接受参数，可能需要使用函数字面量捕获要由 Do 调用的函数所需的参数： 

config.once.Do(func() { config.init(filename) })

由于任何 Do 调用都要等那一次 f 调用返回后才会返回，如果 f 导致再次调用同一个 Once 的 Do，就会发生死锁。

如果 f 触发 panic，Do 会将其视为已返回；此后调用 Do 会直接返回，不再调用 f。

type Pool 1.3

Pool 是一组可分别存入和取出的临时对象。

存入 Pool 的任何对象都可能随时被自动移除，且不发出通知。如果此时只有 Pool 持有该对象的引用，对象就可能被释放。

多个 goroutine 同时使用 Pool 是安全的。

Pool 用于缓存已分配但未使用的对象，以便之后复用，从而减轻垃圾回收器的压力。也就是说，它便于构建高效、线程安全的空闲对象列表。但它并不适用于所有空闲对象列表。

Pool 适合管理一组临时对象，这些对象在包的多个独立并发使用方之间共享和复用，使用方无需感知这一过程。Pool 提供了一种在多个使用方之间摊销分配开销的方式。

fmt 包是合理使用 Pool 的一个例子：它维护一个大小动态变化的临时输出缓冲区存储池。该存储池在负载增加时（大量 goroutine 正在执行输出）扩张，并在空闲时收缩。

另一方面，作为短生命周期对象一部分而维护的空闲对象列表，不适合使用 Pool，因为这种情况下无法有效摊销开销。让此类对象自行实现空闲对象列表更高效。

Pool 首次使用后不得复制。

按照 Go 内存模型的术语，Put(x) 调用“同步先于”返回同一个值 x 的 Pool.Get 调用。同样，返回 x 的 New 调用“同步先于”返回同一个值 x 的 Get 调用。

    // 不得在调用 Get 的同时并发修改此字段。
    New func() any
    // 包含已过滤或未导出的字段
}

type RWMutex

RWMutex 是读写互斥锁。该锁可以由任意数量的读者持有，也可以由单个写者持有。RWMutex 的零值是一把未锁定的锁。

RWMutex 首次使用后不得复制。

如果一个或多个读者已持有锁，此时某个 goroutine 调用 RWMutex.Lock，那么并发调用 RWMutex.RLock 会阻塞，直到该写者获得并释放锁，以确保写者最终能够获得锁。注意，这意味着不能递归获取读锁。不能将 RWMutex.RLock 升级为 RWMutex.Lock，也不能将 RWMutex.Lock 降级为 RWMutex.RLock。

按照 Go 内存模型的术语，对于任意 n < m，第 n 次 RWMutex.Unlock 调用“同步先于”第 m 次 Lock 调用，与 Mutex 相同。对于任意一次 RLock 调用，都存在一个 n，使第 n 次 Unlock 调用“同步先于”该 RLock 调用，而对应的 RWMutex.RUnlock 调用“同步先于”第 n+1 次 Lock 调用。

不应使用 RLock 递归获取读锁；阻塞中的 Lock 调用会阻止新读者获得锁。参见 RWMutex 类型的文档。

RUnlock 解除一次 RWMutex.RLock 调用所获取的读锁，不影响其他并发读者。如果进入 RUnlock 时 rw 未被读锁锁定，会发生运行时错误。

type WaitGroup

WaitGroup 是计数信号量，通常用于等待一组 goroutine 或任务完成。

通常，主 goroutine 调用 WaitGroup.Go，将各个任务分别放到新的 goroutine 中执行，然后调用 WaitGroup.Wait 等待所有任务完成。例如： 

var wg sync.WaitGroup
wg.Go(task1)
wg.Go(task2)
wg.Wait()

也可以通过 WaitGroup.Add 和 WaitGroup.Done 跟踪任务，而不使用 Go 启动新的 goroutine。

前面的示例可以改写为显式创建 goroutine，并配合 Add 和 Done 使用： 

var wg sync.WaitGroup
wg.Add(1)
go func() {
	defer wg.Done()
	task1()
}()
wg.Add(1)
go func() {
	defer wg.Done()
	task2()
}()
wg.Wait()

这种写法常见于 WaitGroup.Go 引入之前的代码。

WaitGroup 首次使用后不得复制。

    // 包含已过滤或未导出的字段

func (*WaitGroup) Add
					
					
				

				
func (wg *WaitGroup) Add(delta int)

				
Add 将 delta（可以为负数）加到 WaitGroup 的任务计数器上。如果计数器变为零，所有阻塞在 WaitGroup.Wait 上的 goroutine 都会被释放。如果计数器变为负数，Add 会触发 panic。

调用方应优先使用 WaitGroup.Go。

注意，当计数器为零时，以正 delta 调用 Add 必须发生在 Wait 之前。以负 delta 调用 Add，或在计数器大于零时开始的正 delta 调用，可以发生在任意时刻。通常这意味着，应先调用 Add，再执行创建 goroutine 或其他待等待事件的语句。如果重复使用 WaitGroup 来等待多组独立事件，新的 Add 调用必须发生在之前所有 Wait 调用返回之后。参见 WaitGroup 示例。

Done 将 WaitGroup 的任务计数器减一，等价于 Add(-1)。

调用方应优先使用 WaitGroup.Go。

按照 Go 内存模型的术语，Done 调用“同步先于”它所解除阻塞的任何 Wait 调用的返回。
