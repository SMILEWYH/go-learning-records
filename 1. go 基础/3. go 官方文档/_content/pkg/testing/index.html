testing 包为 Go 包的自动化测试提供支持。它与“go test”命令配合使用，自动执行以下形式的函数： 

func TestXxx(*testing.T)

其中 Xxx 不能以小写字母开头。函数名用于标识该测试。

在这些函数内，使用 T.Error、T.Fail 或相关方法报告失败。

要编写新的测试套件，请创建一个包含上述 TestXxx 函数的文件，并将文件名设为以“_test.go”结尾。正常构建包时不会包含该文件，运行“go test”命令时才会包含它。

测试文件可以与被测试代码位于同一个包中，也可以位于名称带“_test”后缀的对应包中。

如果测试文件位于同一个包中，就可以引用该包中的未导出标识符，如下例所示： 

package abs

import "testing"

func TestAbs(t *testing.T) {
    got := abs(-1)
    if got != 1 {
        t.Errorf("abs(-1) = %d; want 1", got)
    }
}

如果文件位于单独的“_test”包中，就必须显式导入被测试的包，并且只能使用其导出标识符。这称为“黑盒”测试。 

package abs_test

import (
	"testing"

	"path_to_pkg/abs"
)

func TestAbs(t *testing.T) {
    got := abs.Abs(-1)
    if got != 1 {
        t.Errorf("Abs(-1) = %d; want 1", got)
    }
}

更多细节，请运行 go help test 和 go help testflag。

基准测试

以下形式的函数 

func BenchmarkXxx(*testing.B)

被视为基准测试，在“go test”命令指定 -bench 标志时执行。基准测试按顺序运行。

测试标志的说明参见 go help testflag。

一个基准测试函数示例如下： 

func BenchmarkRandInt(b *testing.B) {
    for b.Loop() {
        rand.Int()
    }
}

以下输出 

BenchmarkRandInt-8   	68453040	        17.8 ns/op

表示循环体运行了 68453040 次，每次循环耗时 17.8 ns。

只对循环体计时，因此基准测试可以在调用 b.Loop 前进行开销较大的准备工作，这些工作不会计入基准测试测量结果： 

func BenchmarkBigLen(b *testing.B) {
    big := NewBig()
    for b.Loop() {
        big.Len()
    }
}

如果基准测试需要测量并行场景下的性能，可以使用 RunParallel 辅助函数；这类基准测试通常与 go test -cpu 标志配合使用： 

func BenchmarkTemplateParallel(b *testing.B) {
    templ := template.Must(template.New("test").Parse("Hello, {{.}}!"))
    b.RunParallel(func(pb *testing.PB) {
        var buf bytes.Buffer
        for pb.Next() {
            buf.Reset()
            templ.Execute(&buf, "World")
        }
    })
}

基准测试结果格式的详细规范见 https://go.dev/design/14313-benchmark-format。

golang.org/x/perf/cmd 提供处理基准测试结果的标准工具。其中，golang.org/x/perf/cmd/benchstat 可进行具有统计可靠性的 A/B 比较。

b.N 风格的基准测试

在引入 B.Loop 之前，基准测试使用 B.N 编写，风格有所不同。例如： 

func BenchmarkRandInt(b *testing.B) {
    for range b.N {
        rand.Int()
    }
}

采用这种写法时，基准测试函数必须将目标代码运行 b.N 次。测试函数会被调用多次，并调整 b.N，直到单次函数执行持续足够长的时间，能够可靠计时。这也意味着循环前的准备工作可能执行多次。

如果基准测试在运行前需要开销较大的准备工作，应显式重置计时器： 

func BenchmarkBigLen(b *testing.B) {
    big := NewBig()
    b.ResetTimer()
    for range b.N {
        big.Len()
    }
}

新的基准测试应优先使用 B.Loop，它更稳健，也更高效。

示例

本包还会运行和验证示例代码。示例函数可以在结尾包含以“Output:”开头的行注释；运行测试时，会将该注释与函数的标准输出比较，忽略首尾空白。示例函数的例子如下： 

func ExampleHello() {
    fmt.Println("hello")
    // Output: hello
}

func ExampleSalutations() {
    fmt.Println("hello, and")
    fmt.Println("goodbye")
    // Output:
    // hello, and
    // goodbye
}

注释前缀“Unordered output:”类似于“Output:”，但允许输出行以任意顺序匹配： 

func ExamplePerm() {
    for _, value := range Perm(5) {
        fmt.Println(value)
    }
    // Unordered output: 4
    // 2
    // 1
    // 3
    // 0
}

没有输出注释的示例函数只编译，不执行。

分别为包、函数 F、类型 T 和类型 T 的方法 M 声明示例时，命名约定如下： 

func Example() { ... }
func ExampleF() { ... }
func ExampleT() { ... }
func ExampleT_M() { ... }

可以通过在名称后添加不同后缀，为同一个包、类型、函数或方法提供多个示例函数。后缀必须以小写字母开头。 

func Example_suffix() { ... }
func ExampleF_suffix() { ... }
func ExampleT_suffix() { ... }
func ExampleT_M_suffix() { ... }

如果测试文件只包含一个示例函数，至少还包含一个其他函数、类型、变量或常量声明，并且不包含测试函数或基准测试函数，则整个测试文件都会作为示例展示。

模糊测试

“go test”和 testing 包支持模糊测试：通过随机生成输入并调用函数，发现单元测试未预料到的缺陷。

以下形式的函数 

func FuzzXxx(*testing.F)

被视为模糊测试。

例如： 

func FuzzHex(f *testing.F) {
  for _, seed := range [][]byte{{}, {0}, {9}, {0xa}, {0xf}, {1, 2, 3, 4}} {
    f.Add(seed)
  }
  f.Fuzz(func(t *testing.T, in []byte) {
    enc := hex.EncodeToString(in)
    out, err := hex.DecodeString(enc)
    if err != nil {
      t.Fatalf("%v: decode: %v", in, err)
    }
    if !bytes.Equal(in, out) {
      t.Fatalf("%v: not equal after round trip: %v", in, out)
    }
  })
}

模糊测试维护一个种子语料库，即一组默认运行、也可用于生成新输入的输入数据。可以调用 F.Add 注册种子输入，或将文件存放在包含模糊测试的包中的 testdata/fuzz/<Name> 目录下，其中 <Name> 是模糊测试名称。种子输入不是必需的，但提供一组体积小、代码覆盖良好的种子输入，可以帮助模糊测试引擎更高效地发现缺陷。这些种子输入也可以作为模糊测试所发现缺陷的回归测试。

在模糊测试中传给 F.Fuzz 的函数称为模糊测试目标。目标函数必须先接受一个 *T 参数，后跟一个或多个用于随机输入的参数。传给 F.Add 的实参类型必须与这些参数的类型完全相同。目标函数可以像普通测试一样报告问题：调用 T.Fail，或调用 T.Error、T.Fatal 等内部会调用 Fail 的方法，也可以触发 panic。

启用模糊测试时（将 -fuzz 标志设为匹配某个模糊测试的正则表达式），引擎会反复随机修改种子输入，生成参数并调用目标函数。在支持的平台上，“go test”会在编译测试可执行文件时插入模糊测试覆盖率探针。引擎利用这些探针发现并缓存能扩大覆盖范围的输入，以提高发现缺陷的概率。如果目标函数针对某个输入失败，引擎会将导致失败的输入写入包目录下 testdata/fuzz/<Name> 中的文件。该文件以后会作为种子输入。如果无法写入此位置（例如目录只读），则改为写入构建缓存中的模糊测试缓存目录。

禁用模糊测试时，会使用通过 F.Add 注册的种子输入，以及 testdata/fuzz/<Name> 中的种子输入调用目标函数。在这种模式下，模糊测试与普通测试非常相似，只是用 F.Fuzz 而非 T.Run 启动子测试。

模糊测试文档参见 https://go.dev/doc/fuzz。

跳过测试

可以在运行时调用 T.Skip 或 B.Skip，跳过测试或基准测试： 

func TestTimeConsuming(t *testing.T) {
    if testing.Short() {
        t.Skip("skipping test in short mode.")
    }
    ...
}

如果模糊测试目标收到无效输入，但该输入不应被视为测试失败，可以使用 T.Skip。例如： 

func FuzzJSONMarshaling(f *testing.F) {
    f.Fuzz(func(t *testing.T, b []byte) {
        var v interface{}
        if err := json.Unmarshal(b, &v); err != nil {
            t.Skip()
        }
        if _, err := json.Marshal(v); err != nil {
            t.Errorf("Marshal: %v", err)
        }
    })
}

子测试和子基准测试

T.Run 和 B.Run 方法允许定义子测试和子基准测试，无需为每个测试单独定义函数。这支持表驱动的基准测试和分层测试等用法，也提供了共享准备与清理代码的方式： 

func TestFoo(t *testing.T) {
    // <准备代码>
    t.Run("A=1", func(t *testing.T) { ... })
    t.Run("A=2", func(t *testing.T) { ... })
    t.Run("B=1", func(t *testing.T) { ... })
    // <清理代码>
}

每个子测试和子基准测试都有唯一名称：由顶层测试名称与传给 Run 的名称序列拼接而成，以斜杠分隔，必要时在末尾添加序号以消除歧义。

命令行标志 -run、-bench 和 -fuzz 的实参是未限定首尾位置的正则表达式，用于匹配测试名称。对于名称由多个斜杠分隔部分组成的测试（例如子测试），实参本身也以斜杠分隔，各表达式依次匹配名称中的各个部分。由于不限定首尾位置，空表达式匹配任意字符串。例如，以下将“匹配”理解为“名称包含”： 

go test -run ''        # Run all tests.
go test -run Foo       # Run top-level tests matching "Foo", such as "TestFooBar".
go test -run Foo/A=    # For top-level tests matching "Foo", run subtests matching "A=".
go test -run /A=1      # For all top-level tests, run subtests matching "A=1".
go test -fuzz FuzzFoo  # Fuzz the target matching "FuzzFoo"

-run 实参也可用于运行种子语料库中的某个特定输入，以便调试。例如： 

go test -run=FuzzFoo/9ddb952d9814

可以同时设置 -fuzz 和 -run 标志，以便对某个目标进行模糊测试，同时跳过所有其他测试。

子测试也可以用于控制并行执行。父测试只有在所有子测试完成后才会完成。在本例中，所有子测试彼此并行运行，但只与彼此并行，不受可能定义的其他顶层测试影响： 

func TestGroupedParallel(t *testing.T) {
    for _, tc := range tests {
        t.Run(tc.Name, func(t *testing.T) {
            t.Parallel()
            ...
        })
    }
}

Run 会等待并行子测试完成后才返回，因此可以在一组并行测试完成后进行清理： 

func TestTeardownParallel(t *testing.T) {
    // 此 Run 会等所有并行测试完成后才返回。
    t.Run("group", func(t *testing.T) {
        t.Run("Test1", parallelTest1)
        t.Run("Test2", parallelTest2)
        t.Run("Test3", parallelTest3)
    })
    // <清理代码>
}

主入口

有时测试或基准测试程序需要在执行前后进行额外的准备或清理，有时还需要控制哪些代码在主线程上运行。为支持这些及其他场景，如果测试文件包含以下函数： 

func TestMain(m *testing.M)

生成的测试程序就会调用 TestMain(m)，而不是直接运行测试或基准测试。TestMain 在主 goroutine 中运行，可以在调用 m.Run 前后执行所需的准备和清理工作。m.Run 返回一个退出码，可以传给 os.Exit。如果 TestMain 返回，测试包装程序会自行将 m.Run 的结果传给 os.Exit。

调用 TestMain 时，flag.Parse 尚未运行。如果 TestMain 依赖命令行标志，包括 testing 包的标志，就应显式调用 flag.Parse。测试或基准测试函数开始运行时，命令行标志一定已经解析完毕。

一个简单的 TestMain 实现如下： 

func TestMain(m *testing.M) {
	// 如果 TestMain 使用命令行参数，此处应调用 flag.Parse()
	m.Run()
}

TestMain 是底层原语；普通测试需求通常不需要它，使用常规测试函数即可。

func AllocsPerRun 1.1 

func AllocsPerRun(runs int, f func()) (avg float64)

AllocsPerRun 返回调用 f 时的平均内存分配次数。虽然返回值类型为 float64，但其值始终是整数。

为计算分配次数，函数会先运行一次作为预热，然后测量指定运行次数内的平均分配次数并返回。

AllocsPerRun 在测量期间将 runtime.GOMAXPROCS 设为 1，并在返回前恢复原值。

func CoverMode() string

CoverMode 报告测试覆盖率模式的设置值，可能为“set”、“count”或“atomic”。如果未启用测试覆盖率，返回空字符串。

func Coverage 1.4 

func Coverage() float64

Coverage 返回当前代码覆盖率，取值范围为 [0, 1]。如果未启用覆盖率，返回 0。

顺序运行大量测试用例时，在每个用例之后检查 Coverage，有助于识别哪些用例覆盖了新的代码路径。但它不能替代“go test -cover”和“go tool cover”生成的报告。

func Init 1.13 

func Init()

Init 注册测试标志。“go test”命令会在运行测试函数前自动注册这些标志，因此只有在不使用“go test”而直接调用 Benchmark 等函数时，才需要调用 Init。

type B

B 是传给基准测试函数的类型，用于管理基准测试计时并控制迭代次数。

基准测试在其 Benchmark 函数返回，或调用 B.FailNow、B.Fatal、B.Fatalf、B.SkipNow、B.Skip、B.Skipf 中任一方法时结束。这些方法只能由运行 Benchmark 函数的 goroutine 调用。其他报告方法，例如 B.Log 和 B.Error 的各种形式，可以由多个 goroutine 同时调用。

func (*B) Loop 1.24 

func (b *B) Loop() bool

只要基准测试应继续运行，Loop 就返回 true。

典型的基准测试结构如下： 

func Benchmark(b *testing.B) {
	... setup ...
	for b.Loop() {
		... code to measure ...
	}
	... cleanup ...
}

Loop 在基准测试中首次被调用时会重置计时器，因此基准测试循环开始之前的准备工作不计入测量结果。同样，返回 false 时会停止计时器，因此清理代码也不计入测量。

在“for b.Loop() { ... }”的循环体内，函数调用的实参、返回结果，以及循环中被赋值的变量都会保持存活，以防编译器将整个循环体优化掉。目前，这通过编译器转换实现：对这些变量插入 runtime.KeepAlive 内建调用。它只适用于语法上位于循环花括号之间的语句，而且循环条件必须严格写作“b.Loop()”。

Loop 返回 false 后，b.N 包含实际运行的总迭代次数，因此基准测试可以用 b.N 计算其他平均指标。

在引入 Loop 之前，基准测试需要包含从 0 到 b.N 的显式循环。基准测试应使用 Loop 或循环到 b.N，不能两者同时使用。Loop 更自动地管理计时器，每次测量只运行一次基准测试函数；基于 b.N 的测试则需要多次运行测试函数及相关的准备和清理代码。

func (*B) RunParallel
					
					1.3
