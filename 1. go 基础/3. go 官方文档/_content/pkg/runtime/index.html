runtime 包包含与 Go 运行时系统交互的操作，例如控制 goroutine 的函数。它还包含 reflect 包使用的底层类型信息；有关运行时类型系统的可编程接口，请参阅 reflect 文档。

环境变量

以下环境变量（根据宿主操作系统采用 $name 或 %name% 形式）控制 Go 程序的运行时行为。其含义和用法可能随版本变化。

GOGC 变量设置垃圾回收的初始目标百分比。新分配数据与上一次回收后剩余存活数据的比值达到该百分比时，触发回收。默认值为 GOGC=100。设置 GOGC=off 会完全禁用垃圾回收器。runtime/debug.SetGCPercent 允许在运行时修改该百分比。

GOMEMLIMIT 变量为运行时设置软内存限制。此限制包括 Go 堆及运行时管理的全部其他内存，不包括外部内存来源，例如二进制文件自身的映射、其他语言管理的内存，以及操作系统为 Go 程序持有的内存。GOMEMLIMIT 是以字节为单位的数值，可以带可选的单位后缀。支持的后缀包括 B、KiB、MiB、GiB 和 TiB，表示 IEC 80000-13 标准定义的字节数量，即以 2 的幂为基数：KiB 表示 2^10 字节，MiB 表示 2^20 字节，依此类推。默认设置为 math.MaxInt64，相当于禁用内存限制。runtime/debug.SetMemoryLimit 允许在运行时修改此限制。

GODEBUG 变量控制运行时内部的调试变量。它是用逗号分隔的 name=val 对列表，用于设置以下命名变量：

clobberfree：设置 clobberfree=1 会使垃圾回收器在释放对象时，用无效内容覆盖对象的内存内容。

cpu.*：cpu.all=off 禁用所有可选指令集扩展。
cpu.extension=off 禁用指定指令集扩展中的指令。
extension 是 internal/cpu 包中列出的指令集扩展的小写名称，例如 sse41 或 avx。
例如，cpu.avx=off 会禁用运行时检测，从而禁用 AVX 指令。

cgocheck：设置 cgocheck=0 会禁用所有针对包通过 cgo 向非 Go 代码错误传递 Go 指针的检查。
设置 cgocheck=1（默认值）会启用开销较小的检查，但可能漏掉某些错误。
可以使用 GOEXPERIMENT 启用更全面但较慢的 cgocheck 模式（需要重新构建），
详见 https://pkg.go.dev/internal/goexperiment。

checkfinalizers：设置 checkfinalizers=1 会使垃圾回收器执行多次局部、非并行的全局暂停（STW）回收，
以发现终结器和清理函数的常见问题，例如
https://go.dev/doc/gc-guide#Finalizers_cleanups_and_weak_pointers 中列出的问题。
如果发现潜在问题，程序会终止，并给出所有潜在问题、相关值，以及这些值的终结器和清理函数列表，
其中包含它们的创建位置。它还会增加对微小内存块的跟踪，以帮助诊断相关问题。
局部回收中执行的分析是保守的。特别是，只要存在从清理函数、清理参数或终结器函数
返回原始对象的任意引用路径，就会将其标记为潜在问题，即使该路径可能在之后执行时被切断
（不过，不推荐这种模式）。此模式还会在每个 GC 周期向标准错误输出一行信息，
给出终结器和清理函数队列的长度。此模式的输出行以 "checkfinalizers:" 开头。

decoratemappings：控制 Go 运行时是否为操作系统的匿名内存映射添加用途说明。
这些注释在 /proc/self/maps 和 /proc/self/smaps 中显示为 "[anon: Go: ...]"。
此设置仅用于 Linux。在 Go 1.25 中，默认值为 `decoratemappings=1`，即启用注释。
使用 `decoratemappings=0` 可恢复 Go 1.25 之前的行为。

disablethp：在 Linux 上设置 disablethp=1 会禁用堆的透明大页。
在其他平台上无效。disablethp 用于兼容 Go 1.21 之前的版本；Go 1.21 不再规避
可能导致内存显著过量使用的某项 Linux 内核默认设置。参见 https://go.dev/issue/64332。
此设置将在未来版本中移除，因此运维人员应在那之前根据需要调整 Linux 配置。
参见 https://go.dev/doc/gc-guide#Linux_transparent_huge_pages。

dontfreezetheworld：默认情况下，致命 panic 或 throw 开始时会“冻结整个程序”，
抢占所有线程并停止所有正在运行的 goroutine，以便获取所有 goroutine 的调用栈，
并使它们的状态保持在接近发生 panic 的时刻。
设置 dontfreezetheworld=1 会禁用这种抢占，允许 goroutine 在处理 panic 期间继续执行。
注意，自然进入调度器的 goroutine 仍然会停止。
这有助于调试运行时调度器，因为 freezetheworld 会扰动调度器状态，从而可能掩盖问题。

efence：设置 efence=1 会使分配器进入特殊模式：每个对象都分配在独立的内存页上，
且地址永不复用。

gccheckmark：设置 gccheckmark=1 会在全局暂停期间执行第二轮标记，
以验证垃圾回收器的并发标记阶段。
如果第二轮发现并发标记遗漏的可达对象，垃圾回收器就会触发 panic。

gcpacertrace：设置 gcpacertrace=1 会使垃圾回收器打印并发节奏控制器的内部状态信息。

gcshrinkstackoff：设置 gcshrinkstackoff=1 会禁止将 goroutine 移到更小的栈上。
在此模式下，goroutine 的栈只能增长。

gcstoptheworld：设置 gcstoptheworld=1 会禁用并发垃圾回收，使每次垃圾回收都全局暂停。
设置 gcstoptheworld=2 还会禁用垃圾回收结束后的并发清扫。

gctrace：设置 gctrace=1 会使垃圾回收器在每次回收时向标准错误输出一行信息，
概述回收的内存量和暂停时长。此行的格式可能发生变化。
下面还列出了各字段对应的 runtime/metrics 指标。目前的格式为：
	gc # @#s #%: #+#+# ms clock, #+#/#/#+# ms cpu, #->#-># MB, # MB goal, # MB stacks, #MB globals, # P
各字段含义如下：
	gc #         GC 编号，每次 GC 递增
	@#s          从程序启动起经过的秒数
	#%           从程序启动起花费在 GC 上的时间百分比
	#+...+#      各 GC 阶段的墙上时钟时间／CPU 时间
	#->#-># MB   GC 开始时、结束时的堆大小，以及存活堆大小，后者对应 /gc/scan/heap:bytes
	# MB goal    目标堆大小，对应 /gc/heap/goal:bytes
	# MB stacks  估算的可扫描栈大小，对应 /gc/scan/stack:bytes
	# MB globals 可扫描全局数据的大小，对应 /gc/scan/globals:bytes
	# P          使用的处理器数，对应 /sched/gomaxprocs:threads
这些阶段依次为：全局暂停（STW）的清扫终止、并发标记与扫描，以及 STW 的标记终止。
标记／扫描阶段的 CPU 时间进一步分为辅助时间（随内存分配同步执行的 GC）、后台 GC 时间和空闲 GC 时间。
如果该行以 "(forced)" 结尾，则这次 GC 是由 runtime.GC() 调用强制触发的。

harddecommit：设置 harddecommit=1 会在将内存归还操作系统时，同时移除其访问权限。
这是 Windows 上唯一的运行模式，但也有助于调试其他平台上的内存清退器相关问题。
目前此设置仅支持 Linux。

inittrace：设置 inittrace=1 会使运行时为每个执行初始化工作的包向标准错误输出一行信息，
概述执行时间和内存分配情况。对于加载插件时执行的初始化，以及既没有用户定义的初始化工作、
也没有编译器生成的初始化工作的包，不会打印信息。此行的格式可能发生变化。目前的格式为：
	init # @#ms, # ms clock, # bytes, # allocs
各字段含义如下：
	init #      包名
	@# ms       初始化开始时距程序启动的毫秒数
	# clock     包初始化工作的墙上时钟时间
	# bytes     在堆上分配的内存字节数
	# allocs    堆分配次数

madvdontneed：在 Linux 上设置 madvdontneed=0，会在向内核归还内存时使用 MADV_FREE，
而不是 MADV_DONTNEED。这样效率更高，但 RSS 数值只有在操作系统面临内存压力时才会下降。
在 BSD 系统及 Illumos/Solaris 上，设置 madvdontneed=1 会使用 MADV_DONTNEED，
而不是 MADV_FREE。这样效率较低，但 RSS 数值会更快下降。

memprofilerate：设置 memprofilerate=X 会更新 runtime.MemProfileRate 的值。
设为 0 时会禁用内存性能分析。默认值请参见 MemProfileRate 的说明。

profstackdepth：profstackdepth=128（默认值）将除 CPU 性能分析器之外的所有 pprof 性能分析器
使用的最大栈深度设为 128 帧。超过该限制的栈回溯会从叶帧开始保留，并截断到此限制。
将 profstackdepth 设为大于 1024 的任意值，都会静默使用默认上限 1024。
Go 的未来版本可能移除此限制，并将 profstackdepth 扩展到 CPU 性能分析器和执行跟踪器。

panicnil：设置 panicnil=1 会禁用使用 nil 接口值或无类型 nil 调用 panic 时产生的运行时错误。

invalidptr：invalidptr=1（默认值）会使垃圾回收器和栈复制器在指针类型的位置发现无效指针值
（例如 1）时让程序崩溃。设置 invalidptr=0 会禁用此检查。
这只能作为诊断错误代码的临时变通办法。真正的修复方法是不要在指针类型的位置存储整数。

sbrk：设置 sbrk=1 会将内存分配器和垃圾回收器替换为简单分配器；
该分配器从操作系统获取内存，并且永不回收任何内存。

scavtrace：设置 scavtrace=1 会使运行时大约在每个 GC 周期向标准错误输出一行信息，
概述内存清退器完成的工作量、归还给操作系统的内存总量，以及物理内存利用率估计值。
此行的格式可能发生变化，目前为：
	scav # KiB work (bg), # KiB work (eager), # KiB total, #% util
各字段含义如下：
	# KiB work (bg)    自上一行以来在后台归还给操作系统的内存量
	# KiB work (eager) 自上一行以来主动归还给操作系统的内存量
	# KiB now          当前已归还给操作系统的地址空间总量
	#% util            尚未清退的全部堆内存中正在使用的比例
如果该行以 "(forced)" 结尾，则本次内存清退由 debug.FreeOSMemory() 调用强制触发。

scheddetail：设置 schedtrace=X 和 scheddetail=1，会使调度器每隔 X 毫秒输出详细的多行信息，
描述调度器、处理器、线程和 goroutine 的状态。

schedtrace：设置 schedtrace=X 会使调度器每隔 X 毫秒向标准错误输出一行信息，概述调度器状态。

tracebackancestors：设置 tracebackancestors=N 会为栈回溯增加创建 goroutine 时的调用栈，
其中 N 限制要报告的祖先 goroutine 数量。这也会扩展 runtime.Stack 返回的信息。
将 N 设为 0 时，不报告祖先信息。

tracefpunwindoff：设置 tracefpunwindoff=1 会强制执行跟踪器以及阻塞和互斥锁性能分析器
使用运行时默认的栈展开器，而不是通过帧指针展开栈。这会增加开销，
但可以用作临时变通办法，或用于调试帧指针栈展开引起的意外性能退化。

traceadvanceperiod：相邻跟踪代之间的近似时间间隔，单位为纳秒。
仅适用于使用 GOEXPERIMENT=exectracer2 构建的程序。主要用于执行跟踪器的测试和调试。

tracecheckstackownership：设置 tracecheckstackownership=1 会启用执行跟踪器中的调试检查，
在获取栈回溯之前再次检查栈的归属。

asyncpreemptoff：asyncpreemptoff=1 会禁用基于信号的 goroutine 异步抢占。
这会使某些循环在较长时间内无法被抢占，可能延迟 GC 和 goroutine 调度。
这有助于调试 GC 问题，因为它也会禁用针对被异步抢占的 goroutine 所使用的保守栈扫描。

net 和 net/http 包也使用 GODEBUG 中的调试变量。详情请参阅这些包的文档。

GOMAXPROCS 变量限制能够同时执行用户级 Go 代码的操作系统线程数量。代表 Go 代码阻塞在系统调用中的线程数量没有上限，也不计入 GOMAXPROCS 限制。本包的 GOMAXPROCS 函数可查询和修改此限制。

GORACE 变量为使用 -race 构建的程序配置竞态检测器。详情请参阅竞态检测器文章。

GOTRACEBACK 变量控制 Go 程序因未恢复的 panic 或意外运行时状况而失败时生成的输出量。默认情况下，失败时输出当前 goroutine 的栈轨迹，省略运行时系统内部函数，然后以退出码 2 退出。如果没有当前 goroutine，或失败发生在运行时内部，则输出所有 goroutine 的栈轨迹。GOTRACEBACK=none 完全省略 goroutine 栈轨迹。GOTRACEBACK=single（默认值）采用上述行为。GOTRACEBACK=all 增加所有用户创建的 goroutine 的栈轨迹。GOTRACEBACK=system 类似于 all，但还包含运行时函数的栈帧，并显示运行时内部创建的 goroutine。GOTRACEBACK=crash 类似于 system，但以操作系统特定方式崩溃，而非正常退出。例如，在 Unix 系统上，崩溃会引发 SIGABRT，触发核心转储。GOTRACEBACK=wer 类似于 crash，但不禁用 Windows 错误报告（WER）。出于历史原因，GOTRACEBACK 的取值 0、1、2 分别是 none、all、system 的同义写法。runtime/debug.SetTraceback 函数允许在运行时增加输出量，但不能将其降低到环境变量指定的程度以下。

GOARCH、GOOS、GOPATH 和 GOROOT 构成其余 Go 环境变量。它们影响 Go 程序的构建（参见 cmd/go 和 go/build）。GOARCH、GOOS 和 GOROOT 在编译时记录，并通过本包的常量或函数提供，但不影响运行时系统的执行。

安全性

在 Unix 平台上，当二进制文件设置了 setuid/setgid，或以类似 setuid/setgid 的属性执行时，Go 运行时系统会采用略有不同的行为，以防止危险行为。在 Linux 上，通过检查辅助向量中的 AT_SECURE 标志判断；在 BSD 和 Solaris/Illumos 上，通过 issetugid 系统调用判断；在 AIX 上，通过检查 uid/gid 是否与有效 uid/gid 一致判断。

当运行时确定二进制文件具有类似 setuid/setgid 的属性时，主要做两件事：

  • 将 GOTRACEBACK 环境变量的值设置为 'none'。
  • 收到终止程序的信号，或遇到原本会覆盖 GOTRACEBACK 值的不可恢复 panic 时，省略 goroutine 栈、寄存器和其他内存相关信息。

此外，在 Unix 平台上，Go 运行时会自动检查标准输入输出文件描述符（0、1、2）是否打开。如果其中任何一个已关闭，则打开它并使其指向 /dev/null。

func GOMAXPROCS 

func GOMAXPROCS(n int) int

GOMAXPROCS 设置可同时执行的 CPU 数量上限，并返回先前设置。如果 n < 1，则不修改当前设置。

默认值

如果 GOMAXPROCS 环境变量设为正整数，GOMAXPROCS 默认采用该值。

否则，Go 运行时综合以下信息选择合适的默认值：

  • 机器的逻辑 CPU 数量；
  • 进程的 CPU 亲和性掩码；
  • 以及在 Linux 上，基于 cgroup CPU 配额得到的进程平均 CPU 吞吐量上限（如果有）。

如果设置了 GODEBUG=containermaxprocs=0，且未通过环境变量设置 GOMAXPROCS，则 GOMAXPROCS 改为默认取 runtime.NumCPU 的值。注意，对于语言版本 1.24 及以下，GODEBUG=containermaxprocs=0 是默认设置。

更新

Go 运行时根据逻辑 CPU 总数、CPU 亲和性掩码或 cgroup 配额的变化，定期更新默认值。通过 GOMAXPROCS 环境变量或调用 GOMAXPROCS 设置自定义值，会禁用自动更新。调用 SetDefaultGOMAXPROCS 可以恢复默认值和自动更新。

如果设置了 GODEBUG=updatemaxprocs=0，Go 运行时不自动更新 GOMAXPROCS。注意，对于语言版本 1.24 及以下，GODEBUG=updatemaxprocs=0 是默认设置。

兼容性

注意，随着调度器改进，GOMAXPROCS 的默认行为可能变化，尤其是下面的实现细节。

实现细节

通过 cgroup 计算默认 GOMAXPROCS 时，Go 运行时将“平均 CPU 吞吐量上限”计算为 cgroup CPU 配额除以周期。在 cgroup v2 中，这些值来自 cpu.max 文件；在 cgroup v1 中，分别来自 cpu.cfs_quota_us 和 cpu.cfs_period_us。对于允许配置 CPU 限制的容器运行时，该值通常对应“CPU limit”选项，而非“CPU request”。

Go 运行时通常将逻辑 CPU 数量、CPU 亲和性掩码中的 CPU 数量和 cgroup CPU 吞吐量上限三者的最小值作为默认 GOMAXPROCS。不过，除非逻辑 CPU 数量或 CPU 亲和性掩码中的 CPU 数量小于 2，否则它绝不会将 GOMAXPROCS 设为小于 2。

如果 cgroup CPU 吞吐量上限不是整数，Go 运行时会向上取整。

GOMAXPROCS 每秒最多更新一次；应用程序空闲时，更新频率可能更低。

func SetCgoTraceback 1.7 

func SetCgoTraceback(version int, traceback, context, symbolizer unsafe.Pointer)

SetCgoTraceback 记录三个 C 函数，用于从 C 代码收集栈回溯信息，并将其转换为符号信息。在为使用 cgo 的程序输出栈轨迹时，会使用这些函数。

traceback 和 context 函数可能从信号处理器调用，因此只能使用异步信号安全的函数。symbolizer 函数可能在程序崩溃过程中调用，因此必须谨慎使用内存。这些函数都不能回调 Go。

context 函数调用时只接收一个参数，即指向以下结构体的指针：

struct {
	Context uintptr
}

用 C 语法表示，该结构体为：

struct {
	uintptr_t Context;
};

如果 Context 字段为 0，表示正在调用 context 函数记录当前的栈回溯上下文。它应将稍后生成栈轨迹所需的当前执行位置信息记录到 Context 字段中，可能包括栈指针和 PC。在这种情况下，context 函数会从 C 代码调用。

如果 Context 字段非 0，它就是之前调用 context 函数返回的值。当该上下文不再需要时，即 Go 代码正要返回其 C 代码调用方时，会发生这种调用。这样 context 函数便可释放所有关联资源。

虽然 context 函数每次调用时都记录完整栈轨迹、再由 traceback 函数简单复制出来也是正确的，但典型程序中 context 函数可能被调用许多次，却从未为相应上下文记录栈回溯。每次调用 context 函数都记录完整栈轨迹，通常效率不高。

traceback 函数调用时只接收一个参数，即指向以下结构体的指针：

struct {
	Context    uintptr
	SigContext uintptr
	Buf        *uintptr
	Max        uintptr
}

用 C 语法表示，该结构体为：

struct {
	uintptr_t  Context;
	uintptr_t  SigContext;
	uintptr_t* Buf;
	uintptr_t  Max;
};

若要从程序当前执行点收集栈回溯，Context 字段为零。在这种情况下，traceback 函数会从 C 代码调用。

否则，Context 是之前调用 context 函数返回的值。traceback 函数应从保存的程序执行点收集栈轨迹。调用 traceback 的执行线程可能不同于记录上下文的线程，但只会在确定上下文仍然有效且不会改变时这样调用。它也可能在记录上下文的同一线程中、更深的调用栈位置被调用。traceback 函数可能多次收到相同的 Context 值；如果可能，通常应在首次处理特定上下文值时缓存结果。

在 Unix 系统上，如果 traceback 函数从信号处理器调用，SigContext 就是传给信号处理器的信号上下文参数（将 C 的 ucontext_t* 转换为 uintptr_t）。它可用于从信号发生的位置开始回溯。如果 traceback 函数并非从信号处理器调用，SigContext 为零。

Buf 是存储栈回溯信息的位置。应在其中存储 PC 值，使 Buf[0] 为调用方的 PC，Buf[1] 为该函数调用方的 PC，依此类推。Max 是最多可存储的条目数。函数应存入零，表示到达栈顶，或者调用方位于另一个栈上，通常是 Go 栈。

与 runtime.Callers 不同，返回的 PC 值在传给 symbolizer 函数时，应返回调用指令所在的文件和行号。不需要也不应再额外减去偏移量。

在所有平台上，当 Go 到 C 再到 Go 的调用请求栈轨迹时，都会调用 traceback 函数。在 linux/amd64、linux/ppc64le、linux/arm64 和 freebsd/amd64 上，正在执行 cgo 调用的线程收到信号时，也会调用 traceback 函数。traceback 函数不应假定自己何时被调用，因为未来的 Go 版本可能增加其他调用时机。

symbolizer 函数调用时只接收一个参数，即指向以下结构体的指针：

struct {
	PC      uintptr // 要查询信息的程序计数器
	File    *byte   // 文件名（以 NUL 结尾）
	Lineno  uintptr // 行号
	Func    *byte   // 函数名（以 NUL 结尾）
	Entry   uintptr // 函数入口点
	More    uintptr // 若此 PC 还有更多信息，则设为非零
	Data    uintptr // 运行时不使用此字段，可供函数自行使用
}

用 C 语法表示，该结构体为：

struct {
	uintptr_t PC;
	char*     File;
	uintptr_t Lineno;
	char*     Func;
	uintptr_t Entry;
	uintptr_t More;
	uintptr_t Data;
};

PC 字段是调用 traceback 函数返回的某个值。

对于特定栈回溯的第一次调用，除 PC 外的所有字段都为 0。函数应尽可能填充其他字段；信息不可用时，将其设为 0 或 nil。Data 字段可用于跨调用保存有用信息。如果该 PC 还有更多信息，应将 More 字段设为非零，否则设为零。如果 More 非零，会使用相同 PC 再次调用此函数，函数可以返回不同信息（这是为内联函数准备的）。如果 More 为零，会使用栈回溯中的下一个 PC 值调用此函数。栈回溯处理完成后，还会将 PC 设为零再调用一次；此时可以释放任何保存的信息。每次调用后，结构体各字段都会保留返回时的值，唯一例外是在 More 为零时 PC 字段会改变。函数不得在调用之间保留此结构体指针的副本。

调用 SetCgoTraceback 时，version 参数表示这些函数预期接收的结构体版本号。目前必须为零。

symbolizer 函数可以为 nil，此时 traceback 函数的结果以数字显示。如果 traceback 函数为 nil，就永远不会调用 symbolizer。context 函数可以为 nil，此时只会在 Context 字段为零的情况下调用 traceback。如果 context 为 nil，则 Go 到 C 再到 Go 的调用不会显示调用栈中 C 部分的栈回溯。

SetCgoTraceback 只应调用一次，最好在 init 函数中调用。

func SetFinalizer 

func SetFinalizer(obj any, finalizer any)

SetFinalizer 将 obj 关联的终结器设置为给定的 finalizer 函数。垃圾回收器发现一个不可达且关联了终结器的内存块时，会清除该关联，并在单独的 goroutine 中运行 finalizer(obj)。这会使 obj 再次变为可达，但此时不再关联终结器。假设没有再次调用 SetFinalizer，下次垃圾回收器发现 obj 不可达时，就会释放 obj。

SetFinalizer(obj, nil) 清除 obj 关联的任何终结器。

新的 Go 代码应考虑改用 AddCleanup，它比 SetFinalizer 更不容易出错。

参数 obj 必须是指向对象的指针，该对象通过调用 new、获取复合字面量地址，或获取局部变量地址来分配。参数 finalizer 必须是只接收一个参数的函数，且 obj 的类型能够赋值给该参数；函数可以有任意返回值，这些返回值会被忽略。如果不满足任一条件，SetFinalizer 可能中止程序。

终结器按依赖顺序运行：如果 A 指向 B，两者都有终结器，且除此之外都不可达，则只运行 A 的终结器；A 释放后，B 的终结器才能运行。如果循环结构包含带终结器的内存块，则不保证该循环被垃圾回收，也不保证终结器运行，因为不存在能够满足依赖关系的执行顺序。

当程序不再能到达 obj 指向的对象后，终结器会被安排在未来某个任意时刻运行。不保证终结器在程序退出前运行，因此它们通常只适合在长期运行的程序中释放与对象关联的非内存资源。例如，当程序丢弃 os.File 而未调用 Close 时，os.File 对象可以通过终结器关闭关联的操作系统文件描述符。但依赖终结器刷新 bufio.Writer 等内存 I/O 缓冲区是错误的，因为程序退出时不保证刷新缓冲区。

如果 *obj 的大小为零字节，不保证终结器运行，因为它可能与内存中的其他零大小对象共享同一地址。参见 https://go.dev/ref/spec#Size_and_alignment_guarantees。

对于在包级变量初始化器中分配的对象，不保证终结器运行。这些对象可能由链接器分配，而不是在堆上分配。

注意，对象不再被引用后，终结器可能在遥远的未来才执行，因此运行时允许采用节省空间的优化，将多个对象批量放入同一个分配槽。如果某个不再被引用的对象始终与被引用对象位于同一批次中，它的终结器可能永远不运行。通常，这种批量分配仅发生在微小（约 16 字节或更小）且不含指针的对象上。

对象一旦不可达，终结器就可能运行。为了正确使用终结器，程序必须确保对象在不再需要之前始终可达。存储在全局变量中的对象，或可以从全局变量沿指针找到的对象，都是可达的。函数参数或接收者可能在函数最后一次使用它的位置之后就变为不可达。要让不可达对象保持可达，应将其传给 KeepAlive，标记函数中该对象必须保持可达的最后位置。

例如，假设 p 指向包含文件描述符 d 的结构体（如 os.File），p 的终结器会关闭该文件描述符，且函数中最后一次使用 p 是调用 syscall.Write(p.d, buf, size)。那么程序一进入 syscall.Write，p 就可能变为不可达。终结器可能立即运行，关闭 p.d，导致 syscall.Write 因写入已关闭的文件描述符而失败（更糟的是，可能写入已被其他 goroutine 打开的完全不同的文件描述符）。为避免此问题，应在 syscall.Write 调用后调用 KeepAlive(p)。

程序的所有终结器由单个 goroutine 顺序执行。如果某个终结器需要长时间运行，应为此启动新的 goroutine。

按照 Go 内存模型的术语，SetFinalizer(x, f) 调用“同步先于”终结器调用 f(x)。但不保证 KeepAlive(x) 或对 x 的其他使用“同步先于” f(x)，因此终结器若需要访问 x 中的可变状态，通常应使用互斥锁或其他同步机制。例如，终结器检查 x 的某个可变字段，而主程序会在 x 不可达、终结器被调用之前不时修改该字段。主程序的修改与终结器的检查必须使用适当同步，例如互斥锁或原子更新，以避免读写竞争。

func AddCleanup 

func AddCleanup[T, S any](ptr *T, cleanup func(S), arg S) Cleanup

AddCleanup 将清理函数附加到 ptr。当 ptr 不再可达后的某个时刻，运行时会在单独的 goroutine 中调用 cleanup(arg)。

典型用法是：ptr 是包装底层资源的对象（例如包装操作系统文件描述符的 File 对象），arg 是底层资源（例如操作系统文件描述符），清理函数释放该资源（例如调用 close 系统调用）。

对 ptr 的限制很少。特别是，可以将多个清理函数附加到同一个指针，或同一次分配内的不同指针。

如果从 cleanup 或 arg 可以到达 ptr，则 ptr 永远不会被回收，清理函数也永远不会运行。为防止这种情况的简单形式，如果 arg 等于 ptr，AddCleanup 会引发 panic。

清理函数的运行顺序未指定。特别是，如果多个对象相互引用，并同时变为不可达，那么它们的清理函数都会具备运行条件，且可以按任意顺序运行。即使这些对象形成循环，这一点也成立。

清理函数与用户创建的 goroutine 并发运行。清理函数之间也可能并发运行，这一点与终结器不同。如果清理函数需要长时间运行，应创建新的 goroutine，以免阻塞其他清理函数的执行。

如果 ptr 同时有清理函数和终结器，那么只有在其终结器已执行、且对象在不再关联终结器的情况下再次变为不可达后，清理函数才会运行。

不总是保证 cleanup(arg) 被调用；特别是，不保证它在程序退出前运行。

如果 T 的大小为零字节，不保证清理函数运行，因为它可能与内存中的其他零大小对象共享同一地址。参见 https://go.dev/ref/spec#Size_and_alignment_guarantees。

对于在包级变量初始化器中分配的对象，不保证清理函数运行。这些对象可能由链接器分配，而不是在堆上分配。

注意，对象不再被引用后，清理函数可能在遥远的未来才执行，因此运行时允许采用节省空间的优化，将多个对象批量放入同一个分配槽。如果某个不再被引用的对象始终与被引用对象位于同一批次中，它的清理函数可能永远不运行。通常，这种批量分配仅发生在微小（约 16 字节或更小）且不含指针的对象上。

对象一旦不可达，清理函数就可能运行。为了正确使用清理函数，程序必须确保在能够安全运行其清理函数之前，对象始终可达。存储在全局变量中的对象，或可以从全局变量沿指针找到的对象，都是可达的。函数参数或接收者可能在函数最后一次使用它的位置之后就变为不可达。要确保清理函数不会过早调用，应在对象必须保持可达的最后位置之后，将它传给 KeepAlive 函数。

type MemStats struct {

    // Alloc 是已分配堆对象的字节数。
    //
    // 这与下面的 HeapAlloc 相同。
    Alloc uint64

    // TotalAlloc 是为堆对象分配的累计字节数。
    //
    // TotalAlloc 随堆对象分配而增加，但
    // 与 Alloc 和 HeapAlloc 不同，它不会在

    //
    // Sys 是下面各个 XSys 字段的总和。它衡量
    // Go 运行时为堆、栈及其他内部数据结构
    // 预留的虚拟地址空间。
    // 在任意给定时刻，可能并非全部虚拟地址空间
    // 都有物理内存支撑，不过一般而言，
    // 这些空间在某个时刻都曾有物理内存支撑。
    Sys uint64

    // Lookups 是运行时执行的指针
    // 查找次数。
    //
    // 它主要用于调试运行时内部实现。
    Lookups uint64

    // Mallocs 是已分配堆对象的累计数量。
    // 存活对象数量为 Mallocs - Frees。
    Mallocs uint64

    // Frees 是已释放堆对象的累计数量。
    Frees uint64

    // HeapAlloc 是已分配堆对象的字节数。
    //
    // “已分配”的堆对象包括全部可达对象，
    // 也包括垃圾回收器尚未释放的
    // 不可达对象。具体而言，HeapAlloc 随堆对象
    // 分配而增加，并在清扫堆、释放
    // 不可达对象时减少。清扫在 GC 周期之间
    // 以增量方式进行，因此这两个过程
    // 同时发生，所以 HeapAlloc 通常
    // 平滑变化（不同于全局暂停式垃圾回收器
    // 常见的锯齿形变化）。
    HeapAlloc uint64

    // HeapSys 是从操作系统获取的堆内存字节数。
    //
    // HeapSys 衡量为堆预留的
    // 虚拟地址空间总量。它包括已预留但尚未使用的
    // 虚拟地址空间，这部分不占物理内存，
    // 通常也较小；还包括曾经使用、后来闲置，
    // 其物理内存已归还给操作系统的
    // 虚拟地址空间（后一部分的大小
    // 参见 HeapReleased）。
    //
    // HeapSys 估算堆曾经达到的最大大小。
    HeapSys uint64

    // HeapIdle 是空闲（未使用）span 中的字节数。
    //
    // 空闲 span 中没有对象。这些 span 可以
    // （也可能已经）归还给操作系统，也可以
    // 复用于堆分配，或复用为
    // 栈内存。
    //
    // HeapIdle 减去 HeapReleased，估算可归还给操作系统
    // 但运行时仍保留的内存量，
    // 使堆增长时不必再向操作系统请求
    // 更多内存。如果该差值显著
    // 大于堆大小，说明最近存活堆的大小
    // 曾出现短暂峰值。
    HeapIdle uint64

    // HeapInuse 是正在使用的 span 中的字节数。
    //
    // 正在使用的 span 至少包含一个对象。这些 span
    // 只能用于其他大小大致相同的
    // 对象。
    //
    // HeapInuse 减去 HeapAlloc，估算已划归
    // 特定大小类别但当前未使用的
    // 内存量。这是碎片量的上界，
    // 不过一般而言，这些内存可以高效
    // 复用。
    HeapInuse uint64

    // HeapReleased 是归还给操作系统的物理内存字节数。
    //
    // 它统计来自空闲 span、已归还给操作系统
    // 且尚未被堆重新获取的堆内存。
    HeapReleased uint64

    // HeapObjects 是已分配的堆对象数量。
    //
    // 与 HeapAlloc 类似，它随对象分配而增加，
    // 并在清扫堆、释放不可达对象时
    // 减少。
    HeapObjects uint64

    // StackInuse 是栈 span 中的字节数。
    //
    // 正在使用的栈 span 至少包含一个栈。这些
    // span 只能用于其他同样大小的栈。
    //
    // 没有 StackIdle，因为未使用的栈 span
    // 会归还给堆（因此计入 HeapIdle）。

    // StackSys 是从操作系统获取的栈内存字节数。
    //
    // StackSys 等于 StackInuse 加上直接从操作系统
    // 获取的操作系统线程栈内存。
    //
    // 在非 cgo 程序中，此指标目前等于 StackInuse，
    // 但不应依赖这一点，其值在将来

    //

    // 和 c-archive 构建模式中的一个栈；其他来自
    // 操作系统的栈（尤其是 C 代码分配的栈）目前不计入。
    // 注意，这也可能在将来改变。
    StackSys uint64

    // MSpanInuse 是已分配 mspan 结构的字节数。
    MSpanInuse uint64

    // MSpanSys 是从操作系统获取的、用于 mspan
    // 结构的内存字节数。
    MSpanSys uint64

    // MCacheInuse 是已分配 mcache 结构的字节数。
    MCacheInuse uint64

    // MCacheSys 是从操作系统获取的、用于

    MCacheSys uint64

    // BuckHashSys 是性能剖析桶哈希表的内存字节数。
    BuckHashSys uint64

    // GCSys 是垃圾回收元数据的内存字节数。
    GCSys uint64 // Go 1.2

    // OtherSys 是运行时各种堆外分配的
    // 内存字节数。
    OtherSys uint64 // Go 1.2

    // NextGC 是下一个 GC 周期的目标堆大小。
    //
    // 垃圾回收器的目标是保持 HeapAlloc ≤ NextGC。
    // 每个 GC 周期结束时，会根据可达数据量和
    // GOGC 的值，计算下一个周期的
    // 目标值。
    NextGC uint64

    // LastGC 是最近一次垃圾回收完成的时间，表示为
    // 自 1970 年（Unix 纪元）以来的纳秒数。

    // PauseTotalNs 是程序启动以来，GC 全局暂停

    //
    // 最近一次暂停位于 PauseNs[(NumGC+255)%256]。
    // 一般而言，PauseNs[N%256] 记录最近一次
    // 编号模 256 为 N%256 的 GC 周期的暂停时长。每个 GC

    EnableGC bool

    DebugGC bool

type Pinner 1.21

Pinner 是一组 Go 对象，每个对象都固定在内存中的某个位置。Pinner.Pin 方法固定一个对象，而 Pinner.Unpin 解除所有已固定对象的固定状态。

Pinner 有两个用途。第一，它允许 C 代码安全地使用未通过 cgo 调用显式传入的 Go 指针。例如，将结构体指针传给 C 函数后，可以安全地访问结构体内部保存的指针。第二，只要对象仍保持固定，即使 cgo 调用已返回，C 内存也可以安全地保留该 Go 指针。

Pinner 会安排在自身变为不可达后的某个时刻，自动解除其对象的固定状态，因此被引用的对象不会泄漏。不过，这意味着在整个 cgo 调用期间，或只要 C 仍然保留对固定 Go 指针的引用，就必须让 Pinner 本身保持存活。

复用 Pinner 是安全的，而且值得提倡，这样可以避免新 Pinner 首次使用时的初始化开销。

Pinner 的零值可直接使用。

func (p *Pinner) Pin(pointer any)

Pin 固定 Go 对象，防止垃圾回收器移动或释放它，直到调用 Pinner.Unpin 方法。

指向已固定对象的指针可以直接存储在 C 内存中，也可以包含在传给 C 函数的 Go 内存中。如果已固定对象自身还包含指向 Go 对象的指针，那么若要从 C 代码访问这些对象，也必须分别固定它们。
