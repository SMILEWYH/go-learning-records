简介

数据竞争是并发系统中最常见、也最难调试的缺陷之一。当两个 goroutine 并发访问同一变量，且至少有一次访问是写入，又没有适当同步时，就会发生数据竞争。详情参见Go 内存模型。

下面的数据竞争示例可能导致程序崩溃和内存损坏： 

func main() {
	c := make(chan bool)
	m := make(map[string]string)
	go func() {
		m["1"] = "a" // First conflicting access.
		c <- true
	}()
	m["2"] = "b" // Second conflicting access.
	<-c
	for k, v := range m {
		fmt.Println(k, v)
	}
}

用法

Go 内置了数据竞争检测器，帮助诊断这类缺陷。使用时，在 go 命令后添加 -race 标志： 

$ go test -race mypkg    // to test the package
$ go run -race mysrc.go  // to run the source file
$ go build -race mycmd   // to build the command
$ go install -race mypkg // to install the package

选项

使用 GORACE 环境变量设置竞争检测器选项，格式如下： 

GORACE="option1=val1 option2=val2"

可用选项包括：

  • log_path（默认 stderr）：将报告写入名为 log_path.pid 的文件。特殊名称 stdout 和 stderr 分别表示标准输出和标准错误。
  • exitcode（默认 66）：检测到竞争后退出时使用的退出状态码。
  • strip_path_prefix（默认 ""）：从报告中的所有文件路径中移除该前缀，使报告更简洁。
  • history_size（默认 1）：每个 goroutine 的内存访问历史长度为 32K * 2**history_size elements。增大该值可以避免报告中的“failed to restore the stack”（无法恢复调用栈）错误，但会增加内存用量。
  • halt_on_error（默认 0）：控制是否在报告首个数据竞争后退出程序。
  • atexit_sleep_ms（默认 1000）：退出前主 goroutine 的休眠时间，单位为毫秒。

示例： 

$ GORACE="log_path=/tmp/race/report strip_path_prefix=/my/go/sources/" go test -race

排除测试

使用 -race 构建时，go 命令会额外定义 race 构建标签。可以借此在启用竞争检测器时排除部分代码和测试。例如： 

// +build !race

package foo

// The test contains a data race. See issue 123.
func TestFoo(t *testing.T) {
	// ...
}

// The test fails under the race detector due to timeouts.
func TestBar(t *testing.T) {
	// ...
}

// The test takes too long under the race detector.
func TestBaz(t *testing.T) {
	// ...
}

使用方法

先使用竞争检测器运行测试（go test -race）。检测器只能发现运行时实际发生的竞争，无法检查未执行到的代码路径。如果测试覆盖不完整，可以在真实工作负载下运行使用 -race 构建的二进制程序，以发现更多竞争。

典型的数据竞争

下面是一些典型的数据竞争，都可以由竞争检测器发现。

循环计数器的数据竞争 

func main() {
	var wg sync.WaitGroup
	wg.Add(5)
	var i int
	for i = 0; i < 5; i++ {
		go func() {
			fmt.Println(i) // Not the 'i' you are looking for.
			wg.Done()
		}()
	}
	wg.Wait()
}

函数字面量中的 i 与循环使用的是同一个变量，因此 goroutine 对它的读取会与循环的自增操作发生竞争。（这个程序通常输出 55555，而不是 01234。）可以通过复制变量来修复： 

func main() {
	var wg sync.WaitGroup
	wg.Add(5)
	var i int
	for i = 0; i < 5; i++ {
		go func(j int) {
			fmt.Println(j) // Good. Read local copy of the loop counter.
			wg.Done()
		}(i)
	}
	wg.Wait()
}

意外共享的变量 

// ParallelWrite writes data to file1 and file2, returns the errors.
func ParallelWrite(data []byte) chan error {
	res := make(chan error, 2)
	f1, err := os.Create("file1")
	if err != nil {
		res <- err
	} else {
		go func() {
			// This err is shared with the main goroutine,
			// so the write races with the write below.
			_, err = f1.Write(data)
			res <- err
			f1.Close()
		}()
	}
	f2, err := os.Create("file2") // The second conflicting write to err.
	if err != nil {
		res <- err
	} else {
		go func() {
			_, err = f2.Write(data)
			res <- err
			f2.Close()
		}()
	}
	return res
}

修复方法是在各 goroutine 内声明新的变量，注意这里使用 :=： 

			...
			_, err := f1.Write(data)
			...
			_, err := f2.Write(data)
			...

未保护的全局变量

多个 goroutine 调用下面的代码时，会在 service 映射上产生竞争。并发读写同一个 map 并不安全： 

var service map[string]net.Addr

func RegisterService(name string, addr net.Addr) {
	service[name] = addr
}

func LookupService(name string) net.Addr {
	return service[name]
}

可以使用互斥锁保护访问，使代码安全： 

var (
	service   map[string]net.Addr
	serviceMu sync.Mutex
)

func RegisterService(name string, addr net.Addr) {
	serviceMu.Lock()
	defer serviceMu.Unlock()
	service[name] = addr
}

func LookupService(name string) net.Addr {
	serviceMu.Lock()
	defer serviceMu.Unlock()
	return service[name]
}

未保护的基本类型变量

基本类型变量（如 bool、int、int64 等）同样可能发生数据竞争，例如： 

type Watchdog struct{ last int64 }

func (w *Watchdog) KeepAlive() {
	w.last = time.Now().UnixNano() // First conflicting access.
}

func (w *Watchdog) Start() {
	go func() {
		for {
			time.Sleep(time.Second)
			// Second conflicting access.
			if w.last < time.Now().Add(-10*time.Second).UnixNano() {
				fmt.Println("No keepalives for 10 seconds. Dying.")
				os.Exit(1)
			}
		}
	}()
}

即使看似“无害”的数据竞争，也可能因为内存访问不是原子的、与编译器优化相互影响，或处理器内存访问重排序，而导致难以调试的问题。

常见的修复方法是使用通道或互斥锁。如果希望保持无锁访问，也可以使用 sync/atomic 包。 

type Watchdog struct{ last int64 }

func (w *Watchdog) KeepAlive() {
	atomic.StoreInt64(&w.last, time.Now().UnixNano())
}

func (w *Watchdog) Start() {
	go func() {
		for {
			time.Sleep(time.Second)
			if atomic.LoadInt64(&w.last) < time.Now().Add(-10*time.Second).UnixNano() {
				fmt.Println("No keepalives for 10 seconds. Dying.")
				os.Exit(1)
			}
		}
	}()
}

未同步的发送和关闭操作

如下例所示，对同一个通道执行未同步的发送与关闭，也会产生竞争： 

c := make(chan struct{}) // or buffered channel

// The race detector cannot derive the happens before relation
// for the following send and close operations. These two operations
// are unsynchronized and happen concurrently.
go func() { c <- struct{}{} }()
close(c)

根据 Go 内存模型，通道发送操作先发生于（happens before）与其对应的接收操作完成。要同步发送和关闭，可以通过接收操作确保发送在关闭之前完成： 

c := make(chan struct{}) // or buffered channel

go func() { c <- struct{}{} }()
<-c
close(c)

使用要求

竞争检测器要求启用 cgo；在非 Darwin 系统上，还需要安装 C 编译器。支持的平台包括 linux/amd64、linux/ppc64le、linux/arm64、linux/s390x、linux/loong64、freebsd/amd64、netbsd/amd64、darwin/amd64、darwin/arm64 和 windows/amd64。

在 Windows 上，竞争检测器运行时依赖所安装 C 编译器的版本。从 Go 1.21 起，使用 -race 构建程序需要 C 编译器包含第 8 版或更新的 mingw-w64 运行时库。可以向 C 编译器传入 --print-file-name libsynchronization.a 参数来检查：符合要求的新编译器会输出该库的完整路径，旧编译器则只会原样输出参数。

运行时开销

竞争检测开销因程序而异。对于典型程序，内存用量可能增至原来的 5～10 倍，执行时间可能增至 2～20 倍。

当前，竞争检测器会为每条 defer 和 recover 语句额外分配 8 字节，这些分配直到 goroutine 退出才会回收。因此，长期运行的 goroutine 如果不断执行 defer 和 recover，可能导致程序内存持续增长。这些额外分配不会出现在 runtime.ReadMemStats 或 runtime/pprof 的结果中。
