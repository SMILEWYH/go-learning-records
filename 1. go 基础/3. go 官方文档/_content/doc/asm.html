Go 汇编器快速指南

本文简要介绍 gc Go 编译器使用的一种较为特殊的汇编语言形式，并非完整参考手册。

Go 汇编器的输入风格源自 Plan 9 汇编器，其详细说明见这份文档。如果打算编写汇编代码，即使其中许多内容只适用于 Plan 9，也应阅读该文档。本文概述相关语法、与该文档描述的差异，以及编写与 Go 交互的汇编代码时需要注意的特殊之处。

理解 Go 汇编器最重要的一点是：它并不直接表示底层机器。有些细节与机器精确对应，有些则不对应。这是因为编译器工具集（参见此说明）在通常的处理流程中不需要独立的汇编阶段。编译器操作的是一种半抽象指令集，部分指令选择发生在代码生成之后。汇编器也处理这种半抽象形式，因此看到 MOV 之类的指令时，工具链实际生成的操作可能根本不是移动，而是清零或加载；也可能恰好对应同名机器指令。总体而言，机器专用操作通常直接表现为自身，而内存移动、子程序调用和返回等更通用的概念则更加抽象。具体细节因体系结构而异；对于描述不够精确之处，我们深表歉意，因为这些行为并没有完全明确的统一定义。

汇编器程序解析这种半抽象指令集的描述，并将其转换为供链接器输入的指令。要了解某种体系结构（例如 amd64）的汇编指令形式，可以参考标准库源码中的大量示例，例如 runtime 和 math/big 包。也可以查看编译器生成的汇编代码，实际输出可能与下例不同：

常量

虽然 Go 汇编器参考了 Plan 9 汇编器，但它是独立的程序，因此存在一些差异。其中之一是常量求值。汇编器按照 Go 的运算符优先级解析常量表达式，而不是原版的类 C 优先级。因此，3&1<<2 的结果为 4，而不是 0：它被解析为 (3&1)<<2，而不是 3&(1<<2)。此外，常量始终按照 64 位无符号整数求值。因此，-2 并不是整数负二，而是具有相同比特模式的 64 位无符号整数。这种区别通常影响不大，但为避免歧义，当除法或右移运算的右操作数最高位为 1 时，汇编器会拒绝该表达式。

符号

某些符号，例如 R1 或 LR，是预定义的寄存器名称，具体集合取决于体系结构。

有四个预声明符号用于表示伪寄存器。它们并非真实寄存器，而是工具链维护的虚拟寄存器，例如虚拟帧指针。所有体系结构都使用相同的伪寄存器集合：

  • FP：帧指针，用于参数和局部变量。
  • PC：程序计数器，用于跳转和分支。
  • SB：静态基址指针，用于全局符号。
  • SP：栈指针，指向局部栈帧中的最高地址。

所有用户定义的符号，都写成相对于伪寄存器 FP（参数和局部变量）或 SB（全局符号）的偏移形式。

可以将 SB 伪寄存器视为内存的起点，因此 foo(SB) 表示符号 foo 在内存中的地址。这种形式用于命名全局函数和数据。在名称后添加 <>，例如 foo<>(SB)，会使该名称仅在当前源文件中可见，类似于 C 文件中的顶层 static 声明。在名称后添加偏移量，表示相对于符号地址的偏移，因此 foo+4(SB) 表示 foo 起始地址之后 4 字节的位置。

FP 是用于引用函数参数的虚拟帧指针。编译器维护这个虚拟帧指针，以相对偏移引用栈上的参数。因此，0(FP) 表示第一个参数，8(FP) 表示第二个参数（在 64 位机器上），依此类推。不过，以这种方式引用参数时，必须在前面加上名称，例如 first_arg+0(FP) 和 second_arg+8(FP)。这里的偏移相对于帧指针，而 SB 中的偏移相对于符号地址，两者不同。汇编器强制要求这一约定，会拒绝单独的 0(FP) 和 8(FP)。名称本身不影响语义，但应当用它说明参数名。需要强调，FP 始终是伪寄存器，即使体系结构具有硬件帧指针，它也不是硬件寄存器。

对于具有 Go 函数声明的汇编函数，go vet 会检查参数名和偏移是否匹配。在 32 位系统上，通过在名称后添加 _lo 或 _hi 区分 64 位值的低 32 位和高 32 位，例如 arg_lo+0(FP)、arg_hi+4(FP)。如果 Go 声明没有为返回值命名，汇编中预期的名称为 ret。

SP 是虚拟栈指针，用于引用栈帧内的局部变量和为函数调用准备的参数。它指向局部栈帧中的最高地址，因此引用应使用 [−framesize, 0) 范围内的负偏移，例如 x-8(SP)、y-4(SP)。

在硬件寄存器也名为 SP 的体系结构上，通过名称前缀区分虚拟栈指针和硬件 SP。也就是说，x-8(SP) 和 -8(SP) 表示不同的内存位置：前者相对于虚拟栈指针伪寄存器，后者相对于硬件 SP 寄存器。

在传统上将 SP 和 PC 作为带编号物理寄存器别名的机器上，Go 汇编器仍对这两个名称作特殊处理。例如，引用 SP 时像 FP 一样需要符号名称。要访问实际硬件寄存器，应使用真实的 R 名称。例如 ARM 上的硬件 SP 和 PC 分别通过 R13 和 R15 访问。

分支和直接跳转始终写成相对 PC 的偏移，或跳转到标签的形式： 

label:
	MOVW $0, R1
	JMP label

每个标签仅在其定义所在的函数内可见，因此，同一文件中的多个函数可以定义并使用相同的标签名。直接跳转和调用指令可以以 name(SB) 等代码符号为目标，但不能跳到 name+4(SB) 这样的符号偏移位置。

指令、寄存器和汇编器指令始终使用大写字母，以提醒你汇编编程需要格外谨慎。例外是 ARM 上重命名的 g 寄存器。

在 Go 目标文件和二进制文件中，符号的完整名称由包路径、句点和符号名组成，例如 fmt.Printf 或 math/rand.Int。汇编器的解析器将句点和斜杠视为标点，因此这些字符串不能直接用作标识符。汇编器允许在标识符中使用中点字符 U+00B7 和除法斜杠 U+2215，并将它们改写为普通句点和斜杠。因此，上述符号在汇编源文件中写作 fmt·Printf 和 math∕rand·Int。编译器使用 -S 输出的汇编清单直接显示句点和斜杠，不使用汇编源文件所要求的 Unicode 替代字符。

大多数手写汇编文件不会在符号名中包含完整包路径，因为链接器会在任何以句点开头的名称前补上当前目标文件的包路径。例如，在 math/rand 包的汇编实现中，可以用 ·Int 引用该包的 Int 函数。这避免了在包自己的源码中硬编码导入路径，便于将代码迁移到其他位置。

汇编器指令

汇编器使用各种指令，将代码和数据绑定到符号名。下面是一个简单而完整的函数定义。TEXT 声明符号 runtime·profileloop，后续指令组成函数体。TEXT 块的最后一条指令必须是某种跳转，通常为 RET 伪指令；否则链接器会追加一条跳向自身的指令，因为不同 TEXT 块之间不会顺序贯穿执行。符号后面的参数依次是标志位（见下文）和常量形式的栈帧大小，后者也有下文说明的特殊语法： 

TEXT runtime·profileloop(SB),NOSPLIT,$8
	MOVQ	$runtime·profileloop1(SB), CX
	MOVQ	CX, 0(SP)
	CALL	runtime·externalthreadhandler(SB)
	RET

通常，栈帧大小之后还要写参数大小，中间用减号分隔。这不是减法，只是一种特殊语法。$24-8 表示该函数具有 24 字节栈帧，并使用位于调用方栈帧中的 8 字节参数。如果 TEXT 未指定 NOSPLIT，就必须提供参数大小。对于具有 Go 声明的汇编函数，go vet 会检查参数大小是否正确。

注意，符号名使用中点分隔各部分，并写成相对于静态基址伪寄存器 SB 的偏移形式。在 runtime 包的 Go 源码中，可以用简单名称 profileloop 调用该函数。

全局数据符号由一系列用于初始化的 DATA 指令和紧随其后的 GLOBL 指令定义。每条 DATA 初始化相应内存的一部分，未显式初始化的内存会清零。DATA 的一般形式为： 

DATA	symbol+offset(SB)/width, value

它使用给定值，初始化符号内存中指定偏移和宽度的区域。同一符号的 DATA 指令必须按偏移递增的顺序书写。

GLOBL 将符号声明为全局符号。参数包括可选的标志位，以及声明为全局数据的大小。除非已经通过 DATA 初始化，否则初始值全为零。GLOBL 必须写在所有对应的 DATA 指令之后。

例如： 

DATA divtab<>+0x00(SB)/4, $0xf4f8fcff
DATA divtab<>+0x04(SB)/4, $0xe6eaedf0
...
DATA divtab<>+0x3c(SB)/4, $0x81828384
GLOBL divtab<>(SB), RODATA, $64

GLOBL runtime·tlsoffset(SB), NOPTR, $4

这段代码声明并初始化了 divtab<>，一个由 4 字节整数构成的只读表，总大小为 64 字节；同时声明了 runtime·tlsoffset，一个不包含指针、隐式清零的 4 字节变量。

这些指令可以有一个或两个参数。若有两个，第一个是标志位掩码，可以写为相加或按位或组合的数值表达式，也可以使用符号名称以便阅读。这些标志定义在标准 #include 文件 textflag.h 中，取值如下：

  • NOPROF = 1
    用于 TEXT。不对标记的函数进行性能剖析。此标志已弃用。
  • DUPOK = 2
    允许同一二进制文件中存在该符号的多个实例，链接器会选择其中一个使用。
  • NOSPLIT = 4
    用于 TEXT。不插入检查是否需要分裂栈的前导代码。该函数及其所调用函数所需的栈空间，必须能够容纳在当前栈段剩余的空间内。用于保护栈分裂代码自身等底层例程。
  • RODATA = 8
    用于 DATA 和 GLOBL。将数据放入只读区段。
  • NOPTR = 16
    用于 DATA 和 GLOBL。数据不包含指针，因此无需垃圾回收器扫描。
  • WRAPPER = 32
    用于 TEXT。表示包装函数，在判断 recover 是否有效时，不应把这一层视为导致 recover 失效的调用层。
  • NEEDCTXT = 64
    用于 TEXT。表示闭包函数，会使用传入的上下文寄存器。
  • LOCAL = 128
    该符号仅在当前动态共享对象内可见。
  • TLSBSS = 256
    用于 DATA 和 GLOBL。将数据放入线程局部存储。
  • NOFRAME = 512
    用于 TEXT。即使不是叶子函数，也不插入分配栈帧和保存、恢复返回地址的指令。仅对声明栈帧大小为 0 的函数有效。
  • TOPFRAME = 2048
    用于 TEXT。表示调用栈最外层的函数，栈回溯应在此停止。

特殊指令

PCALIGN 伪指令要求通过填充空操作指令，将下一条指令对齐到指定边界。

目前支持 arm64、amd64、ppc64、loong64 和 riscv64。例如，下面的 MOVD 指令起始位置按 32 字节对齐： 

PCALIGN $32
MOVD $2, R0

与 Go 类型和常量交互

如果包中存在 .s 文件，go build 会要求编译器生成名为 go_asm.h 的特殊头文件，供 .s 文件通过 #include 引入。它通过 #define 提供 Go 结构体字段偏移、结构体大小，以及当前包中大多数 Go const 声明对应的符号常量。Go 汇编代码应使用这些常量，避免假定 Go 类型的内存布局。这既提高可读性，也能适应 Go 类型定义或编译器布局规则的变化。

常量名称采用 const_name 形式。例如，对于 Go 声明 const bufSize = 1024，汇编代码可以使用 const_bufSize 引用其值。

字段偏移采用 type_field 形式，结构体大小采用 type__size 形式。例如，考虑以下 Go 定义： 

type reader struct {
	buf [bufSize]byte
	r   int
}

汇编代码可以通过 reader__size 引用结构体大小，通过 reader_buf 和 reader_r 引用两个字段的偏移。因此，如果寄存器 R1 保存着指向 reader 的指针，就可以用 reader_r(R1) 引用 r 字段。

如果这些 #define 名称存在歧义，例如结构体中有一个名为 _size 的字段，#include "go_asm.h" 会因“redefinition of macro”（宏重定义）错误而失败。

与运行时协调

为了让垃圾回收正确运行，运行时必须知道所有全局数据和大多数栈帧中的指针位置。Go 编译器在编译 Go 源文件时会生成这些信息，但汇编程序必须显式定义。

带有 NOPTR 标志的数据符号，被视为不包含指向运行时分配数据的指针。带有 RODATA 标志的数据符号位于只读内存中，因此隐含 NOPTR。总大小小于一个指针的数据符号，也隐含 NOPTR。汇编源文件不能定义包含指针的符号，这类符号必须在 Go 源文件中定义。即使没有 DATA 和 GLOBL 指令，汇编代码仍可按名称引用它。一个实用原则是：所有非 RODATA 符号都应在 Go 中定义，而不是在汇编中定义。

每个函数还需要注解，说明参数、返回值和局部栈帧中存活指针的位置。如果汇编函数没有指针返回值，并且没有局部栈帧，或者没有函数调用，那么只需在同一包的 Go 源文件中为其提供函数声明。汇编函数名称不能包含包名部分，例如 syscall 包的 Syscall 函数，应在 TEXT 指令中使用 ·Syscall，而不是等价的 syscall·Syscall。更复杂的情况需要显式注解，这些注解使用标准 #include 文件 funcdata.h 中定义的伪指令。

如果函数既没有参数，也没有返回值，可以省略指针信息，通过 TEXT 上的参数大小标注 $n-0 表示。否则，即使汇编函数并不由 Go 直接调用，也必须在 Go 源文件中提供函数声明，以生成指针信息；该声明也能让 go vet 检查参数引用。函数入口处假定参数已初始化、返回值未初始化。如果在执行调用指令时，返回值中会包含存活指针，函数应先将返回值清零，再执行 GO_RESULTS_INITIALIZED 伪指令。它记录返回值已经初始化，需要在栈移动和垃圾回收时扫描。通常，让汇编函数不返回指针，或不包含调用指令会更简单；标准库中的汇编函数均未使用 GO_RESULTS_INITIALIZED。

如果函数没有局部栈帧，可以省略指针信息，通过 TEXT 上的局部帧大小标注 $0-n 表示。函数没有调用指令时，也可以省略。否则，局部栈帧不得包含指针，且汇编代码必须执行 NO_LOCAL_POINTERS 伪指令来确认这一点。由于栈扩缩容通过移动栈实现，任何函数调用期间栈指针都可能变化，因此连指向栈数据的指针也不能保存在局部变量中。

汇编函数始终应提供 Go 函数声明，既用于提供参数和返回值的指针信息，也让 go vet 检查访问它们所用的偏移是否正确。

各体系结构的细节

逐一列出每种机器的所有指令和细节并不现实。要查看某种机器（例如 ARM）定义的指令，可以阅读该体系结构的 obj 支持库源码，位于 src/cmd/internal/obj/arm。其中的 a.out.go 文件包含一长串以 A 开头的常量，例如： 

const (
	AAND = obj.ABaseARM + obj.A_ARCHSPECIFIC + iota
	AEOR
	ASUB
	ARSB
	AADD
	...

这就是该体系结构的汇编器和链接器所认识的指令及其拼写。列表中的每条指令都以大写 A 开头，因此 AAND 表示按位与指令 AND，在汇编源码中去掉前缀 A，写为 AND。枚举大体按字母顺序排列。定义在 cmd/internal/obj 中、与体系结构无关的 AXXX 表示无效指令。这些 A 名称的排列顺序与机器指令的实际编码无关，编码细节由 cmd/internal/obj 处理。

386 和 AMD64 的指令都列在 cmd/internal/obj/x86/a.out.go 中。

各种体系结构对常见寻址模式使用相同语法，例如 (R1) 表示寄存器间接寻址，4(R1) 表示带偏移的寄存器间接寻址，$foo(SB) 表示绝对地址。汇编器还支持各体系结构特有的部分寻址模式，但不一定全部支持。下面分别列出。

从前面的示例可以看出，指令中的数据从左向右流动：MOVQ $0, CX 会清零 CX。即使某些体系结构的传统写法方向相反，也遵守这一规则。

下面介绍各受支持体系结构中，与 Go 有关的一些关键细节。

32 位 Intel 386

运行时指向 g 结构体的指针，通过 MMU 中一个对 Go 而言不作其他用途的寄存器值维护。在 runtime 包中，汇编代码可以包含 go_tls.h，使用其中依赖操作系统和体系结构的 get_tls 宏访问该寄存器。宏接收一个参数，用于指定将 g 指针加载到哪个寄存器。

例如，使用 CX 加载 g 和 m 的指令序列如下： 

#include "go_tls.h"
#include "go_asm.h"
...
get_tls(CX)
MOVL	g(CX), AX     // Move g into AX.
MOVL	g_m(AX), BX   // Move g.m into BX.

amd64 上也定义了 get_tls 宏。

寻址模式：

  • (DI)(BX*2)：地址 DI 加 BX*2 所指的位置。
  • 64(DI)(BX*2)：地址 DI 加 BX*2 再加 64 所指的位置。这些模式只允许 1、2、4、8 作为比例因子。

使用编译器和汇编器的 -dynlink 或 -shared 模式时，必须假定对全局变量等固定内存位置的任何加载或存储都会覆盖 CX。因此，为安全兼容这些模式，汇编源码通常应避免使用 CX，除非只在相邻内存访问之间短暂使用。

64 位 Intel 386（即 amd64）

这两种体系结构在汇编器层面基本相同。64 位版本中访问 m 和 g 指针的汇编，与 32 位 386 相同，只是使用 MOVQ，而不是 MOVL： 

get_tls(CX)
MOVQ	g(CX), AX     // Move g into AX.
MOVQ	g_m(AX), BX   // Move g.m into BX.

BP 是由被调用方保存的寄存器。栈帧大小大于零时，汇编器会自动插入保存和恢复 BP 的指令。允许将 BP 用作通用寄存器，但可能干扰基于采样的性能剖析。

ARM

编译器和链接器保留了寄存器 R10 和 R11。

R10 指向 g（goroutine）结构体。在汇编源码中，必须用 g 引用该指针；名称 R10 不会被识别。

为便于开发者和编译器编写汇编，ARM 链接器允许通用寻址形式，以及 DIV、MOD 等可能无法用单条硬件指令表达的伪操作。链接器会将这些形式实现为多条指令，通常使用 R11 保存临时值。手写汇编可以使用 R11，但必须确保链接器不会同时用它实现函数中的其他指令。

定义 TEXT 时，栈帧大小设为 $-4，表示这是一个入口处无需保存 LR 的叶子函数。

名称 SP 始终表示前文的虚拟栈指针。访问硬件寄存器时，使用 R13。

条件码的语法是在指令后添加句点和一到两个字母的代码，例如 MOVW.EQ。可以同时添加多个代码，例如 MOVM.IA.W，这些修饰符的顺序不影响含义。

寻址模式：

  • R0->16
    R0>>16
    R0<<16
    R0@>16：<< 将 R0 左移 16 位。其他代码分别为 ->（算术右移）、>>（逻辑右移）和 @>（循环右移）。
  • R0->R1
    R0>>R1
    R0<<R1
    R0@>R1：<< 将 R0 左移 R1 指定的位数。其他代码分别为 ->（算术右移）、>>（逻辑右移）和 @>（循环右移）。
  • [R0,g,R12-R15]：用于多寄存器指令，表示包含 R0、g 以及 R12 至 R15 的寄存器集合。
  • (R5, R6)：目标寄存器对。

ARM64

R18 是“平台寄存器”，在 Apple 平台上保留使用。为避免误用，命名为 R18_PLATFORM。编译器和链接器保留 R27、R28。R29 是帧指针，R30 是链接寄存器。

指令修饰符通过句点附加在指令之后。仅有 P（后增量）和 W（前增量）两种，例如 MOVW.P、MOVW.W。

寻址模式：

  • R0->16
    R0>>16
    R0<<16
    R0@>16：与 32 位 ARM 相同。
  • $(8<<12)：将立即数 8 左移 12 位。
  • 8(R0)：将 R0 的值与 8 相加。
  • (R2)(R0)：地址 R0 加 R2 所指的位置。
  • R0.UXTB
    R0.UXTB<<imm：UXTB 从 R0 的低位提取 8 位值，并零扩展到 R0 的宽度。R0.UXTB<<imm 将 R0.UXTB 的结果左移 imm 位，imm 可以为 0、1、2、3、4。其他扩展包括 UXTH（16 位）、UXTW（32 位）和 UXTX（64 位）。
  • R0.SXTB
    R0.SXTB<<imm：SXTB 从 R0 的低位提取 8 位值，并符号扩展到 R0 的宽度。R0.SXTB<<imm 将 R0.SXTB 的结果左移 imm 位，imm 可以为 0、1、2、3、4。其他扩展包括 SXTH（16 位）、SXTW（32 位）和 SXTX（64 位）。
  • (R5, R6)：用于 LDAXP/LDP/LDXP/STLXP/STP/STP 的寄存器对。

参考：Go ARM64 汇编指令参考手册。

IBM z/Architecture（即 s390x）

R10 和 R11 是保留寄存器，汇编器在汇编某些指令时用它们保存临时值。

R13 指向 g（goroutine）结构体。必须通过 g 引用此寄存器，名称 R13 不会被识别。

R15 指向栈帧，通常只应通过虚拟寄存器 SP 和 FP 访问。

多寄存器加载和存储指令作用于一段寄存器范围，通过起始和结束寄存器指定。例如，LMG (R9), R5, R7 会将 0(R9)、8(R9) 和 16(R9) 处的 64 位值，分别加载到 R5、R6 和 R7。

MVC 和 XC 等存储到存储指令，将长度写为第一个参数。例如，XC $8, (R9), (R9) 会清零 R9 指定地址处的 8 字节。

如果向量指令接收长度或索引参数，该参数必须放在第一位。例如，VLEIF $1, $16, V2 会将数值 16 加载到 V2 的索引 1 位置。使用向量指令时，应确保运行环境支持它。机器既需要向量设施（设施列表中的第 129 位），也需要内核支持。如果缺少内核支持，向量指令不会产生效果，相当于 NOP。

寻址模式：

  • (R5)(R6*1)：地址 R5 加 R6 所指的位置。这是一种类似 x86 的比例寻址模式，但唯一允许的比例因子是 1。

MIPS、MIPS64

通用寄存器名为 R0 至 R31，浮点寄存器名为 F0 至 F31。

R30 保留用于指向 g，R23 用作临时寄存器。

在 TEXT 指令中，MIPS 的栈帧大小设为 $-4，或 MIPS64 的栈帧大小设为 $-8，表示要求链接器不保存 LR。

SP 表示虚拟栈指针。访问硬件寄存器时，使用 R29。

寻址模式：

  • 16(R1)：地址 R1 加 16 所指的位置。
  • (R1)：0(R1) 的别名。

汇编代码通过预定义的 GOMIPS_hardfloat 或 GOMIPS_softfloat，获知环境变量 GOMIPS 的值是 hardfloat 还是 softfloat。

汇编代码通过预定义的 GOMIPS64_hardfloat 或 GOMIPS64_softfloat，获知环境变量 GOMIPS64 的值是 hardfloat 还是 softfloat。

不受支持的操作码

汇编器主要为编译器提供支持，因此并非每种体系结构都定义了全部硬件指令：如果编译器不会生成某条指令，汇编器也可能不支持。需要使用缺失指令时，有两种办法。第一种是修改汇编器以支持该指令，这通常比较直接，但只有预计将来还会继续使用时才值得这样做。对于简单的一次性需求，也可以在 TEXT 中通过 BYTE 和 WORD 指令，将明确的数据字节写入指令流。下面展示 386 运行时如何定义 64 位原子加载函数。 

// uint64 atomicload64(uint64 volatile* addr);
// so actually
// void atomicload64(uint64 *res, uint64 volatile *addr);
TEXT runtime·atomicload64(SB), NOSPLIT, $0-12
	MOVL	ptr+0(FP), AX
	TESTL	$7, AX
	JZ	2(PC)
	MOVL	0, AX // crash with nil ptr deref
	LEAL	ret_lo+4(FP), BX
	// MOVQ (%EAX), %MM0
	BYTE $0x0f; BYTE $0x6f; BYTE $0x00
	// MOVQ %MM0, 0(%EBX)
	BYTE $0x0f; BYTE $0x7f; BYTE $0x03
	// EMMS
	BYTE $0x0F; BYTE $0x77
	RET
