以下说明适用于标准工具链（gc Go 编译器及其工具）。 Gccgo 原生支持 gdb。

调试使用标准工具链构建的 Go 程序时，Delve 是比 GDB 更合适的选择。 它对 Go 运行时、数据结构和表达式的理解都优于 GDB。 Delve 目前支持 amd64 架构上的 Linux、OSX 和 Windows。 最新的支持平台列表，请参阅 Delve 文档。

GDB 对 Go 程序的支持并不完善。 Go 的栈管理、线程和运行时中的一些机制与 GDB 预期的执行模型存在较大差异，可能使调试器产生误判，给出错误结果，即使程序由 gccgo 编译也是如此。 因此，虽然 GDB 在某些场景下有用（例如调试 Cgo 代码或运行时本身），但它并不是可靠的 Go 程序调试器，对大量使用并发的程序尤其如此。 此外，这些问题解决起来很困难，也不是 Go 项目的优先事项。

以下说明仅用于介绍在 GDB 能够正常工作的情况下如何使用它，并不能保证调试一定成功。 除了本文的概述，你还可以查阅 GDB 手册。

简介

在 Linux、macOS、FreeBSD 或 NetBSD 上使用 gc 工具链编译、链接 Go 程序时，生成的二进制文件会包含 DWARFv4 调试信息。 较新的 GDB 调试器（≥7.5）可以使用这些信息检查正在运行的进程或核心转储文件。

向链接器传入 '-w' 标志可以省略调试信息（例如，go build -ldflags=-w prog.go）。

gc 编译器生成代码时会进行函数调用内联、将变量分配到寄存器等优化。 这些优化有时会增加使用 gdb 调试的难度。 如果需要禁用这些优化，请使用 go build -gcflags=all="-N -l" 构建程序。

如果希望使用 gdb 检查核心转储，可以在支持此功能的系统中设置环境变量 GOTRACEBACK=crash，让程序崩溃时生成转储文件（更多信息见 runtime 包文档）。

常用操作

  • 显示代码的文件名和行号、设置断点，以及反汇编： 
    (gdb) list
(gdb) list line
(gdb) list file.go:line
(gdb) break line
(gdb) break file.go:line
(gdb) disas
  • 显示调用栈回溯并切换栈帧： 
    (gdb) bt
(gdb) frame n
  • 显示局部变量、参数和返回值的名称、类型及其在栈帧中的位置： 
    (gdb) info locals
(gdb) info args
(gdb) p variable
(gdb) whatis variable
  • 显示全局变量的名称、类型和位置： 
    (gdb) info variables regexp

Go 扩展

GDB 较新的扩展机制允许它为指定的二进制文件加载扩展脚本。 工具链利用这一机制为 GDB 增加了一些命令，用于检查运行时代码的内部状态（例如 goroutine，轻量级协程），并以易读的格式显示内置的映射（map）、切片和通道类型。

  • 以易读格式显示字符串、切片、映射、通道或接口： 
    (gdb) p var
  • 用于字符串、切片和映射的 $len() 与 $cap() 函数： 
    (gdb) p $len(var)
  • 将接口转换为其动态类型的函数： 
    (gdb) p $dtype(var)
(gdb) iface var

    已知问题：如果接口值的动态类型的完整名称与简短名称不同，GDB 无法自动找到该动态类型。 这在打印调用栈时很不方便，因为格式化打印器会退回到输出简短类型名和一个指针。

  • 检查 goroutine： 
    (gdb) info goroutines
(gdb) goroutine n cmd
(gdb) help goroutine
    例如： 
    (gdb) goroutine 12 bt
    将具体的 goroutine ID 替换为 all，就可以检查所有 goroutine。 例如： 
    (gdb) goroutine all bt

如果你想了解其工作原理或扩展其功能，可以查看 Go 源码发行包中的 src/runtime/runtime-gdb.py。 它依赖一些特殊类型（hash<T,U>）和变量（runtime.m 与 runtime.g）， 链接器（src/cmd/link/internal/ld/dwarf.go）会确保在 DWARF 信息中描述这些类型和变量。

如果想查看调试信息的具体内容，可以运行 objdump -W a.out，浏览其中的 .debug_* 节。

已知问题

  1. 字符串的格式化显示只对 string 类型生效，对基于它定义的类型不生效。
  2. 运行时库中的 C 语言部分缺少类型信息。
  3. GDB 无法理解 Go 的名称限定规则，会把 "fmt.Print" 视为包含 "." 的无结构字面量，因此必须加上引号。 对于 pkg.(*MyType).Meth 形式的方法名，它的处理问题更明显。
  4. 从 Go 1.11 开始，调试信息默认会被压缩。 较旧的 gdb（例如 MacOS 默认提供的版本）不支持这种压缩。 可以使用 go build -ldflags=-compressdwarf=false 生成未压缩的调试信息。 为方便使用，可以将 -ldflags 选项放入 GOFLAGS 环境变量中，这样就不必每次都指定它。

教程

本教程将检查 regexp 包单元测试生成的二进制文件。 要构建该文件，请切换到 $GOROOT/src/regexp，运行 go test -c。 这会生成名为 regexp.test 的可执行文件。

启动 GDB，调试 regexp.test：

“Loading Go Runtime support”消息表示 GDB 已从 $GOROOT/src/runtime/runtime-gdb.py 加载了扩展。

为了帮助 GDB 找到 Go 运行时源码及配套的支持脚本，请通过 '-d' 标志传入 $GOROOT 的路径： 

$ gdb regexp.test -d $GOROOT

如果 GDB 因某种原因仍然找不到该目录或脚本，可以手动让 gdb 加载它（假设 Go 源码位于 ~/go/）： 

(gdb) source ~/go/src/runtime/runtime-gdb.py
Loading Go Runtime support.

查看源码

使用 "l" 或 "list" 命令查看源码。 

(gdb) l

向 "list" 传入函数名，可以列出指定部分的源码；函数名必须带上包名限定。 

(gdb) l main.main

列出指定文件和行号附近的源码： 

(gdb) l regexp.go:1
(gdb) # Hit enter to repeat last command. Here, this lists next 10 lines.

名称表示

变量名和函数名必须使用所属的包名进行限定。 regexp 包中的 Compile 函数在 GDB 中表示为 'regexp.Compile'。

方法名必须使用其接收者类型的名称进行限定。 例如，*Regexp 类型的 String 方法表示为 'regexp.(*Regexp).String'。

遮蔽其他变量的变量，在调试信息中会自动附加数字后缀。 闭包引用的变量则会显示为指针，并自动添加 '&' 前缀。

格式化显示

GDB 通过对类型名进行正则表达式匹配，触发格式化显示机制。下面以切片为例： 

(gdb) p utf
$22 =  []uint8 = {0 '\000', 0 '\000', 0 '\000', 0 '\000'}

切片、数组和字符串并不是 C 指针，因此 GDB 无法直接解释它们的下标操作。 不过，可以通过查看运行时内部表示来访问元素（这里可以使用 Tab 补全）： 


(gdb) p slc
$11 =  []int = {0, 0}
(gdb) p slc-><TAB>
array  slc    len
(gdb) p slc->array
$12 = (int *) 0xf84057af00
(gdb) p slc->array[1]
$13 = 0

扩展函数 $len 和 $cap 可用于字符串、数组和切片： 

(gdb) p $len(utf)
$23 = 4
(gdb) p $cap(utf)
$24 = 4

通道和映射属于“引用”类型，gdb 会把它们显示为类似 C++ 类型的指针，例如 hash<int,string>*。 对指针解引用会触发格式化显示。

接口在运行时中由指向类型描述符的指针和指向值的指针表示。 Go 的 GDB 运行时扩展会解析这些信息，并自动对运行时类型触发格式化显示。 扩展函数 $dtype 可以解析动态类型（以下示例取自 regexp.go 第 293 行处的断点）。 

(gdb) p i
$4 = {str = "cbb"}
(gdb) whatis i
type = regexp.input
(gdb) p $dtype(i)
$26 = (struct regexp.inputBytes *) 0xf8400b4930
(gdb) iface i
regexp.input: struct regexp.inputBytes *
